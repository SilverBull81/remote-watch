### Замечания по приоритету

1. **R1, высокий для эксплуатации: не наблюдается отказ обслуживания hub.**
   [hub.py](../src/remote_watch/commands/hub.py) создаёт `_refresh_time` без
   обработчика завершения; [commands.py](../src/remote_watch/gateway/commands.py)
   смотрит только `source.stats.closed`. При неожиданном исключении именно
   в maintenance прекращаются его периодическое обновление UTC и sweep,
   но процесс/listener могут оставаться доступны. Sweep также вызывается при
   чтении результатов, поэтому не утверждается полная остановка всех очисток.
   В локальной fault injection RuntimeError добавлен только в проход sweep
   из maintenance task: задача завершена, после ещё 1,1 с у gateway и источника
   `closed=false`, `last_error=null`. Обычные ошибки CommandError не были
   подменены. Нужны явная проверка всех критичных tasks и регрессионный тест;
   общий supervisor не должен лечить такой отказ только проверкой TCP-порта.
2. **R2, высокий для эксплуатации: запуск не равен готовности команд.**
   `_update_time` намеренно поглощает сетевой отказ, оставляя TrustedClock
   недоступным. Это безопасно для свежести, но `CommandGateway.stats()` не
   показывает состояние времени. С подставным неработающим TimeSource старт
   и listener успешны, `closed=false`, `last_error=null`, доверенного времени
   нет. Нужны readiness/degraded и безопасная причина отказа. Исправление
   не должно включать fallback на часы VM или разрешать старые команды.
3. **R3, средний: сообщения о настройках слишком общие.**
   [command_config.py](../src/remote_watch/gateway/command_config.py) использует
   `field=hub` при общих проверках связей; повтор токенов двух principals
   уже вызвал затруднение у владельца. Нужны фиксированные reason codes
   для повторов token/identity, отсутствующих ссылок, CA и неверного endpoint,
   с путём к полю/индексом без значения секрета. `--check-config` остаётся
   offline-проверкой и не обещает правильный actor_id или доступность провайдера.
4. **R4, средний: нет готового управления deployment и ресурсов для deploy из wheel.**
   Существующие CLI не обеспечивают общий статус, restart policy и автозапуск;
   вывод статистики в основном появляется при остановке. Это отсутствующий
   эксплуатационный слой, а не дефект заявленной доставки. JSON-шаблоны сейчас
   входят в sdist через MANIFEST.in, но wheel содержит только пакет/metadata.
   Новому deploy-инструменту нужны package resources и тест чистой установки
   без checkout. Не переписывать ради него wire-контракты и схемы компонентов.
5. **R5, средний: после UNKNOWN оператору не хватает средств разбора.**
   Документированные pending/lookup есть, готового безопасного status/doctor
   для journal нет. Нужны наблюдение ёмкости, pending/UNKNOWN и памятка ручного
   разбора. Открытие рабочего SQLite новым владельцем ради диагностики может
   изменить generation: такой способ запрещён. Автоматическое освобождение
   UNKNOWN и повтор callback не являются исправлением этого пробела.
6. **R6, низкий: смысл комментариев и статусы документов требуют внимания.**
   Формальные style/Ruff проходят, но в `CommandParser.error` описание message
   ошибочно говорит о командной операции; ряд `:return:` в command_config и
   CommandGateway.stats перечисляет несвязанные типы результата. Исправить
   точечно при доработке соответствующих модулей. В README/плане/review были
   устаревшие «следующие шаги» и отрицание нового CI; они исправлены в этом
   документационном изменении. Ранее исправленные девять пунктов ниже сохранены
   как история, не объявлены вновь найденными проблемами.

R1/R2 воспроизведены с fake provider/time, временными SQLite и loopback listener;
реальные tokens/провайдеры/рабочие журналы не использовались. Исходный код этим
ревью не изменён: R1–R5 остаются открытыми, R6 закрыт только в части документации.

## Найдено и исправлено в 0.3.5

1. **Сбой после выбора приложения мог изменить адресата повтора.** Источник теперь
   сохраняет выбранные session/command_id до передачи запроса hub и продолжает
   именно это решение после рестарта. Смена запуска приложения не перенаправляет
   старую команду новой сессии. Позиции двух журналов сверяются до начала чтения.
2. **Обычный числовой offset Telegram не описывает все перезапуски потока.** После
   недели без updates ID может стать меньше. Чтение начинается без старого offset;
   ACK проверяет текущую голову очереди и подтверждает только сохранённое событие.
3. **Очистка ID зависела от предположения, что внешнее UTC никогда не откатится.**
   Необратимая граница удалённых дат теперь хранится в source journal. Сообщение
   старше границы отклоняется и после получения более раннего показания времени.
4. **Длинный Unicode-текст мог остановить получатель до разбора команды.** Размер
   события и допустимый размер самой команды разделены. Корректное событие с
   чрезмерной командой фиксируется как отказ; поток продолжает работу.
5. **Справка могла превысить лимит ответа провайдера.** Общий предел UTF-8 действует
   и на справку, и на итог callback; усечение заметно, ID результата остаются в начале.
6. **Rate limit Telegram нельзя читать только из HTTP-заголовка.** Учтён JSON
   `parameters.retry_after`, в том числе при разбиении ответа на сетевые порции.
   Ответы обходятся ограниченными порциями; недоступный чат не создаёт бесконечной
   внутренней очереди отправки.
7. **Второй процесс мог открыть hub с новым поколением до обнаружения конфликта
   провайдера.** Блокировка всего deployment берётся первой. Частичный запуск
   проверяет все источники до потребления событий; активный webhook не удаляется.
8. **Описание состояния отставало от кода.** В README оставалось утверждение, что
   подключение callbacks к RemoteWatcher ещё впереди. Обновлены текущие статусы,
   границы ntfy, команды запуска, шаблоны и различие реализации/полевой приёмки.
9. **Командный HTTP не наследовал защиту сетевых логов контура уведомлений.**
   Вокруг обмена клиента и источника теперь устанавливается тот же служебный контекст;
   он всегда сбрасывается после запроса. Пользовательские callbacks сохраняют
   обычный logging. Отдельный тест наблюдает контекст внутри подставного сетевого отказа.

Новые контрактные проверки используют подставные провайдеры, настоящий локальный
HTTP и настоящие SQLite-журналы. Проверены общий чат с двумя экземплярами,
status/suspend/status/resume, чужой actor, старое сообщение, неправильный тип
Telegram update, закрытость ntfy, потеря подтверждения источника/ответа hub,
рестарт до submit и потеря ответа после callback. Полные результаты и ограничения
проверенных сред находятся в [VALIDATION.md](VALIDATION.md).

## Осознанные ограничения

- **UNKNOWN требует решения приложения.** Тайм-аут не доказывает, что операция
  остановилась. Автоматического повторного callback и готового административного
  CLI для освобождения неизвестного исполнения нет. Методы чтения и разбора журнала
  описаны в [COMMAND_EXECUTION.md](COMMAND_EXECUTION.md); автоматизировать это до
  выяснения фактического состояния приложения нельзя.
- **ntfy даёт права теме, а не удостоверенному автору сообщения.** Только закрытый
  command topic с проверенными правами записи. Анонимная read-проба при запуске
  не является проверкой write ACL; разрешённые писатели разделяют одного actor.
- **Доставка ответа допускает дубликат.** Потеря provider ACK может показать два
  ответа с одним command_id; callback при этом не повторяется. Доставка на телефон
  и прочтение не выводятся из HTTP success. Короткая справка — одна попытка.
- **Один активный владелец.** Блокировки локальны; запуск второго bot reader с другой
  VM/директорией не поддерживается. HA и распределённый выбор лидера отложены.
- **Хранилище конечно.** Переполнение свежей защиты от повторов, pending commands
  или UNKNOWN закрывает приём. Это предпочтительнее удаления доказательств ради
  продолжения работы. Для высокочастотного управления текущая схема не предназначена.
- **Чтение ntfy потоковое, по одному сообщению.** Так не загружается весь кеш в RAM;
  при большом накопившемся архиве наверстывание может идти медленно, а команды
  старше исходного срока уже не исполнятся. Массовая пакетная обработка не нужна
  для текущего интерактивного сценария.
- **Сетевые и platform-проверки различаются.** CI 0.3.5.dev2 подтвердил Windows/Linux
  на Python 3.10/3.12, core/extras; все восемь jobs прошли. Реальные TLS,
  crash и callback-тесты из предыдущих этапов сохранены в общем наборе.
