# Разбор конфликтующих результатов команд

Version 1.0.0

Автор: Sergey Fundobny (silverbull@mail.ru) + GPT-6

Дата и время последнего изменения: 261014-001243

## Для чего нужна сверка

В 0.4.4.dev3 появился отдельный локальный инструмент
`python -m remote_watch.diagnostics.command_resolution`.
Он решает конкретный случай: приложение сохранило `COMPLETED`, gateway сохранил
`UNKNOWN` той же команды, а владелец проверил, что исполнение действительно окончено.
Обычные временные обрывы связи по-прежнему обрабатывает автоматический reconnect.

Инструмент не повторяет callback, не меняет текст/исход команды в журнале hub,
не удаляет клиентскую запись и не ставит клиенту ACK вручную. На hub отдельно
сохраняется принятый владельцем клиентский результат. При следующей передаче
клиент получает обычную квитанцию именно этого результата и сам записывает ACK.
Источник команд продолжает видеть первоначальный UNKNOWN; сообщение на телефоне
задним числом не исправляется. Решение фиксируется как `admin_resolved`.

Это административное решение, а не доказательство результата бизнес-операции.
Сам по себе завершённый процесс не доказывает успешность рассылки или другой работы.
Файл доказательства также не подписан: доверие основано на его проверенном происхождении
и правах владельца локальных файлов. Удалённого административного endpoint нет.

Не поддерживается автоматическое разрешение локального UNKNOWN/STARTED либо
произвольных расхождений. Для них требуется отдельный разбор исполнения.

## Порядок действий на RU и LV

Все пути ниже — примеры. Подставьте фактический путь клиентского SQLite из конфига
SpamBot. Не используйте копию из `runs` вместо рабочего журнала при окончательном
подтверждении состояния. Не удаляйте журналы, не меняйте owner и курсоры источников.

1. Запланируйте остановку SpamBot и command gateway. Если commands принадлежит
   `gateway_server`, остановите управляющее приложение, чтобы оно не подняло
   дочерний процесс вновь. Caddy и его CA менять не требуется. Убедитесь, что
   процесс приложения и его callback/порождённые им работы действительно закончены.
2. Сохраните резервные копии **остановленных** клиентского и hub SQLite, а также
   журналов источников. Обновите remote-watch на обеих машинах до 0.4.4.dev3.
   Новый runtime переводит command journal из схемы 1 в 2; старые версии его
   не открывают. Откат требует согласованных резервных копий, а не понижения
   `PRAGMA user_version` вручную. Wire-протокол и конфиги не изменены.
3. На машине приложения прочитайте список неподтверждённых записей. В выводе
   есть локальный `sequence`, состояние и флаги, но нет аргументов/текста ответа.

```powershell
$py = 'C:\Work\SpamBot\.venv\Scripts\python.exe'
$journal = 'C:\path-to-actual-client-journal\commands.sqlite'
& $py -m remote_watch.diagnostics.command_resolution list --journal $journal
& $py -m remote_watch.diagnostics.command_resolution export --journal $journal --sequence 8 --output .\command-evidence.local.json
```

`8` — номер из исследованной копии SpamBot от 13 октября; на рабочей машине
выберите номер по свежему выводу. Export допускает только COMPLETED без ACK
и без активного локального исполнения. Существующий output не перезаписывается.
Файл содержит исходный запрос и ответ, включая частные данные приложения:
храните его с ограниченным доступом, не помещайте в Git и не присылайте в чат.

4. Передайте файл на LV защищённым способом и выполните preview при остановленном
   command gateway. Команда только читает существующие данные; runtime recovery
   не запускается, новое поколение не создаётся.

```powershell
$py = 'C:\Work\RemoteWatch\.venv\Scripts\python.exe'
$hub = 'C:\Work\RemoteWatch\data\commands\hub.sqlite'
& $py -m remote_watch.diagnostics.command_resolution preview --journal $hub --evidence .\command-evidence.local.json
```

Сверяются **весь** исходный запрос, Identity/session/epoch/command ID, claim и два
результата. `fingerprint` привязан к этим данным, ревизии, настройкам и поколению
hub. Сверьте решение `execution_ended_accept_client_result`: оно принимает
клиентский COMPLETED для будущей квитанции и снимает неопределённость исполнения.

5. Только после проверки и подтверждения остановки примените решение:

```powershell
& $py -m remote_watch.diagnostics.command_resolution apply --journal $hub --evidence .\command-evidence.local.json --expect '<fingerprint из preview>' --confirm-owners-stopped
```

`--confirm-owners-stopped` — явное утверждение оператора. SQLite-блокировка
защищает транзакцию, но не может доказать отсутствие callback на другой VM.
Применение дополнительно меняет служебное поколение hub и ограждает старые
handle. Исходная привязка команды, owner и позиции источников не меняются.

Решение, снятие `execution_active`, аудит и смена служебного поколения атомарны.
При сбое до commit изменения откатываются; при неизвестном результате самой CLI
повторите **те же** apply/evidence/fingerprint: `already_applied` означает,
что решение уже сохранено. Изменённый preview отклоняется как `preview_changed`.
По одному лишь времени ожидания повторно подтверждать исполнение нельзя.

6. Запустите gateway, затем SpamBot с прежними журналами. Клиент передаст исходный
   COMPLETED, получит точную квитанцию и снимет pending. Проверьте `ready=true`,
   `has_pending_results=false`, ответ на новую `/status`. Затем повторите обычный
   перезапуск gateway, **оставив SpamBot работать**, и проверьте рост `reconnects`.

Принятый результат хранится рядом с исходным UNKNOWN до обычной очистки этой
команды. Если источник уже подтвердил UNKNOWN, после нового запуска hub действует
его обычный retention (по умолчанию 24 часа). Поэтому завершайте обмен квитанцией
с клиентом сразу в том же окне обслуживания; это не бессрочное архивное хранилище.
Резервные копии и evidence нужны для последующего разбора. Объём решения учитывается
в лимитах БД; при заполнении команда возвращает `store_capacity`.

## Чтобы следующий инцидент был понятен

`CommandHealth.operator_action_required` сообщает о `unknown_execution`,
`unresolved_results` и конфликте результата `outcome_conflict`.
`recovery_hint="review_command_journal"` указывает на эту инструкцию.
Оба поля доступны через `watcher.command_stats.health` и сохраняются после close.
Обычный `unavailable` их не включает. Это наблюдение состояния, без нового
сетевого запроса и без автоматического административного решения.

Для SpamBot рекомендуются следующие изменения мониторинга:

- В `runtime/monitoring.py`, методе `command_stats()`, добавить в словарь
  `details` два поля: `"operator_action_required": health.operator_action_required`
  и `"recovery_hint": health.recovery_hint`. Сейчас метод перечисляет разрешённые
  поля вручную, поэтому новые признаки библиотеки сами в лог не попадут.
- При первом переходе `operator_action_required` в true писать отдельное ERROR:
  `Command recovery requires journal review; automatic callback replay is disabled.`
  Добавлять только безопасные `reconnect_reason`, `recovery_hint` и названия этапов.
- Однократно направлять владельцу это уведомление через notifications, если канал
  работает; не полагаться на commands для сообщения об отказе самого commands.
  Ограничить повторные сообщения состоянием/интервалом, чтобы не засыпать чат.
- Сохранять периодическую строку `Monitoring status` и после закрытия dispatcher;
  `mailings=running` не означает `commands=ready`.
- При исчерпании ожидания квитанции `kill_bot` явно записывать
  `Shutdown reply remains unacknowledged; command journal retained for recovery.`
  Не удалять БД и не считать `stats.completed` доказательством получения квитанции.

В изученном `runtime/command_delivery.py` SpamBot уже проверяет совпадение
CommandReceipt, а `_drain_command_reply` в `runtime/monitoring.py` ждёт ACK,
отсутствия выполняемого callback и pending. Этот порядок следует сохранить:
callback лишь запрашивает остановку и возвращает ответ; внешний владелец останавливает
watcher после ограниченного ожидания. Увеличение ожидания не устраняет длительную
недоступность сети и не является исправлением исторического UNKNOWN.
Доказательств конкретной причины старого таймаута `kill_bot` пока нет.

Код SpamBot и рабочие журналы этой доработкой не изменяются. Полевая приёмка
сверки и повторного reconnect выполняется отдельно после согласованной остановки.
