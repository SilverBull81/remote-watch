# Короткая диагностика длинных уведомлений ntfy

Version 1.0.0

Автор: Sergey Fundobny (silverbull@mail.ru) + GPT-6

Дата и время последнего изменения: 260929-185913

## Назначение

В 0.2.0.dev5 добавлен сценарий для выяснения причин long text на реальных серверах.
Он отправляет **до десяти синтетических сообщений**, каждое ровно один раз, без
скрытого retry. Между попытками по умолчанию десять секунд. Сначала ASCII, затем
кириллица с emoji; размеры подготовленного текста вместе со служебной шапкой —
512, 3500, 4095, 4096 и 5000 байт. Последний размер проверяет усечение адаптером.
Вместе с таймаутами сценарий обычно занимает несколько минут, а не сутки.

Это диагностическая отправка напрямую в ntfy через тот же NtfyChannel, которым
пользуется runtime. Она изолирует поведение HTTP/размера; logging/очереди/retry
по-прежнему проверяет [field_smoke](FIELD_SMOKE.md). При 401/403/429 серия
останавливается досрочно: дальнейшая проверка длины не решает отказ прав или квоты.

## Запуск одной командой

Установите одну ревизию **0.2.0.dev5 или новее** с extra ntfy на нужной VM.
Используйте прежний credentials.local.json с секцией ntfy; токен и topic не печатаются.
Проверяйте сначала одну машину, затем другую, чтобы проще сопоставлять номера
сообщений на телефоне и не расходовать общую квоту одновременно.

```powershell
python -m remote_watch.ntfy_diagnostic --output runs/ntfy-size-ru-01.jsonl
```

Каждый повтор требует **нового** имени отчёта. Существующий файл не перезаписывается.
Для другой VM замените суффикс, например ru-02 или lv-01. Можно задать
`--credentials C:\путь\credentials.local.json`; без этого используется текущий каталог.
`--interval 10` задаёт паузу, допустимо от 5 до 60 секунд. Без --output создаётся
уникальный JSONL-файл в runs. Полный длинный текст в отдельный .log не дублируется.

Сохраните JSONL и отметьте номера seq, полученные на телефоне. Сообщения разных
запусков различаются по run. Даже неизвестный исход не повторяется автоматически.
Сценарий явно запускается пользователем; обычный pytest его в интернет не отправляет.

## Что записывается

Начальная запись содержит версию пакета, Python/ОС, run_id, число запланированных
образцов и интервал. Каждая законченная попытка содержит только:

| Поле | Значение |
| --- | --- |
| sample / alphabet | Номер образца и ascii/unicode |
| rendered_bytes | Размер текста с шапкой перед усечением |
| status / reason | Классификация DeliveryResult и безопасная причина |
| http_status | Полученный HTTP-код; null, если он неизвестен |
| provider_code | Допустимый числовой code ntfy при отказе; иначе null |
| message_bytes | Размер текста после усечения в UTF-8 |
| request_bytes | Размер подготовленного JSON, переданного HTTP-клиенту |

request_bytes не доказывает передачу всех байтов при сетевом обрыве. При ошибке
во время чтения ответа известный HTTP-код сохраняется, но сам исход может остаться
UNKNOWN. error/description/link, URL, токены, topic и тексты сообщений в отчёт
не копируются. Числовой provider_code ограничен диапазоном 0–999999, HTTP — 100–599;
строки, bool и чрезмерные числа из ответа не принимаются.

В summary есть attempted, accepted, completed и provider_acceptance_complete.
completed означает выполнение всей серии; незавершённая/прерванная серия не даёт
полного успеха. При аварийном уничтожении процесса summary может отсутствовать.
Приём провайдером не подтверждает показ на Android; phone_display_verified всегда false.

Коды завершения: 0 — все десять приняты, 1 — отказ/неполная серия, 2 — ошибка
настройки или выполнения/очистки, 130 — Ctrl+C. Код 2 не позволяет считать запуск
штатным, даже если часть или все сообщения приняты до ошибки очистки.

## Обычный field smoke и relay

Те же четыре числовых поля с dev5 появляются в attempt-записях field_smoke.
Старые JSONL остаются читаемыми, но восстановить отсутствующие HTTP-коды из них нельзя.

Новый gateway переносит диагностику провайдера в relay **схемы 2**. Для этого клиенту
задают RelayConfig(schema_version=2); см. [RELAY.md](RELAY.md). Схема 1 остаётся
по умолчанию для совместимости и этих полей в ответе не содержит. Диагностическая
команда выше не требует gateway и всегда проверяет прямой ntfy.

## Граница готовности

Offline проверены точные размеры образцов, отсутствие повторов, паузы, ошибки,
отмена, отказ перезаписывать отчёт, очистка временного токена и перенос
диагностики через настоящий локальный HTTP. Точная причина реальных http_temporary
из прежних recheck пока неизвестна. Подготовка этой команды не объявляется
исправлением long text; нужен её короткий запуск на проблемных VM.
