# ADR 0002 — relay как настройка назначения

Version 1.0.1

Автор: Sergey Fundobny (silverbull@mail.ru) + GPT-6

Дата и время последнего изменения: 260930-172038

Статус: реализовано в 0.2; основной RU → LV → Telegram smoke подтверждён 30.09.2026.

## Контекст

Доступность provider endpoint различается между серверами. Пользователь хочет
необязательный шлюз как дополнительную настройку remote channels. При этом
будущий общий чат с командами требует собственного владельца inbound state.

## Решение

Отделить логическое destination от способа доставки. Каждое назначение задаёт
direct либо relay. Core отправляет через общий минимальный контракт транспорта;
logger, Notification и router от выбора не меняются.

Relay хранит provider credentials и alias mapping, приложение — свою service
credential. Outbound relay и command hub включаются независимо. Смешанный режим
поддерживается в одном приложении. 0.1 только direct, без фиктивно работающего relay.

Первая relay-версия выполняет одну provider attempt на запрос, а повторяет runtime
приложения. Только provider acknowledgement даёт provider_accepted. Async acceptance,
receipts и durable queue не добавляются без отдельного контракта.

## Рассмотренные альтернативы

- Обязательный gateway для всех: лишняя инфраструктура для доступных direct-каналов.
- Новый logger/API для relay: заставляет менять вызовы при смене маршрута.
- Произвольный HTTP proxy: не задаёт identity/ACL и результат доставки проекта.
- Две независимые retry policy: умножают попытки и задержки без ясного бюджета.

## Последствия

Можно перенести выбранное назначение на gateway без изменения приложения.
Появляются дополнительный сервис, service auth и новый отказ сети. Потеря ответа
может дать duplicate; delivery ID не обещает exactly-once. Подробности:
[GATEWAY.md](../GATEWAY.md).
