# ADR 0001 — стандартное logging и независимая доставка

Version 1.0.0

Автор: Sergey Fundobny (silverbull@mail.ru) + GPT-6

Дата и время последнего изменения: 260928-100331

Статус: принято для проектирования; реализация ожидается.

## Контекст

Приложения уже используют обычный Logger вместе с прежним TelegramBot.
Пользователь допускает изменения при переходе и не требует сохранения API бота.
Сеть не должна задерживать приложение или локальные логи. Несколько назначений
имеют независимые отказы, а неограниченная фоновая работа недопустима.

## Решение

Сохранить стандартный Logger и подключаемый NotificationHandler. Удобный helper
создаёт явную конфигурацию, runtime владеет только своими handlers/ресурсами.
Не создавать обязательный Logger subclass, wrapper или compatibility shim.

Локальное logging отделено от remote ingress. Один фоновый loop обслуживает
ограниченные очереди назначений через async adapters. Retry, active send и отложенная
работа входят в outstanding budget. Переполнение отбрасывает новое без ожидания.

В 0.1 доставка в памяти — best effort с конечными повторами. Provider acceptance
не равен mobile display. Unknown outcome и duplicates документируются.
Публичные каналы структурные, optional dependencies изолированы с первого релиза.

## Рассмотренные альтернативы

- Logger subclass: не нужен для handler integration и осложняет совместимость.
- Обязательная facade: создаёт второй API без необходимой первой версии функции.
- Общий listener для файлов и сети: связывает независимые задержки и ошибки.
- Unbounded queue: переносит provider outage в рост памяти процесса.
- Durable outbox сразу: требует хранения/recovery до проверки основной потребности.

## Последствия

Приложения переходят на настройку стандартного logger. Возможны потери даже важных
сообщений при перегрузке; counters обязательны. Shutdown ограничен только при
соблюдении async/cancellation-контракта адаптером. Локальные handlers могут иметь
собственную синхронную стоимость. Детали в [архитектуре](../../ARCHITECTURE.md).
