# ADR 0012: общий deployment и управление процессами gateway

Version 1.0.0

Автор: Sergey Fundobny (silverbull@mail.ru) + GPT-6

Дата и время последнего изменения: 261002-185330

## Статус и контекст

Принято для реализации 0.4 по согласованному владельцем
[плану эксплуатации](../GATEWAY_OPERATIONS_PLAN.md). В 0.4.1.dev1 реализованы
модели настроек, их локальная проверка и правила ограниченного перезапуска.
Управление процессами, status, deploy, doctor и служба ОС ещё не реализованы.

Текущий deployment владельца: Windows VM в Латвии, Caddy с внутренним CA,
HTTPS на 8443, HTTP backends на 127.0.0.1:8765 и 127.0.0.1:8766.
Один gateway обслуживает несколько приложений; отдельный процесс на приложение
не нужен. Прямой доступ к физическому серверу не требуется.

## Конфигурация и границы

Новый пакет `remote_watch.gateway_server` находится в том же distribution.
Настройки описаны в [GATEWAY_DEPLOYMENT.md](../GATEWAY_DEPLOYMENT.md).
Общий JSON содержит endpoint, ссылки на существующие конфиги компонентов,
внутренние listeners, пути управления/логов, режим Caddy и конечные сроки.
Отсутствующий раздел компонента отключает его; хотя бы один нужен.
Токены остаются в отдельных конфигурациях компонентов. Существующие CLI сохраняются.

Все пути общего JSON разрешаются относительно его файла. Пути внутри связанных
конфигов по-прежнему разрешаются относительно соответствующего файла. Manager
передаёт дочернему процессу абсолютный путь к конфигу, а не переписывает содержимое.
Перенос файла с `state_dir: data/commands` меняет журнал: такой перенос не является
безопасной миграцией. Environment и `~` в общих путях не раскрываются.

Проверка общего конфига не открывает SQLite, не захватывает owner lock, не создаёт
каталогов и не читает токены из окружения. Она не запускает Caddy, не проверяет
его синтаксис/маршруты, сертификаты, права файлов, реальные порты или ACL провайдера.
Ошибка вложенного конфига указывает компонент; его прежний `--check-config`
даёт более точные безопасные поля. Неизвестные ключи, пути и значения не печатаются.

## Владение процессами

Manager запускает отдельные процессы notifications и commands. Их event loops,
таймеры, зависания и исключения изолированы. Общий процесс с несколькими asyncio
tasks отклонён: заблокированный loop остановил бы и наблюдение, и второй компонент.
Отдельный deployment на каждое приложение также не нужен: маршрутизация уже
поддерживает несколько principals/Identity.

Для Caddy выбирается один из двух режимов:

- `external`: оператор или отдельная служба управляет Caddy. Manager может
  наблюдать доступность ingress, но не посылает reload/stop и не завершает процесс.
- `managed`: manager запускает заданный локальный binary с явным Caddyfile и
  постоянным `data_dir`. Он управляет только своим дочерним процессом. Никаких
  автоматических скачиваний, нового CA при обновлении или захвата чужого порта.

Перед любым запуском manager удерживает локальный OS lock deployment. Дочерние
компоненты дополнительно сохраняют собственные locks журналов/источников.
PID в файле не доказывает владение; нельзя убивать найденный процесс по PID или
отбирать порт. Локальный control endpoint должен быть привязан к текущему запуску,
с отдельным случайным секретом, ограниченным вводом и правами каталога. Он не
публикуется через Caddy. Status выводит фиксированные имена компонентов и причины,
без application IDs, args, credentials и сырых stdout/traceback.

Для Windows выбран механизм Job Object с завершением собственных процессов
при закрытии последнего дескриптора; дочерние процессы не получают право breakaway.
Его нужно установить до запуска рабочих ресурсов и проверить реальным crash-тестом
manager. PID-файл не заменяет этот механизм.
[Windows Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects).

Для Linux выбран bootstrap с `PR_SET_PDEATHSIG`, проверкой родительского PID после
установки и до открытия ресурсов. Это учитывает гонку со смертью родителя;
привилегированные/setuid binaries не допускаются, поскольку условия наследования
сигнала отличаются. Для Caddy bootstrap должен сохраняться до обычного exec.
Применимость и отсутствие осиротевших readers проверяются в 0.4.2 на реальных
процессах; вне Windows/Linux старт пока не обещается.
[Linux PR_SET_PDEATHSIG](https://man7.org/linux/man-pages/man2/PR_SET_PDEATHSIG.2const.html).

## Готовность и контроль

Контракт будущего status различает состояние manager и каждого компонента:
`starting`, `ready`, `degraded`, `failed`, `stopping`, `stopped`, а также отдельно
`ingress: unverified/ready/degraded`. Процесс и открытый listener — лишь часть
готовности. Командный компонент использует готовность hub, источников, журнала
и доверенного времени; исходящий — listener и обслуживающий loop. Доступность
провайдера и получение на телефоне не следуют из `ready`.

Heartbeat создаётся **в обслуживающем loop ребёнка**, а не соседним потоком.
Manager измеряет возраст принятого heartbeat своим monotonic clock; UTC VM и
монотонные отсчёты разных процессов не сравниваются. Сообщения привязаны к запуску
ребёнка, имеют предел размера и не могут бесконечно накапливаться в pipe.
Status также должен отвечать при зависшем компоненте.

Внешний Caddy без проверки ingress остаётся `unverified`. Готовые backends не
превращают весь deployment в подтверждённо доступный HTTPS endpoint. Полная
готовность клиента и регистрация его командной сессии — ещё отдельный уровень.

## Перезапуск, ошибки и остановка

`RestartBudget` уже реализует учёт одного компонента в течение жизни manager.
Вход — монотонное время наблюдения **завершившегося** дочернего процесса,
фиксированная причина и подставляемая случайная величина 0..1. Он резервирует
попытку, а не запускает её. Повторный запрос status не расходует лимит.
Неудачный spawn расходует зарезервированную попытку. При hang сначала необходимо
завершить и дождаться прежнего процесса: параллельный reader не допускается.

По умолчанию допустимы три повторных запуска за 300 секунд. Backoff начинается
с двух секунд, удваивается по числу резервирований в текущем окне, получает
поправку ±20% и ограничивается 30 секундами. Резервирование ровно на границе
окна удаляет старую попытку. После исчерпания лимита компонент остаётся `failed`
до вмешательства оператора, даже если окно уже истекло. `max_restarts: 0`
полностью запрещает автоматический повтор.

| Причина | Действие manager |
| --- | --- |
| Неожиданный выход / завершённый зависший процесс | Ограниченный перезапуск |
| Ошибка конфига, авторизации, ownership или постоянного журнала | Отказ без автоматического перезапуска |
| Недоступен провайдер или TimeAPI, loop отвечает | Degraded и восстановление штатными механизмами компонента |
| Явная остановка | Без перезапуска |

Если дочерний процесс не смог сообщить тип ошибки, manager не угадывает её
по произвольному тексту; неизвестный неожиданный выход расходует конечный crash-бюджет.
Кратковременная занятость SQLite не равна повреждению журнала. Предупреждения
источника/UTC не разрешают очистку состояния или исполнение просроченной команды.

Начальный запуск имеет общий срок 60 секунд и считается успешным только после
готовности всех включённых собственных компонентов. До этого момента отказ
вызывает rollback всего запущенного manager. После успешного запуска отказ одного
компонента оставляет здоровые работающими, но общий status показывает degraded.
Доступность external Caddy отражается отдельно и не даёт права управлять им.

Остановка имеет общий срок мягкого завершения 30 секунд плюс до пяти секунд
на подтверждение принудительного завершения собственных процессов. Сначала
прекращается приём новой работы, затем закрываются loops/listeners и журналы.
Timeout callback не означает, что приложение закончило действие; UNKNOWN сохраняется.
Не подтверждённое завершение ребёнка запрещает запуск замены. Locks освобождаются
после остановки; чужие процессы, SQLite, CA и конфиги не удаляются.

Счётчик текущего `RestartBudget` хранится в памяти и переживает рестарты ребёнка,
но не manager. В 0.4.5 служба ОС обязана иметь собственный конечный предел попыток,
чтобы не превращать перезапуск manager в обход лимита. Без службы ОС возврат
после reboot/crash manager не обещается. Журналирование и control transport
реализуются в 0.4.2 с проверкой ограничений, а не выводом сырых логов процессов.

## Постоянное состояние и миграция

Caddy должен продолжать использовать прежнее хранилище, включая CA. Одного поля
`data_dir` недостаточно для доказательства этого: Caddyfile может задавать собственный
storage. В managed-режиме 0.4.2 обязан проверить эффективную конфигурацию Caddy и
соответствие выбранного filesystem storage, не печатая адаптированный JSON целиком.
Неизвестный storage требует явного отказа, а не молчаливого создания нового CA.
[Настройки Caddy storage](https://caddyserver.com/docs/json/storage/).

Владелец существующей установки сначала сохраняет реальные абсолютные пути
журналов/CA, затем останавливает прежние readers. Новый manager ссылается на
**те же** component configs, source IDs и каталоги. Нельзя копировать активные
SQLite по отдельным файлам, восстанавливать старый journal поверх нового или
сбрасывать cursor для проверки. Снимок/backup требует отдельной согласованной процедуры.

Каждый старт command hub создаёт новую generation; прежние UNKNOWN сохраняются.
Автоперезапуск hub не вызывает callback повторно. При этом нынешний CommandClient
не регистрирует старую сессию заново автоматически после смены эпохи hub или
истечения сессии. Поэтому восстановление server readiness не означает, что
приложение снова принимает команды.

До отдельного контракта reconnect оператор согласованно завершает прежний командный
клиент приложения и создаёт новую сессию с прежним постоянным клиентским журналом.
Незавершённые callbacks и UNKNOWN разбираются по
[COMMAND_EXECUTION.md](../COMMAND_EXECUTION.md), без автоматического повтора.
Если использован RemoteWatcher, его lifecycle также учитывается при создании
нового клиента; остановленный объект не объявляется автоматически переиспользуемым.
Это нужно учитывать при первой миграции реального приложения. Прозрачное
восстановление клиентской регистрации остаётся отдельной задачей проектирования.

## Проверка последующих шагов

0.4.1 проверяет строгую схему, безопасные ошибки, отключённые компоненты,
относительные/Unicode-пути, отсутствие побочных действий и конечный restart budget.
0.4.2 должен отдельно доказать Windows/Linux ownership при crash manager,
crash/hang ребёнка, отсутствие второго владельца, rollback запуска, bounded stop,
независимость компонентов и сохранение journal/CA. Прохождение тестов конфигурации
не закрывает ни один из этих процессных сценариев.
