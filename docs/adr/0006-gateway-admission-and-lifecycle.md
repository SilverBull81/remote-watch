# ADR 0006: приём запросов и время работы outbound gateway

Version 1.0.0

Автор: Sergey Fundobny (silverbull@mail.ru) + GPT-6

Дата и время последнего изменения: 260929-122613

## Статус

Реализовано в 0.2.0.dev3 и проверено offline на Windows/Python 3.12. Размещение
gateway в целевой инфраструктуре остаётся отдельной полевой проверкой.

## Решение

Сохранить wire v1 из [ADR 0005](0005-relay-wire-and-packaging.md). Сервер поставляется
через extra gateway в том же пакете и запускается отдельным процессом. Настройки —
типизированные Python-объекты из доверенной локальной функции; HTTP-запрос не выбирает код.

GatewayPrincipal привязывает credential к точной Identity и конечному списку aliases.
Токены проверяются при старте, в серверном индексе хранятся SHA-256-хеши; сравнение
выполняется compare_digest. Разные principals не могут делить один токен. Права статичны
на время работы; для изменения и отзыва нужен перезапуск. Durable audit пока отсутствует.

Общая и per-principal capacity резервируются до чтения тела. Нет ожидающих семафоров
или очереди отправки. Каждый alias владеет одним прямым каналом и выполняет одну
попытку; занятому alias возвращается 429. Минимальные интервалы для principal и alias
ограничивают частоту, Retry-After указывает нижнюю границу повтора. Повторы остаются
в runtime приложения. Server destination требует DIRECT и max_attempts=1.

Тело не распаковывается, читается частями с пределом 64 KiB и отдельным сроком.
Проверяются строгое JSON, identity/ACL и expiry. Время чтения вычитается из присланных
TTL/timeout, собственная политика сервера может только сократить срок отправки.
Допуск будущего created_at по умолчанию нулевой, expiry не продлевается допуском часов.

Shutdown закрывает listener и приём, ограниченно дренирует запросы, отменяет остаток
и параллельно закрывает принадлежащие каналы. Отмена ожидающего close не отменяет
общую задачу очистки. Adapter contract требует неблокирующей работы и принятия отмены.
Повторный start закрытого объекта запрещён; новая конфигурация создаёт новый Gateway.

Обрыв клиента отменяет handler, но уже начатая provider attempt может иметь неизвестный
исход. Подтверждение не записывается в durable storage; повтор после потери ответа
может дублировать сообщение. Идентификатор доставки не является ключом дедупликации.

## Граница ограничения нагрузки

Capacity ограничивает принятые операции библиотеки, но не все TCP/TLS-соединения,
предварительные буферы и задачи HTTP-парсера aiohttp. Для публичного входа нужны
конечные ограничения соединений/заголовков/трафика на reverse proxy или сетевом входе.
Эта граница указана явно: сервер не объявляется самодостаточной защитой публичного
порта от неограниченной входящей нагрузки. Plain HTTP разрешён только на loopback;
прямое прослушивание иных адресов требует SSLContext.

## Последствия

Путь от существующего RelayChannel до provider adapter реализован без изменения
logging API и без второго retry loop. Один медленный alias не задерживает другие.
Цена простого ограничения — явные временные отказы при одновременных отправках
в один alias. Масштабирование несколькими gateway-процессами разделит их квоты;
распределённого ограничителя и автоматического failover здесь нет.

Контур команд, динамический административный HTTP API, persistent receipts и
дедупликация не включаются вместе с relay. Настройки и проверки:
[GATEWAY_SERVER.md](../GATEWAY_SERVER.md).
