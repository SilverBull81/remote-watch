# ADR 0014: восстановление сессии живого командного клиента

Version 1.0.1

Автор: Sergey Fundobny (silverbull@mail.ru) + GPT-6

Дата и время последнего изменения: 261013-232656

Статус: принято и реализовано в 0.4.2.dev4.

## Контекст

Supervisor может перезапустить hub, но до dev4 приложение теряло командный путь
до собственного перезапуска. Простой повтор register под старым session_id
не подходит после истечения lease. Переоткрытие клиентской БД с новым поколением
может превратить ещё работающий callback в чужую старую запись.

## Решение

Разделить generation владельца журнала и session_id маршрутизации. В первой сессии
они по-прежнему совпадают для существующих конструкторов; последующие регистрации
одного живого клиента получают новые session_id. SQLite хранит прежнее поколение
строк и metadata. Новый bind_session допускается только без неподтверждённых или
выполняющихся записей. Смена привязки нужна только в памяти живого владельца:
после его аварии open нового поколения всё равно выполняет прежнее восстановление.
Никакой миграции схемы SQLite, wire или сброса stream cursor не требуется.

Одна задача heartbeat становится координатором восстановления. Она не меняет
сессию при незавершённом acquire или активном ticket. Dispatcher переживает
stale_session и удалённый closed/503, но не повторяет callback. Новый register
идемпотентно использует один кандидат до ответа либо доказанного истечения.
Конфликт может подождать только до консервативной верхней границы последнего
server lease: локальный lease короче из-за вычета полного RTT.

Перед новой сессией старые результаты сверяются. Для старого hub_epoch операция
result разрешает исключительно чтение квитанции уже сохранённого точного результата:
действующий principal должен иметь ту же Identity, а ref/claim/body должны совпасть.
Неизвестная запись, другой результат или неподходящие права отвергаются.
Этот путь не принимает новые итоги, не освобождает execution_active и не выдаёт grant.
Обычные claim/release/heartbeat/poll сохраняют прежнюю проверку epoch/session.

UNKNOWN после аварии не переписывается поздним успешным ответом. Если локальный
результат расходится с ним, reconnect блокируется и оставляет доказательства в БД.
Автоматического повтора действий и административного разрешения UNKNOWN нет.
Это сознательный предел доступности ради прежних гарантий исполнения.

## Последствия и проверка

Уточнение 0.4.4.dev2: после перезапуска самого приложения незаквитированный
COMPLETED из прежней session_id может быть отправлен тем же механизмом, если
Identity совпадает и локальная работа завершена. Идентификаторы и результат
не переадресуются новой сессии. Старые UNKNOWN/живые executions не разрешаются;
противоречие результату hub остаётся `outcome_conflict`. Health учитывает
неподтверждённые результаты всех сохранённых сессий, а не только текущей.

Обычный рестарт в простое и длительный разрыв восстанавливаются без перезапуска
приложения. Уже начатое действие может потребовать явной сверки. Проверки покрывают
перезапуск/expiry, реальный TLS, dispatcher, два клиента, потерю ACK/register/grant,
живой callback, сбой хранения, TLS/права/конфликт, вычет RTT и остановку в backoff.
Наблюдаемость и обновление описаны в [COMMAND_RECONNECT.md](../COMMAND_RECONNECT.md).
Новые возможности требуют полевой проверки; успешный прежний prod-пилот сам по себе
не является её подтверждением.
