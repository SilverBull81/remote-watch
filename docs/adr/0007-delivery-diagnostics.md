# ADR 0007: безопасная диагностика и пределы relay

Version 1.0.0

Автор: Sergey Fundobny (silverbull@mail.ru) + GPT-6

Дата и время последнего изменения: 260929-185913

## Причина

Повторные короткие проверки ntfy дали http_temporary для long text, но прежний
DeliveryResult отбрасывал HTTP-статус и числовой код API. Это не позволяло отличить
408/500/502/503 и сопоставить отказ с фактическим размером подготовленного запроса.
Отдельно обнаружено различие локальных SnapshotLimits и пределов принимающего relay.

## Решение в 0.2.0.dev5

DeliveryResult расширен четырьмя nullable-полями: http_status, provider_code,
message_bytes, request_bytes. Все значения — ограниченные целые числа без bool;
никакие произвольные тексты ошибок, URL, заголовки или настройки не сохраняются.
NtfyChannel измеряет собственный подготовленный payload и выбирает только
допустимый числовой code из ответа. HTTP-слой сохраняет известный статус даже
при обрыве чтения тела; классификация UNKNOWN остаётся консервативной.

Обычный field report и отдельный конечный ntfy_diagnostic сохраняют эти поля.
Диагностические размеры описывают подготовленные байты, а не гарантированный
объём передачи при обрыве. Принятие провайдером не означает показ на телефоне.

Старый decoder relay требует точного состава полей. Поэтому добавлять новые поля
в ответ schema 1 нельзя. Вводится явно выбираемая schema 2; новый gateway понимает
обе и отвечает в запрошенной версии. RelayConfig по умолчанию использует schema 1.
Новый decoder требует совпадения версии с текущей попыткой; автоматического
fallback и повторного POST нет из-за риска дубликата. Путь /v1/notifications
сохраняется; версия JSON и версия пути здесь не переключаются совместно.

Схема Notification остаётся 1. Обе версии relay принимают только стандартные
SnapshotLimits. Клиент повторно проверяет фактическое событие до HTTP и возвращает
relay_payload_limits при несовместимости. Клиент не расширяет серверные лимиты
передачей собственных настроек. Для проверки и отправки применяется один JSON encoder.

## Проверки и последствия

Проверены v1 без дополнительных полей, v2 с диагностикой, несовпадение версий,
недопустимые диагностические значения, реальный HTTP путь ntfy → gateway → relay,
запись field journal и отказ больших локальных событий до POST.
Для HTTPS проверены временный доверенный CA, неизвестный CA, истечение срока,
неверное имя, HTTP на TLS-порту и загрузка cert/key через CLI.

Новые runtime-зависимости core и провайдеров не добавлены. cryptography добавлена
только в dev для создания временных сертификатов тестов. Корневой CA не устанавливается
в ОС; тестовый SSLContext продолжает проверять цепочку, имя и срок сертификата.
Реальная причина long text остаётся открытой до запуска диагностического сценария
на проблемных VM. Сама диагностика не считается исправлением провайдера.
