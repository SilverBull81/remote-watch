## Что требуется для полного закрытия 0.4

1. **0.4.5 — запуск gateway_server как службы ОС.** Нужны установка, удаление,
   состояние службы, фиксированная учётная запись/рабочая папка, доступ к конфигам,
   журналам и Python, ограничения восстановления. Приоритет — Windows на LV.
   В исходном плане также заявлен systemd для Linux: его нужно реализовать либо
   отдельно согласовать перенос, а не считать Windows-проверку проверкой Linux.
   Работающая отдельная служба Caddy не заменяет службу gateway_server.
2. **Довести наблюдение журналов (остаток R5).** Утилита сверки закрыла разбор
   одного известного конфликта, но doctor/status пока не показывают полную ёмкость
   command journal, количества pending/UNKNOWN/активных исполнений. Нужен безопасный
   ограниченный снимок от действующего владельца; для остановленной БД — чтение
   без recovery, миграции, изменения generation/cursors. Не добавлять автоматический
   повтор callback или снятие UNKNOWN ради улучшения статуса.
3. **Проверить эксплуатацию именно службы.** Закрытие RDP/выход пользователя,
   reboot VM, ограниченное восстановление после падения manager и дочернего
   компонента, отсутствие второго reader, сохранение CA/SQLite, доступность
   notification и command маршрутов после восстановления. Сбой процесса не должен
   вызывать бесконечный restart. Подтвердить сообщения владельцу об отказе/восстановлении
   и сохранение локальной диагностики, когда внешний канал недоступен.
4. **Завершающий контроль выпуска.** Применить новое health в SpamBot и проверить
   отказ → успешную доставку без перезапуска приложения. Выполнить один полевой
   проход doctor после установки службы; прежний server/client doctor уже принят.
   Для существенного сервисного изменения запустить
   согласованную Windows/Linux × Python 3.10/3.12 × core/extras CI-матрицу,
   затем зафиксировать точные результаты и окончательный статус 0.4.

Обычные deploy, запуск gateway и reconnect заново доказывать не требуется.
Целевые проверки после изменения службы нужны для нового способа запуска.
Первым следующим шагом предлагается согласовать и реализовать сервисный слой
0.4.5; затем добавить снимок журналов, выполнить эксплуатационные проверки и
подвести окончательные итоги. Установка службы и reboot рабочей VM остаются
отдельными согласованными действиями, а не побочным эффектом разработки.

## Вне обязательного объёма 0.4

Live команды ntfy на закрытом топике отложены владельцем; покупать аккаунт для
приёмки Telegram deployment не требуется. Matrix/email, durable notification outbox,
HA, массовые команды, автоматическое разрешение UNKNOWN и публичная публикация
остаются отдельными направлениями. Итог недельного prod-прогона SpamBot полезен
как дополнительное свидетельство, но не заменяет конкретные проверки новой службы.
