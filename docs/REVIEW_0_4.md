## Полевые результаты службы, 14 октября

Владелец подтвердил работу обоих каналов через службу, одного manager/reader,
Stop из трея, повторный start и reconnect приложений без повтора callback.
Операции с треем не создают второй сервер; повторный start работающей службы
отклоняется. Пункт о независимости службы от пользовательского сеанса отмечен
владельцем успешным; отдельных OS-журналов этой проверки не предоставлено.
Remove удаляет службу; сохранение файлов отмечено владельцем без побайтной сверки.

Повторный install выявил дефект dev1/dev2: запрет записи в прежний lock ошибочно
выдавался за живого manager. На LV прочитаны только ACL/режимы открытия: rb разрешён,
r+b запрещён, SCM 1060. В dev3 исправлены проверка владения и повторная выдача уже
достаточных прав. По согласованному уточнению иконка теперь скрывается/появляется
автоматически; контроллер остаётся в фоне. Реальная переустановка и новый UI требуют
повтора владельцем после обновления, это не результат автотестов.

Reboot, контролируемые crash/budgets на тестовом deployment и полевой переход
notification health из отказа в исправное состояние остаются открытыми.

## Что требуется для полного закрытия 0.4

1. **Повторить целевую приёмку dev3.** Обновить venv и старый контроллер, выполнить
   install после remove с прежними путями, затем start. Проверить исчезновение
   иконки после stopped и возврат после start, переключение headless/tray через
   sync-tray без второго manager. Инструкция: [GATEWAY_SERVICE.md](GATEWAY_SERVICE.md).
   Установка и файлы на LV автоматически этой разработкой не изменены.
2. **Согласованный reboot VM.** До входа пользователя запускается служба, после входа
   появляется иконка; Caddy сохраняет прежний CA. Проверить doctor и оба канала.
   Успешный прежний reboot Caddy не доказывает этот сценарий gateway_server.
3. **Контролируемый crash и конечные бюджеты.** Проверять manager и компоненты только
   на тестовом deployment; production процесс без отдельного решения не завершать.
   Подтвердить восстановление каналов, отсутствие бесконечного restart, сохранение
   UNKNOWN и отсутствие повторного callback. Проверить сообщения владельцу и локальную
   диагностику, когда внешний канал недоступен. Windows не подтверждает systemd/Linux.
4. **Полевой переход notification health из отказа в исправное состояние.** Новая
   логика уже подключена в SpamBot со слов владельца. Успешный server doctor не
   заменяет этот переход и не выполняет отправку. Для проверки не требуется портить
   рабочие журналы или останавливать production без отдельного решения.
5. **Завершающий контроль выпуска.** После целевых исправлений выполнить согласованную
   Windows/Linux × Python 3.10/3.12 × core/extras CI-матрицу и записать окончательный
   статус 0.4. Текущие локальные Windows-проверки не являются новым CI/Linux прогоном.

Полевой контроль сводок журналов R5 закрыт свежим server doctor: все 12 checks ok,
hub/source capacity=ok. Архивный UNKNOWN=1 при unresolved_unknown=0 не разрешает
автоматического освобождения или повтора callback. Офлайн-проверка остановленной
копии SQLite через mode=journal остаётся доступным инструментом эксплуатации.
Обычные deploy, оба канала, reconnect и базовую работу службы заново доказывать
не требуется. Сохранение данных после remove отмечено владельцем без побайтной сверки.
