## Полевые результаты службы, 14 октября

Владелец подтвердил работу обоих каналов через службу, одного manager/reader,
Stop из трея, повторный start и reconnect приложений без повтора callback.
Операции с треем не создают второй сервер; повторный start работающей службы
отклоняется. Пункт о независимости службы от пользовательского сеанса отмечен
владельцем успешным; отдельных OS-журналов этой проверки не предоставлено.
Remove удаляет службу; сохранение файлов отмечено владельцем без побайтной сверки.

Повторный install выявил дефект dev1/dev2: запрет записи в прежний lock ошибочно
выдавался за живого manager. На LV прочитаны только ACL/режимы открытия: rb разрешён,
r+b запрещён, SCM 1060. В dev3 исправлены проверка владения и повторная выдача уже
достаточных прав. По согласованному уточнению иконка теперь скрывается/появляется
автоматически; контроллер остаётся в фоне. После обновления владелец подтвердил
работу трея и установки/удаления/переустановки. Это полевая приёмка из переписки,
а не вывод из автотестов.

Reboot и контролируемые crash/budgets на тестовом deployment остаются открытыми.
Полевое восстановление notifications отложено владельцем за пределы 0.4.

## Что требуется для полного закрытия 0.4

1. **Согласованный reboot VM.** Владелец выполняет его самостоятельно.
   До входа запускается служба, после входа появляется иконка; Caddy сохраняет CA.
   Затем нужны doctor и оба канала. Результат пока не получен.
2. **Контролируемый crash и конечные бюджеты.** Только отдельный тестовый deployment,
   без остановки production. Пошаговая инструкция: [GATEWAY_SERVICE.md](GATEWAY_SERVICE.md).
   Проверяются восстановление, конечность повторов, служебные сообщения и диагностика.
   Для команд отдельно сохраняются UNKNOWN и запрет автоматического повтора callback.
3. **Завершающий контроль выпуска.** Согласованная Windows/Linux × Python 3.10/3.12 ×
   core/extras CI-матрица. Локальные Windows-проверки не заменяют CI/Linux.

Трей, установка/удаление/повторная установка службы приняты владельцем после dev3.
Он также подтвердил наличие notification_health в Monitoring status SpamBot.
Это свидетельство из переписки, не новый осмотр полевых файлов.
Полевой отказ → восстановление notifications по явному решению владельца вынесен
за пределы 0.4; воспроизводить ночной сбой production для закрытия этапа не требуется.

Полевой контроль сводок журналов R5 закрыт свежим server doctor: все 12 checks ok,
hub/source capacity=ok. Архивный UNKNOWN=1 при unresolved_unknown=0 не разрешает
автоматического освобождения или повтора callback. Офлайн-проверка остановленной
копии SQLite через mode=journal остаётся доступным инструментом эксплуатации.
Обычные deploy, оба канала, reconnect и базовую работу службы заново доказывать
не требуется. Сохранение данных после remove отмечено владельцем без побайтной сверки.
