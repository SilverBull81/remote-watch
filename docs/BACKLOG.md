## Эксплуатация и проверки

- Продолжить длительное наблюдение реального приложения и notification health:
  временный отказ → принятие провайдером → снятие текущего degraded при сохранённой истории.
  По решению владельца это не блокирует 0.4.
- Проверить private ntfy-команды на реально закрытом topic. Отложено без срока,
  не блокирует Telegram deployment; публичный topic не использовать как замену.
- Полевой Linux/systemd install/reboot/recovery; не подменять Windows-приёмкой.
- Отдельно подтвердить offline resolution на остановленных тестовых журналах:
  точный COMPLETED/UNKNOWN, получение квитанции и последующий reconnect.
  Общая приёмка reconnect не доказывает применение конкретной admin-сверки.
- Длительное продление TLS, региональные/смешанные сети и нагрузочные/ёмкостные
  сценарии; фиксировать отдельно от коротких synthetic тестов.
- Продумать внешний health observer для Caddy external, смерти manager/VM и
  недоступности ingress. Внутренние owner alerts не покрывают эти случаи.

## Возможности

- Matrix, затем обоснованные дополнительные каналы, включая email fallback.
- Опциональная durable notification outbox с явной политикой потерь/дубликатов,
  quotas, cleanup и migration; текущие очереди остаются in-memory.
- Дополнительное удобство callback registry и конфигурации без второго конкурирующего
  контракта. Динамическая перезагрузка настроек потребует отдельного проектирования.
- HA/масштабирование, несколько gateway owners и массовые команды — только после
  проектирования fencing/consensus/authorization, без неявного broadcast.

## Ограничения направления

Не планируются произвольные shell/Python eval, автоматический повтор неизвестного
callback, молчаливое разрешение UNKNOWN, отключение TLS и compatibility aliases
для прежних Relay API. Конкретный дополнительный мессенджер рассматривается по
потребности, не включается только из-за наличия SDK.
