## Текущее состояние

Реализованы библиотечные части шагов 1–5: модели, конфигурация, локальная регистрация команд и полный
путь от logging до тестовых каналов через ограниченные очереди фонового runtime.
Базовая версия 0.1.0 завершена; текущая приватная итерация — 0.2.0.dev6. Повторы, ограниченные сроки и sync/async lifecycle реализованы.
Добавлены Telegram/ntfy, relay-клиент с optional aiohttp и полевой smoke;
реализован исходящий gateway с auth/ACL и ограниченным приёмом.
Номера 0.1/0.2/0.3 обозначают предполагаемые релизы пакета;
Version 1.0.0 в шапках обозначает редакцию отдельного документа.

Работа выполняется небольшими проверяемыми изменениями. Сначала проверяется
полный путь на fake-канале, затем добавляется сеть. Приложения из соседних
репозиториев не меняются в рамках подготовки этой библиотеки.

Повторное ревью 29.09: [остаток работ по 0.1/0.2](REVIEW_0_1_0_2.md).
Два коротких повторных запуска с 0.2.0.dev2 снова дали 3/4 подтверждения ntfy;
на long text тогда был http_temporary после трёх попыток. Последующая диагностика
dev5 локализовала границу: 4095 байт приняты, ровно 4096 — HTTP 500/50001.
В dev6 текст ограничен 4095 байтами; локальная регрессия проверена, полевой повтор нужен.
Кроме полевых тестов остаются матрица Python/ОС и улучшение диагностики gateway-процесса.

В dev5 реализованы диагностика HTTP/ntfy и короткий сценарий размеров, фиксированные
пределы relay с ранним отказом, совместимые схемы 1/2 и локальные TLS-тесты.
Для сценария VM компании расширена инструкция Gateway/TLS. Числовая диагностика
доступна в field report; результаты двух российских запусков и команда проверки dev6
собраны в [NTFY_DIAGNOSTIC.md](NTFY_DIAGNOSTIC.md). Матрица Python/ОС и прочие
эксплуатационные улучшения остаются открытыми.

## Подготовка

- Подтвердить Python на целевых Windows/Linux-машинах; проверить проектную цель 3.10+.
- Выбрать async HTTP-клиент для Telegram/ntfy по lifecycle, отмене, timeouts,
  отсутствию скрытых retries, размеру зависимостей и поддерживаемым Python.
- Проверить ntfy с российских и остальных серверов и Android-телефона по
  [CHANNELS.md](CHANNELS.md). Размещение сервиса определить по результатам.
- Решено 28.09.2026: только личное/закрытое использование. Публичная лицензия
  и публикация не входят в 0.1; classifier Private :: Do Not Upload сохранён.

Результат: подтверждённая среда, выбранный HTTP transport и отчёт о полевой проверке.
Разработку fake-прототипа можно вести параллельно ожиданию доступа к серверам;
релиз нельзя объявлять проверенным на этих серверах без фактического теста.

## 0.1 — библиотека уведомлений

### Шаг 1. Каркас и контракты

Статус: реализован. Добавлены также CommandContext/CommandSpec/CommandRegistry
и commands в WatcherConfig по уточнённому требованию пользователя. Это регистрация,
а не перенос сетевого контура команд в первый этап.

Создать pyproject, layout src/remote_watch и тестовые каталоги только при начале
реализации. Определить Identity, Notification, Destination, DeliveryResult,
минимальный async channel protocol и типизированную конфигурацию.
Отдельно проверить сериализацию, ограничения размера и неизменяемость снимка.

Готово, когда core импортируется без provider dependencies, fake channel может
реализовать контракт структурно, а validation errors объясняют неверную настройку.

### Шаг 2. Полный путь без сети

Статус: реализован. Добавлены NotificationHandler, PolicyRouter и NotificationRuntime.
Проверены Logger/LoggerAdapter, консоль и файл, два независимых получателя,
пользовательский канал, защита identity, ограничения очередей и пробуждений.
В версии шага 2 отправка требовала `max_attempts=1`; шаг 3 снял это временное ограничение.
Инструкция и исполняемый пример: [RUNTIME.md](RUNTIME.md).

Реализовать NotificationHandler, router, bounded ingress и управляемый worker.
Один стандартный logger одновременно пишет локально и доставляет выбранное событие
в fake channel. Затем проверить два назначения и custom adapter.

Готово, когда обычный logger и LoggerAdapter работают без подмены глобального
Logger, существующие handlers сохраняют поведение, а identity нельзя подменить
через extra. Результаты маршрутизации определяются тестами для notify/levels/tags.

### Шаг 3. Надёжность и lifecycle

Статус: реализован. К ограничениям и sync lifecycle шага 2 добавлены повторы,
full jitter, retry-after, сохранение delivery ID и слота при ожидании, счётчики
по получателям, async lifecycle с обработкой отмены и ограниченная остановка atexit.
Проверены неизвестные исходы, исчерпание попыток, общий TTL, порядок очереди,
одновременные повторы нескольких получателей и остановка при нарушении async-контракта.
В шаге 4 добавлены проверки таймаутов и отмены настоящего HTTP-клиента на loopback-сервере.

Добавить budgets назначений, retry scheduler, full jitter, timeouts, TTL,
rate-limit handling, stats, sync/async lifecycle и диагностическую изоляцию.
Clock и random source подменяются в тестах; thread/loop ownership проверяется
отдельными настоящими concurrency-тестами с конечными deadlines.

Готово, когда retries не обходят bounds, slow destination не останавливает соседний,
очередь не порождает unbounded tasks/callbacks, stop учитывает неизвестный исход
активной отправки, а внутренняя диагностика не создаёт новые уведомления.

### Шаг 4. Telegram и ntfy

Статус: реализован. TelegramConfig/NtfyConfig создают ленивые назначения с общей
политикой таймаутов. Есть plain-text отправка, усечение, классификация ответов,
retry-after и закрытие клиентов. Проверки используют fake HTTP и loopback;
live-provider тесты включаются отдельно. Пользователь подтвердил оба smoke на Android.
Тема бесплатного аккаунта ntfy не зарезервирована; закрытый ACL не подтверждён. Добавлены smoke одной командой с локальным credentials-файлом.
Инструкции: [ADAPTERS.md](ADAPTERS.md), [SMOKE.md](SMOKE.md), [NTFY_SETUP.md](NTFY_SETUP.md).

Создать два optional adapters с одной попыткой на send, управляемыми клиентами,
plain-text рендерингом, усечением и безопасной классификацией ответов.
Provider credentials не входят в модели событий. Fake HTTP проверяет ошибки,
rate limit, invalid responses и отмену; каждый адаптер проходит общие contract tests.

Готово, когда обе реализации проходят offline contract tests и core устанавливается
без их extras. Реальная отправка включается только отдельным integration run.

### Шаг 5. Пользовательская настройка и упаковка

Статус: библиотечная реализация завершена. Добавлены RemoteWatcher, ConsoleConfig,
RotatingFileConfig и исполняемые sync/async/hierarchy-примеры в [WATCHER.md](WATCHER.md).
Проверены владение ресурсами, откат запуска, async-отмена и ротация. Сборка и установка
проверены на Windows/Python 3.12; Python 3.10/Linux остаются внешними проверками.

Исходный объём: добавить helper для обычного logger и принадлежащего ему runtime, локальные
console/rotating-file handlers по явной настройке, примеры sync/async программ
и подключения к существующей logger hierarchy. Примеры должны исполняться в тестах
на fake channel; сетевые примеры отдельно помечаются как opt-in.

Готово, когда wheel/sdist устанавливаются в чистое окружение, docs соответствуют
реальному API, нет зависимости от fin-data, tests без сети проходят на выбранных
Windows/Linux и минимальном Python. Лицензия/metadata определены до публикации.

### Приёмка 0.1

Библиотечная часть 0.1 завершена для личного использования на проверенной среде.

до готовности минимальных команд. Он выполняется отдельным изменением в репозитории
приложения, чтобы сразу внедрить весь новый интерфейс. Compatibility shim не требуется.
Потери до отправки, возможные дубликаты и ограничения Android остаются явными.

## 0.2 — необязательный outbound relay

В 0.2.0.dev4 добавлены запуск gateway из JSON без пользовательского Python-кода,
пример четырёх приложений с отдельными чатами и руководство Windows/TLS.
Один сервер проверен с четырьмя точными Identity/ACL и независимыми каналами;
публичный HTTPS и региональный маршрут по-прежнему требуют развёртывания и smoke.

Статус 0.2.0.dev3: реализованы клиент, серверный gateway, auth/ACL, ограничение
приёма/частоты, одна provider attempt и завершение процесса. Выполнен смешанный
direct/relay-сценарий с настоящими HTTP-адаптерами и подставными provider endpoints.
Пункты 1–5 ниже проверены offline. Реальное размещение, TLS/proxy, региональный relay
и Android остаются полевой приёмкой; весь этап ещё не объявляется проверенным в эксплуатации.
См. [RELAY.md](RELAY.md), [GATEWAY_SERVER.md](GATEWAY_SERVER.md) и
[ADR 0006](adr/0006-gateway-admission-and-lifecycle.md).

Дополнительно готов конечный длительный [полевой smoke](FIELD_SMOKE.md) для возможностей
0.1. Пользователь начал установку/короткие smoke на трёх серверах, включая российский;
первые результаты разобраны, ошибка размера ntfy JSON исправлена в 0.2.0.dev2;
повторные короткие тесты пользователь выполняет параллельно реализации gateway.

1. Выбрать packaging и серверный transport; определить wire schema и auth.
2. Реализовать client transport как замену direct transport в одном назначении.
3. Реализовать gateway с aliases/ACL, bounded concurrency, одной provider attempt.
4. Проверить смешанный режим: Telegram через relay, ntfy напрямую в том же runtime.
5. Проверить timeout после provider success, overload, expiry и неправильную identity.

Готово, когда смена direct/relay не меняет вызовы logger, приложение в relay-режиме
не требует provider token/SDK, а недоступность gateway подчиняется общей retry policy.
Command endpoints в relay-only deployment отсутствуют.
