30.09.2026 владелец подтвердил RU → HTTPS gateway на LV → Telegram → телефон
после обновления venv до dev9. На этой базе выпущена разработческая версия

Замечания №1–5 предыдущего ревью закрыты в описанном объёме. Длительный mixed,
автозапуск после перезагрузки VM и эксплуатационные проверки вынесены в явный
остаток, без утверждения об их выполнении. [Итог ревью](REVIEW_0_1_0_2.md).

В 0.3.0.dev1 реализован контракт шага 0.3.1; сеть и исполнение ещё не включены. По уточнению владельца первая рабочая версия
должна поддерживать и status/check_load, и изменяющие состояние resume_load /
suspend_load. Все имена и callbacks принадлежат приложению; встроенного списка
допустимых команд не будет. Первый проверяемый шаг остаётся read-only, но одной
проверки статуса недостаточно для приёмки всей 0.3.

Номера 0.1/0.2/0.3 — этапы пакета; Version в шапках — версии отдельных файлов.
Изменения выполняются небольшими проверяемыми частями. Приложения из соседних
репозиториев не меняются до отдельной задачи внедрения. Последние результаты
тестов, сборки и проверенные версии сред: [VALIDATION.md](VALIDATION.md).

## Подготовка

- Подтвердить Python на целевых Windows/Linux-машинах; проверить проектную цель 3.10+.
- Выбрать async HTTP-клиент для Telegram/ntfy по lifecycle, отмене, timeouts,
  отсутствию скрытых retries, размеру зависимостей и поддерживаемым Python.
- Проверить ntfy с российских и остальных серверов и Android-телефона по
  [CHANNELS.md](CHANNELS.md). Размещение сервиса определить по результатам.
- Решено 28.09.2026: только личное/закрытое использование. Публичная лицензия
  и публикация не входят в 0.1; classifier Private :: Do Not Upload сохранён.

Результат: подтверждённая среда, выбранный HTTP transport и отчёт о полевой проверке.
Разработку fake-прототипа можно вести параллельно ожиданию доступа к серверам;
релиз нельзя объявлять проверенным на этих серверах без фактического теста.

## 0.1 — библиотека уведомлений

### Шаг 1. Каркас и контракты

Статус: реализован. Добавлены также CommandContext/CommandSpec/CommandRegistry
и commands в WatcherConfig по уточнённому требованию пользователя. Это регистрация,
а не перенос сетевого контура команд в первый этап.

Создать pyproject, layout src/remote_watch и тестовые каталоги только при начале
реализации. Определить Identity, Notification, Destination, DeliveryResult,
минимальный async channel protocol и типизированную конфигурацию.
Отдельно проверить сериализацию, ограничения размера и неизменяемость снимка.

Готово, когда core импортируется без provider dependencies, fake channel может
реализовать контракт структурно, а validation errors объясняют неверную настройку.

### Шаг 2. Полный путь без сети

Статус: реализован. Добавлены NotificationHandler, PolicyRouter и NotificationRuntime.
Проверены Logger/LoggerAdapter, консоль и файл, два независимых получателя,
пользовательский канал, защита identity, ограничения очередей и пробуждений.
В версии шага 2 отправка требовала `max_attempts=1`; шаг 3 снял это временное ограничение.
Инструкция и исполняемый пример: [RUNTIME.md](RUNTIME.md).

Реализовать NotificationHandler, router, bounded ingress и управляемый worker.
Один стандартный logger одновременно пишет локально и доставляет выбранное событие
в fake channel. Затем проверить два назначения и custom adapter.

Готово, когда обычный logger и LoggerAdapter работают без подмены глобального
Logger, существующие handlers сохраняют поведение, а identity нельзя подменить
через extra. Результаты маршрутизации определяются тестами для notify/levels/tags.

### Шаг 3. Надёжность и lifecycle

Статус: реализован. К ограничениям и sync lifecycle шага 2 добавлены повторы,
full jitter, retry-after, сохранение delivery ID и слота при ожидании, счётчики
по получателям, async lifecycle с обработкой отмены и ограниченная остановка atexit.
Проверены неизвестные исходы, исчерпание попыток, общий TTL, порядок очереди,
одновременные повторы нескольких получателей и остановка при нарушении async-контракта.
В шаге 4 добавлены проверки таймаутов и отмены настоящего HTTP-клиента на loopback-сервере.

Добавить budgets назначений, retry scheduler, full jitter, timeouts, TTL,
rate-limit handling, stats, sync/async lifecycle и диагностическую изоляцию.
Clock и random source подменяются в тестах; thread/loop ownership проверяется
отдельными настоящими concurrency-тестами с конечными deadlines.

Готово, когда retries не обходят bounds, slow destination не останавливает соседний,
очередь не порождает unbounded tasks/callbacks, stop учитывает неизвестный исход
активной отправки, а внутренняя диагностика не создаёт новые уведомления.

### Шаг 4. Telegram и ntfy

Статус: реализован. TelegramConfig/NtfyConfig создают ленивые назначения с общей
политикой таймаутов. Есть plain-text отправка, усечение, классификация ответов,
retry-after и закрытие клиентов. Проверки используют fake HTTP и loopback;
live-provider тесты включаются отдельно. Пользователь подтвердил оба smoke на Android.
Тема бесплатного аккаунта ntfy не зарезервирована; закрытый ACL не подтверждён. Добавлены smoke одной командой с локальным credentials-файлом.
Инструкции: [ADAPTERS.md](ADAPTERS.md), [SMOKE.md](SMOKE.md), [NTFY_SETUP.md](NTFY_SETUP.md).

Создать два optional adapters с одной попыткой на send, управляемыми клиентами,
plain-text рендерингом, усечением и безопасной классификацией ответов.
Provider credentials не входят в модели событий. Fake HTTP проверяет ошибки,
rate limit, invalid responses и отмену; каждый адаптер проходит общие contract tests.

Готово, когда обе реализации проходят offline contract tests и core устанавливается
без их extras. Реальная отправка включается только отдельным integration run.

### Шаг 5. Пользовательская настройка и упаковка

Статус: библиотечная реализация завершена. Добавлены RemoteWatcher, ConsoleConfig,
RotatingFileConfig и исполняемые sync/async/hierarchy-примеры в [WATCHER.md](WATCHER.md).
Проверены владение ресурсами, откат запуска, async-отмена и ротация. Сборка и установка
проверены на Windows/Linux с Python 3.10/3.12, включая чистые core/extras-окружения.

Исходный объём: добавить helper для обычного logger и принадлежащего ему runtime, локальные
console/rotating-file handlers по явной настройке, примеры sync/async программ
и подключения к существующей logger hierarchy. Примеры должны исполняться в тестах
на fake channel; сетевые примеры отдельно помечаются как opt-in.

Готово, когда wheel/sdist устанавливаются в чистое окружение, docs соответствуют
реальному API, нет зависимости от fin-data, tests без сети проходят на выбранных
Windows/Linux и минимальном Python. Лицензия/metadata определены до публикации.

## 0.2 — необязательный outbound relay

Статус: программная часть и основной полевой сценарий завершены для личного
использования. Последняя реализация — dev9: JSON/token, безопасные ошибки,
TLS, clock_skew_tolerance, CLI summary/stop-file и mixed field smoke.
Пункты ниже проверены локально; региональный путь RU → LV → Telegram подтверждён
владельцем с немедленным получением на телефоне. Длительный mixed и автозапуск
остаются эксплуатационными проверками, см. [ревью](REVIEW_0_1_0_2.md).

1. Выбрать packaging и серверный transport; определить wire schema и auth.
2. Реализовать client transport как замену direct transport в одном назначении.
3. Реализовать gateway с aliases/ACL, bounded concurrency, одной provider attempt.
4. Проверить смешанный режим: Telegram через relay, ntfy напрямую в том же runtime.
5. Проверить timeout после provider success, overload, expiry и неправильную identity.

Готово, когда смена direct/relay не меняет вызовы logger, приложение в relay-режиме
не требует provider token/SDK, а недоступность gateway подчиняется общей retry policy.
Command endpoints в relay-only deployment отсутствуют.

## 0.3 — команды проверки и управления приложением

Статус: контракт 0.3.1 реализован в 0.3.0.dev1, сетевого исполнения ещё нет. Объём расширен владельцем
30.09: resume/suspend входят в первую рабочую версию вместе с проверкой состояния.
Ниже порядок реализации; направление и нерешённые детали — в
[ADR 0009](adr/0009-command-scope-and-safety.md).

### 0.3.1. Контракт запросов, времени и результата

Статус: реализованы модели, строгий JSON, корреляция, относительные сроки,
чистые переходы и одноразовое подтверждение намерения. Спецификация:
[COMMAND_PROTOCOL.md](COMMAND_PROTOCOL.md), решение: [ADR 0010](adr/0010-command-wire-time-and-transitions.md).
Постоянная фиксация и действующая защита runtime от повторов относятся к 0.3.2;
helper перехода сам callback не вызывает. Исходные критерии ниже сохранены.

Определить wire-модели команды, регистрации instance, сессии, выдачи права
на выполнение, результата и квитанции. Закрепить переходы состояний и отличие
«обработчик завершился», «операция приложения завершилась», «исход неизвестен».
Словарь callbacks/partial сохраняется; CommandSpec описывает аргументы и политику.
Зафиксировать finite limits и правила для None/текста результата до реализации сети.

Здесь же решить работу при несовпадающих UTC-часах: авторитет сроков у hub,
локальные ожидания монотонные, задержка запроса вычитается из выдаваемого бюджета.
Не переносить clock_skew_tolerance уведомлений на команды. Перед кодом утвердить
отдельным контрактом обработку старых Telegram updates, скачков часов и рестартов.

Готово, когда тесты моделей и переходов покрывают повтор, неверную сессию,
разницу часов в обе стороны и запрет повторного запуска изменяющего callback.

### 0.3.2. Ограниченное постоянное хранение

Реализовать storage protocol и SQLite-вариант: cursor источника, запросы,
результаты, аудит и защита от повторов на hub; журнал исполнения в приложении.
Фиксация запроса предшествует подтверждению источнику, фиксация начала исполнения
предшествует callback. Отказ/переполнение хранилища закрывают новые команды.
Retention не удаляет незавершённые операции или защиту от ещё допустимого повтора.

Готово, когда crash/restart на каждой границе записи не приводит к повторному
побочному действию; неясный исход обозначается явно. Внешний сервер БД не требуется.

### 0.3.3. Hub и клиент приложения

Добавить отдельные command credentials/ACL, регистрацию точной Identity,
session binding, heartbeat и HTTPS long polling клиента. Один hub обслуживает
несколько приложений и чатов; на RU не нужен входящий порт. Запрос без живой
однозначной цели отклоняется. Старые сессии не получают новые команды.
Конкуренция, очереди, запросы хранения и shutdown конечны; relay-only ничего не включает.

Готово, когда fake source → hub → клиент → fake callback → результат проходит
локально, а чужой actor/chat/instance/scope и старая сессия отклоняются.

### 0.3.4. Исполнение пользовательских callbacks

Подключить CommandRegistry к отдельному dispatcher. Явно определить владение
потоком/loop: sync callbacks не блокируют уведомления, async callbacks исполняются
в согласованном loop приложения. Проверить аргументы и права до вызова.
Сначала проверить status/check_load, затем resume/suspend в том же механизме.
Не освобождать слот незавершившегося sync callback только из-за timeout.

Готово, когда словарь/partial и CommandSpec работают, unknown не превращается
в автоматический повтор, а установка Event не выдаётся за окончание загрузки.

### 0.3.5. Telegram, конфигурация и приёмка

Один владелец getUpdates на bot, устойчивый cursor, проверенные actor/chat IDs,
явный адрес приложения в общем чате и коррелированный ограниченный ответ.
Не запускать второго потребителя того же bot рядом с прежним TelegramBot.
Добавить командные секции JSON/typed config, справку по разрешённым командам
и конечный smoke с подставным приложением: status → suspend → status → resume.
Реальный smoke выполняется явно, с тестовым состоянием, а не торговой/загрузочной задачей.

Приёмка 0.3: как минимум два instances в одном чате, точная маршрутизация,
проверка и изменение тестового состояния, запрет чужих запросов, дубликаты,
обрыв после callback, перезапуск hub/клиента, расходящиеся часы и известные unknown.
Проверить отсутствие влияния команд на доставку уведомлений. После этого —
отдельная миграция одного настоящего приложения с его собственными callbacks.

Matrix, broadcast, произвольное выполнение shell/Python и гарантии exactly-once
не входят в этот этап. Shell/Python evaluation не предусматриваются и далее.
