# Восстановление командных клиентов

Version 1.0.3

Автор: Sergey Fundobny (silverbull@mail.ru) + GPT-6

Дата и время последнего изменения: 261014-001243

## Что меняется в 0.4.2.dev4

Для конфликта результатов теперь доступна отдельная
[явная сверка журналов](COMMAND_RESOLUTION.md) в 0.4.4.dev3.
Health сообщает `operator_action_required` и `recovery_hint`; обновление само по
себе не разрешает исторический UNKNOWN и не подтверждает полевое восстановление.

После успешного первоначального запуска CommandClient автоматически восстанавливает
командную сессию при перезапуске gateway или истечении регистрации. Перезапуск
приложения для обычного восстановления связи больше не нужен. Это относится и к
клиенту, созданному через `load_command_client`, и к `RemoteWatcher(command_client=...)`.
Первоначальный `start/astart` по-прежнему сообщает ошибку сразу: запуск приложения
при уже недоступном gateway не превращён в бесконечное фоновое ожидание.

Обновите библиотеку на command gateway и в приложении при их плановой остановке.
Сохраняйте клиентские и серверные SQLite, журналы источников и доверенный корневой CA.
Настройки JSON, token, endpoint и пути менять не требуется. Caddy перезапускать не нужно.
До завершения текущего prod-прогона рабочую установку можно оставить прежней.
Новых HTTP endpoints и wire-схем нет; новая версия hub нужна для подтверждения
точного результата, сохранённого до перезапуска. Старый hub этого не гарантирует.

## Как проходит восстановление

Одна фоновая задача обслуживает heartbeat и восстановление. При потере сессии
приём новых callbacks приостанавливается. Клиент дожидается завершения текущего
получения команды и уже запущенного callback, проверяет журнал и доставляет
неподтверждённые результаты. Затем создаёт новый `session_id` при прежних Identity,
capabilities и `command_display_mode`. Повтор потерянного ответа регистрации
использует тот же новый ID; новые ID не создаются на каждый сетевой отказ.

Поколение владельца клиентского журнала при этом не меняется. Файл не переоткрывается,
позиции не сбрасываются, старые запросы не переадресуются новой сессии. После реального
перезапуска приложения поколение по-прежнему должно быть новым. Для собственного
CommandStore добавлен метод `bind_session(session_id)`: он меняет только цель будущего
приёма и запрещает смену при неподтверждённых либо ещё выполняющихся записях.

Задержка между попытками растёт с jitter до 30 с по умолчанию; начальная величина
`reconnect_delay=1.0`, верхняя `reconnect_max_delay=30.0`. Для Python-конструктора
CommandClient допустимо `0.01 <= reconnect_delay <= reconnect_max_delay <= 300`.
Фактическая пауза составляет от половины до полной текущей величины. Попытки временной
недоступности продолжаются до восстановления или shutdown, но одновременно работает
один координатор, без очереди запросов и накопления таймеров. Обнаружение обрыва
зависит от текущего heartbeat/long poll; мгновенное восстановление не обещается.

При обычном session_ttl=60 heartbeat вызывается примерно раз в 20 секунд
(треть срока из последнего ответа hub). Если poll уже получил stale_session,
а heartbeat ещё ожидает своего очередного запуска, возможен снимок
`connection_state=connected`, `session_valid=false`, `reconnect_attempts=0`.
Это ещё не попытка восстановления; для готовности проверяйте `ready`, а не только
connection_state. При разрешённом session_ttl=300 интервал может достигать 100 секунд.
Далее добавляются backoff, время запросов и готовности сервера; 20 или 30 секунд
не являются общей гарантией восстановления.

HTTP 503 с `closed` означает останавливающийся удалённый hub и допускает восстановление;
локальный `closed` означает закрытый объект. `denied`, неверный ответ, ошибка доверия
TLS и необъяснённый конфликт останавливают восстановление. Конфликт с ещё живым
предыдущим lease ожидается только до верхней границы его срока, вычисленной из
последнего ответа и монотонных часов клиента. Это учитывает консервативный вычет RTT,
не давая клиенту права выполнять команды в промежутке. Чужая живая Identity не вытесняется.

## Результаты и UNKNOWN

С **0.4.4.dev2** неподтверждённые результаты предыдущего запуска приложения тоже
учитываются в `has_pending_results`. Раньше результат чужой session_id мог не
попадать в этот флаг, хотя затем блокировал reconnect как `unresolved_results`.
Сохранённый COMPLETED той же Identity с `execution_active=false` передаётся на
сверку с исходными ref/claim/result. Обработчик команды не вызывается. ACK ставится
только после совпадающей квитанции gateway; неизвестный или отличающийся серверный
результат остаётся конфликтом. Старый UNKNOWN/живое исполнение этот путь не разрешает.

- Если hub уже сохранил результат, но квитанция потерялась, новый hub может подтвердить
  строго тот же результат. Проверяются действующие права token на Identity, исходная
  полная ссылка, claim и всё содержимое результата. В старую запись ничего не записывается.
- Если hub после аварии восстановил STARTED как UNKNOWN, поздний COMPLETED клиента
  его не заменяет. Журналы сохраняют обе стороны наблюдения, клиент блокируется для
  разбора. Нельзя удалять БД или менять owner_id, чтобы обойти эту неопределённость.
- Пока callback фактически работает, новая сессия не открывается. Timeout не освобождает
  его слот. Никакой callback автоматически не повторяется — даже resume/suspend.
- Потерянный grant, который клиент не получил, не превращается в повторный запуск:
  его неисполненная локальная запись завершается; серверный UNKNOWN сохраняется.
- Смена сессии не снимает старые UNKNOWN и не сбрасывает provider cursors. Отдельной
  автоматической сверки неизвестного внешнего побочного действия в этой версии нет.

## Наблюдение

`client.health` и `watcher.command_stats.health` предоставляют:

| Поле | Значение |
| --- | --- |
| `connection_state` | `starting`, `connected`, `reconnecting`, `blocked`, `closed` |
| `reconnect_reason` | Безопасная фиксированная причина, без token/адресов/текста исключения |
| `reconnect_attempts` | Число проходов сверки и регистрации |
| `reconnects` | Число успешно установленных новых сессий |
| `operator_action_required` | Требуется явная сверка журнала; сохраняется после close |
| `recovery_hint` | `review_command_journal` при конфликте результатов или неопределённом исполнении |
| `ready` | Действующая сессия, исправные этапы и отсутствие ожидающих результатов |

`execution_pending` означает ожидание текущей работы, `previous_lease` — ожидание
границы прежней регистрации. `unknown_execution`, `unresolved_results` и
`outcome_conflict` требуют сверки журнала; `tls_certificate` сохраняет `verify_code`
в соответствующем StageHealth. После остановки dispatcher `connection_state`
становится `closed`, но `reconnect_reason` и история ошибок сохраняются.

Успех регистрации снимает прежний запрет сессии, но не скрывает сбой хранения
или доставки результата. `last_error` остаётся историей; смотрите `ready`, текущие
этапы и счётчик `reconnects`. `gateway_server --status` видит серверные процессы,
а не готовность каждого приложения. Его `re_registration_required` после рестарта
означает необходимость новых сессий; клиенты dev4 выполняют это автоматически.

## Проверка при плановом обслуживании

1. Обновить command gateway и приложение, сохранив конфиги, журналы и CA.
2. Выполнить `/status`, убедиться в ответе и готовности командного клиента.
3. В отсутствие исполняемой команды остановить gateway server через трей или --stop.
   SpamBot оставить работающим. Затем снова запустить gateway server через --start;
   Stop сам по себе не планирует следующий запуск. Caddy оставьте работающим.
4. Дождаться готовности серверных компонентов, затем увеличения `reconnects`
   и восстановления клиентского `ready`. При стандартных настройках сначала
   дайте клиенту 1–2 минуты. Отправьте **новую** `/status`: команда, поступившая
   во время недоступности приложения, автоматически заново не исполняется.
5. Проверить resume/suspend новой командой. Старую команду при неизвестном результате
   повторять нельзя без проверки фактического состояния приложения.

Если ответа всё ещё нет, сохраните версию библиотеки **из venv приложения**,
время остановки/запуска, состояние manager и текущие `connection_state`,
`session_valid`, `reconnect_attempts`, `reconnects`, `reconnect_reason`, `ready`
и ошибки poll/heartbeat/storage/result. В версиях ниже 0.4.2.dev4 reconnect
не реализован; обновление только серверного venv код уже работающего приложения
не меняет. Не удаляйте journals и не перезапускайте приложение до сбора состояния,
если нужно разобраться, почему восстановление остановилось.

## Как получить состояние без работающего канала команд

Полевой разбор 13.10.2026: повторный тест SpamBot показал одну попытку reconnect,
затем `closed`, `reconnect_reason=unresolved_results`, `has_pending_results=false`.
Предоставленная копия клиентского journal содержала один неподтверждённый COMPLETED
прежнего запуска (`kill_bot`); на LV hub тот же запрос/claim имел UNKNOWN/timeout
и сохранённую занятость исполнения. Это подтверждённый конфликт результатов,
а не доказательство неисправности TLS или недостаточного ожидания heartbeat.
Оба журнала проверены только чтением; запись и UNKNOWN не изменялись.

Dev2 исправляет пропуск старого результата и ложный признак отсутствия pending,
но **не разрешает этот полевой конфликт автоматически**. После обновления его
точная сверка может дать `outcome_conflict`; это ожидаемый защитный отказ.
Нужно отдельное административное решение с сохранением исходных наблюдений.
Такого штатного интерфейса пока нет; удалять БД, менять owner_id или править ACK
вручную для обхода проверки нельзя. Команду остановки приложения следует завершать
так, чтобы командный runtime успел сохранить и доставить ответ до своего закрытия;
реализация этого порядка в SpamBot требует отдельной проверки в его проекте.

`Application unavailable` — ответ источника команд, а не снимок клиента. Строка
лога, записанная только при переходе monitoring в degraded, также может устареть:
последующие reconnecting/blocked не обязаны менять общее degraded на другое значение.
Приложение должно читать `watcher.command_stats` локально, например раз в 30 секунд
при отсутствии готовности. Это чтение не обращается к gateway или журналу SQLite:

```python
from dataclasses import asdict

stats = watcher.command_stats
if stats is not None and not stats.ready:
    logger.warning("Command recovery status: %s", asdict(stats), extra={"notify": False})
```

Вызов включают в существующий локальный цикл наблюдения приложения с ограничением
частоты. `notify=False` оставляет запись локальной при использовании обработчика
Remote Watch. Этот пример не создаёт второй CommandClient и не регистрирует сессию.
Отдельно запущенный Python-процесс не может прочитать объект watcher из уже работающего
SpamBot. Если локального вывода нет, изменение диагностики приложения потребует
его обновления/перезапуска; старый снимок нельзя выдавать за текущую причину отказа.

Не требуется менять сертификаты клиента или отключать TLS. Локальные проверки
используют подставные callbacks и настоящий тестовый HTTPS; они не заменяют эту
полевую проверку на ваших VM. Основание контракта: [ADR 0014](adr/0014-command-reconnect.md).
