## Рекомендация на 28 сентября 2026 года

Первой альтернативой Telegram предлагается **ntfy**. Целевой телефон пользователя —
Android. Основная ближайшая задача — уведомления; общий чат с командами остаётся
обязательным последующим этапом. **Matrix** предлагается следующим двусторонним
каналом. Это проектный выбор по документации, без подтверждения сетевой доступности.

| Критерий | ntfy | Matrix |
| --- | --- | --- |
| Основная модель | Публикация в topic и подписка | Общение в rooms через homeserver |
| Исходящий адаптер | Небольшой HTTP publish client | Клиент room events с учётной записью |
| Управление приложением | Потребуется отдельный command UX и проверка identity | Чат естественно подходит для команд и ответов |
| Собственное размещение | Свой ntfy endpoint | Собственный homeserver либо выбранный оператор |
| Дополнительное состояние | В основном настройки назначения | Sync state; при E2EE также устройства и ключи |
| Роль в проекте | Первые альтернативные уведомления | Следующий полноценный чат для команд |

Оценки сложности и последовательность — вывод проекта из возможностей протоколов,
а не обещание доступности или сравнительный benchmark.

## ntfy

Публикация использует HTTP POST/PUT; поддерживаются заголовок, приоритет и теги.
Это позволяет сделать небольшой адаптер исходящей доставки.
Источник: [официальный publish API](https://docs.ntfy.sh/publish/).

Android-приложение поддерживает instant delivery через foreground service.
Для self-hosted подписок оно не использует Firebase; F-Droid-вариант также работает
без Firebase. Это делает ntfy подходящим кандидатом для выбранного телефона,
но фоновые ограничения конкретного устройства необходимо проверить.
Источник: [Android delivery](https://docs.ntfy.sh/subscribe/phone/#instant-delivery).

Рабочий профиль должен использовать закрытый topic: отдельные права публикации
приложений и чтения телефона. Случайное имя topic не заменяет авторизацию.
Для собственного сервера задаётся deny-all и явные разрешения.
Источник: [access control](https://docs.ntfy.sh/config/#access-control).

Свой ntfy-сервер — инфраструктура провайдера, а не Remote Watch relay.
Можно отправлять напрямую в него или через relay. Прямой путь проще по числу
компонентов; размещение выбирается по доступности с серверов и телефона.

ntfy нельзя считать отсутствием любых возможностей обратной связи: Android app
умеет публиковать сообщения. Однако публикация в topic сама по себе не задаёт
наш контракт аутентифицированных команд, адресации и аудита. В первой версии
ntfy используется только как outbound-канал.
Источник: [publishing from Android](https://docs.ntfy.sh/subscribe/phone/#publishing-messages).

Если позже понадобится iPhone, instant push для self-hosted ntfy требует отдельного
upstream-маршрута через APNS/Firebase; это меняет инфраструктурные зависимости.
Источник: [iOS instant notifications](https://docs.ntfy.sh/config/#ios-instant-notifications).

## Matrix

Matrix определяет комнаты, отправку событий, идентичность отправителя и получение
изменений через sync. Эти механизмы подходят общему чату с адресными командами.
Источник: [Client-Server API](https://spec.matrix.org/latest/client-server-api/).

Для encrypted rooms адаптеру понадобятся хранение криптографического состояния,
ключей и работа с устройствами. Выбор SDK, восстановление состояния и поведение
при недоступных ключах нужно проверить отдельным прототипом. Нельзя молча отключать
шифрование или выдавать незашифрованную отправку за поддержку encrypted room.
Источник: [end-to-end encryption](https://spec.matrix.org/latest/client-server-api/#end-to-end-encryption).

Рекомендуемый порядок: сначала проверить отправку и чтение комнаты выбранного
homeserver и Android-клиента, затем E2EE/SDK, затем подключать CommandSource к hub.
Matrix можно поднять в приоритетах, если единый чат с командами станет важнее
скорости запуска исходящих уведомлений. Пока ntfy закрывает более узкую первую задачу.

## Другие варианты

| Вариант | Оценка для проекта |
| --- | --- |
| Gotify | Кандидат для self-hosted уведомлений; модель разделяет отправляющие приложения и принимающие clients. Не даёт заметной причины добавлять третий push-адаптер в 0.1 |
| Pushover | Кандидат, если предпочтителен управляемый push-сервис с HTTP API; отдельная внешняя зависимость, не замена чату команд |
| Signal через signal-cli | Возможен отдельный адаптер, но используемый инструмент неофициальный и требует сопровождения совместимости |
| Email | Резервный канал по пожеланию пользователя; не первый мобильный интерфейс |
| Generic webhook | Полезная точка интеграции, но сам по себе не даёт приложение на телефоне |
| MAX | Исключён из текущего плана по выбору пользователя; доступность не оценивалась |

Источники: [Gotify model](https://gotify.net/docs/),
[Pushover API](https://pushover.net/api),
[signal-cli](https://github.com/AsamK/signal-cli).
Сроки, тарифы и региональная доступность этих сервисов здесь не утверждаются.

## Проверка перед принятием канала

Использовать одно синтетическое сообщение без рабочих логов и секретов.
Зафиксировать дату, endpoint, сервер/регион, Android-версию и вариант приложения.
Реальный endpoint и credentials хранятся локально, в отчёт попадают безопасные alias.

1. Отправить с каждого целевого сервера, включая проблемный российский.
2. Проверить получение по Wi-Fi и мобильной сети, при заблокированном экране
   и после длительного простоя; записать задержку и пропуски.
3. Проверить восстановление после потери сети и перезапуска приложения телефона.
4. Проверить два одновременно отправляющих instance и различимость их identity.
5. Подтвердить, что без credentials нельзя читать и публиковать в рабочий topic.
6. При relay отдельно проверить оба участка: сервер → relay и relay → провайдер.

До выполнения этих пунктов статус выбора ntfy — «рекомендован, полевой тест ожидается».
Просмотр документации не считается успешной проверкой доставки.
