## Что уже работает

В **0.4.2.dev1** доступны проверка конфига, запуск manager с независимыми дочерними
процессами notifications/commands, локальные status/stop и ограниченные перезапуски.
Windows tray и прямые сообщения владельцу включаются отдельно. Существующие
CLI компонентов сохранены; одновременно запускать их с manager на тех же ресурсах нельзя.
Подготовка файлов доступна через [gateway_server.deploy](GATEWAY_DEPLOY.md) с 0.4.3.dev1.
Установка службы ОС и doctor — следующие шаги. Сам manager не устанавливает автозапуск.

Проверить существующие настройки можно одной строкой:

```powershell
C:\Work\RemoteWatch\.venv\Scripts\python.exe -m remote_watch.gateway_server --config C:\Work\RemoteWatch\gateway_server.local.json --check-config
```

Пример для текущей схемы LV VM, Caddy на 8443 и двух внутренних listeners:

```json
{
  "schema_version": 1,
  "endpoint": "https://YOUR_LV_VM_IP:8443",
  "control_dir": "control",
  "log_dir": "logs",
  "notifications": {"config": "notification_gateway.local.json", "port": 8765},
  "commands": {"config": "command_gateway.local.json", "port": 8766},
  "caddy": {"mode": "external"}
}
```

Замените `YOUR_LV_VM_IP` на реальный IP или DNS-имя, совпадающее с сертификатом
Caddy. Это адрес, к которому обращаются приложения; порты 8765/8766 здесь не нужны.
Шаблон с синтаксически допустимым примерным DNS-именем:
[gateway_server.example.json](examples/gateway_server.example.json).
Относительные ссылки в нём указывают на соседние открытые примеры; в рабочем
файле следует сослаться на собственные существующие конфиги.

Успех означает только корректную структуру общего и связанных конфигов.
Проверка **не читает окружение с токенами**, не открывает журналы/locks и не
создаёт каталогов. Она не проверяет credentials у провайдера, свободные порты,
синтаксис Caddyfile, права службы, TLS или сетевую доступность RU → LV.
Запуск без `--check-config` пока завершается ошибкой использования, а не делает
вид, что сервер запущен. `--help` доступен и без extras.

## Поля schema_version 1

| Поле | Значение |
| --- | --- |
| `schema_version` | Целое 1, обязательное |
| `endpoint` | Обязательный HTTPS origin, без user/password, пути, query и fragment; конечный `/` допустим |
| `control_dir` | Будущий каталог локального управления и owner lock, обязательный |
| `log_dir` | Отдельный каталог ограниченных служебных логов, обязательный |
| `notifications` | `config`, `port`, необязательный `host`; отсутствие раздела отключает компонент |
| `commands` | Та же структура; отсутствие отключает командный компонент |
| `caddy` | По умолчанию `{"mode":"external"}` |
| `lifecycle` | Необязательные конечные сроки из таблицы ниже |
| `restart` | Необязательные пределы повторных запусков из таблицы ниже |

Нужен хотя бы один компонент. `null`, пустой раздел или `enabled: false` не
заменяют отсутствие раздела. `host` — строго `127.0.0.1` (по умолчанию) или `::1`;
имя `localhost`, wildcard и внешние адреса не принимаются. Listener-порты обоих
компонентов и внешний порт должны различаться, даже при разных host.
Прежние отдельные CLI сохраняют свои возможности; это ограничение общего deployment.

Пути разрешаются относительно **файла, в котором указаны**, а не текущей папки
PowerShell. Общий конфиг можно держать отдельно и ссылаться на прежние абсолютные
пути. Он не меняет относительный `state_dir` внутри command_gateway.json.
Не переносите командный конфиг в другую папку без проверки его реального state_dir.
Пути буквальные: переменные среды и `~` автоматически не раскрываются.
Control, logs и managed Caddy data не могут совпадать или вкладываться друг в друга.

Credentials приложений остаются в прежних конфигурациях. Необязательный раздел
`application.alerts` содержит отдельные назначения владельца и может содержать
`token` либо `token_env`; рабочий общий JSON поэтому тоже приватный.
Неизвестные поля, повторные JSON-ключи, NaN/Infinity, логические значения вместо
чисел и файл больше 1 MiB отклоняются. При записи в Git сохраняются только примеры;
рабочие `*.local.json`, ключи, CA data и SQLite не входят в коммит.

## Caddy

Для существующей установки оставьте `external`: manager не управляет запущенным
отдельно Caddy, не обращается к его admin API и не останавливает его службу.
Ingress в текущем status честно отмечен `unverified`. Поля executable,
config и data_dir в этом режиме запрещены, чтобы не возникало двойного владения.

Настройки managed-режима для нового deployment:

```json
{
  "mode": "managed",
  "executable": "caddy.exe",
  "config": "Caddyfile",
  "data_dir": "caddy-data"
}
```

Все три пути обязательны; binary и Caddyfile должны существовать как файлы.
`data_dir` — **реальное прежнее хранилище Caddy**, а не произвольно выбранная новая
папка. Проверка 0.4.1 подтверждает только наличие файлов и тип пути каталога.
Она не исполняет binary и не доказывает соответствие storage в Caddyfile.
При `--start` manager запускает ограниченный по времени/выводу `caddy adapt` и
сверяет `storage.module=file_system` и абсолютный `storage.root` с `data_dir`.
В Caddyfile требуется явный `storage file_system "C:/.../caddy-data"` и числовой
loopback admin, например `admin 127.0.0.1:2019`. Выключенный admin, wildcard,
hostname и `enforce_origin` для этого режима пока не поддерживаются. Если admin
не указан, задаётся `127.0.0.1:2019`. Ожидается свободный admin-порт.
Ограничения основаны на [параметрах Caddy](https://caddyserver.com/docs/caddyfile/options).

Запускается закрытая JSON-копия проверенного effective config. Во время работы
проверяется ответ admin `/config/` и живой собственный процесс; внешний reload
для этого режима не предусмотрен. Долгая потеря ответа считается зависанием.
CA остаётся в прежнем `data_dir`. Не указывайте новый пустой каталог при миграции
существующего Caddy. Для managed-режима назначьте Caddy отдельный ограниченный
файловый runtime log в его конфиге: его stderr manager намеренно не сохраняет,
чтобы не пересылать неотфильтрованные данные. Настройки файла и ротации описаны
в [CADDY_RECOVERY.md](CADDY_RECOVERY.md).

## Сроки и перезапуск

| Раздел/поле | По умолчанию | Смысл |
| --- | --- | --- |
| `lifecycle.startup_timeout` | 60 | Общий срок начального запуска, секунды |
| `lifecycle.shutdown_timeout` | 30 | Общий срок мягкой остановки |
| `lifecycle.kill_timeout` | 5 | Дополнительный срок подтверждения принудительной остановки |
| `lifecycle.heartbeat_interval` | 1 | Интервал наблюдения обслуживающего loop |
| `lifecycle.heartbeat_timeout` | 15 | Максимальный возраст heartbeat |
| `restart.max_restarts` | 3 | Повторные запуски в окне, целое 0..100; 0 запрещает их |
| `restart.window` | 300 | Скользящее окно учёта попыток |
| `restart.initial_delay` | 2 | Начальная задержка перед повтором |
| `restart.max_delay` | 30 | Верхний предел задержки с учётом jitter ±20% |

Сроки положительные, конечные, не больше суток. Heartbeat interval не меньше 0.1;
timeout не меньше трёх интервалов; startup timeout не меньше heartbeat timeout.
Для restart: `initial_delay <= max_delay <= window`. Расчёты используют
монотонное время, а не расходящиеся часы VM.

Параметры управляют реальными процессами; бюджет хранится в памяти manager.
После исчерпания попыток нужен оператор. Конфиг, права, ownership и отказ
постоянного журнала не исправляются бесконечным перезапуском.
Недоступность TimeAPI сама по себе не должна перезапускать здоровый loop.
Heartbeat поступает из рабочего event loop, время получения отмечает manager.
Падение/зависание после успешного общего запуска восстанавливается независимо
от соседнего процесса. Начальный отказ или истечение startup timeout откатывают
все уже запущенные собственные компоненты. После исчерпания бюджета компонент
остаётся failed, а manager и здоровые соседи продолжают работать.

Общая мягкая остановка ограничена shutdown timeout; после него manager завершает
только свои процессы и ждёт не дольше kill timeout. Локальное освобождение UI,
alert runtime и control listener имеет отдельные короткие сроки: до 3, 2 и 1 секунды соответственно.
Windows x64 использует Job Object с kill-on-close; Linux — parent-death signal.
Дочерний процесс не открывает ресурсы до установления владения. Иные ОС и
32-битный Windows пока не поддерживаются для manager; библиотечный API от этого не меняется.
Подробный контракт: [ADR 0012](adr/0012-gateway-deployment-and-supervision.md).

## Первый запуск вместо двух окон gateway

1. Установите эту версию в **отдельное тестовое окружение** с нужными extras:
   `remote-watch[gateway,commands,telegram,ntfy]`. Для Windows tray добавьте `tray`.
2. Создайте `gateway_server.local.json` по примеру выше, сохранив реальные пути
   конфигов и `state_dir`. Для работающей службы Caddy оставьте `external`.
3. Выполните `--check-config`. Перед эксплуатационным переключением штатно
   остановите два прежних gateway. Caddy останавливать не требуется.
4. Запустите manager и прочитайте статус из другого PowerShell:

```powershell
C:\Work\RemoteWatch\.venv\Scripts\python.exe -m remote_watch.gateway_server --config C:\Work\RemoteWatch\gateway_server.local.json --start
C:\Work\RemoteWatch\.venv\Scripts\python.exe -m remote_watch.gateway_server --config C:\Work\RemoteWatch\gateway_server.local.json --status
```

Для остановки — Ctrl+C в первом окне либо та же команда с `--stop` из второго.
Ответ `stopping` подтверждает принятие запроса; окончание процесса подтверждает
завершение остановки. `--status/--stop` читают только общий `control_dir`, поэтому
работают и после повреждения/удаления связанного component JSON.

Локальный status содержит состояния, фиксированные причины, счётчики и число
перезапусков; `ingress=unverified` не заменяет клиентский HTTPS smoke. Control
слушает случайный порт только `127.0.0.1`; его **не нужно добавлять в Caddyfile**.
Каталог control закрывается для других пользователей: Windows — текущий аккаунт
и SYSTEM, Linux — 0700. Управляйте сервером из того же аккаунта. Не удаляйте lock
и не запускайте второй manager через другой control_dir для обхода ownership.
Старый runtime.json после crash не разрешает завершать процесс по сохранённому PID.

Служебный журнал — `log_dir/gateway_server.jsonl`: безопасные переходы состояния
с UTC-временем, до 1 MiB на файл и 5 архивов по умолчанию. Это не журнал содержимого
команд. Ошибка записи видна в status и через независимое оповещение владельца;
её признак сохраняется до перезапуска manager. Пути, токены и traceback в status не попадают.

## Трей и сообщения владельцу

Настройки самого приложения находятся в `application` **того же общего файла**:

```json
"application": {
  "ui": "tray",
  "icon_path": null,
  "log_max_bytes": 1048576,
  "log_backups": 5,
  "alerts": {
    "cooldown": 60,
    "destinations": [
      {
        "alias": "operator-telegram",
        "provider": "telegram",
        "settings": {
          "token_env": "GATEWAY_OPERATOR_BOT_TOKEN",
          "chat_id": 123456789,
          "display_mode": "text"
        }
      }
    ]
  }
}
```

Можно вместо `token_env` указать приватный `token`. Формат назначения совпадает
с notification gateway; ntfy также поддерживается. Максимум 8 назначений,
по 16 ожидающих сообщений на каждое, одна попытка на доставку. Можно задать
`timeouts` назначения по [GATEWAY_SERVER.md](GATEWAY_SERVER.md). Получатели задаются
явно: manager не считает владельцами автоматически все чаты обслуживаемых приложений.

Сообщения на английском отправляются напрямую провайдеру при сбое/восстановлении
компонента, повторном запуске и исчерпании бюджета. Для каждого компонента
действует cooldown 1..86400 секунд; повтор одинакового состояния не отправляется,
в очереди переходов остаётся последнее состояние. Отказ доставки не входит
повторно в этот же канал. Счётчики `alert_delivery` показывают попытки/приём
провайдером/отказы, а не подтверждение показа на телефоне. Недоступность всего
хоста или manager требует внешнего наблюдателя: остановившийся процесс не отправит
сообщение о собственной смерти. По умолчанию destinations пусты и сообщений нет.

Tray — необязательный Windows UI с текущим состоянием в подсказке и пунктами
`About` и `Stop gateway server`. About показывает версию и описание в подменю;
Stop вызывает ту же общую остановку. Для службы ОС
нужен `ui=headless`; интерактивный трей и системная служба — разные сеансы Windows.
После проверки запуска в консоли можно использовать `pythonw.exe` с теми же
аргументами `--start`; диагностика останется в файле и `--status`.
Необязательный extra `tray` содержит pystray/Pillow; Linux manager не требует их.

С 0.4.2.dev2 встроен логотип Remote Watch — серый робот с символом наблюдения
и связи. Он поставляется внутри wheel; копировать папку `logo` на сервер не нужно.
В 0.4.2.dev3 эмблема стала фиолетовой, лицо уточнено по большому исходнику.
С dev4 единственный исходный ICO лежит в [logo/remote_watch.ico](../logo/remote_watch.ico).
В src копии нет; wheel устанавливает его в `share/remote-watch/logo` своего Python-окружения.
Запуск из checkout использует корневую logo независимо от текущего рабочего каталога.
С 0.4.3.dev3 deploy дополнительно создаёт `logo/remote_watch.ico` в серверном
комплекте и задаёт `application.icon_path: "logo/remote_watch.ico"` в новом JSON.
При повторном deploy прежний конфиг и пользовательская иконка сохраняются.
Клиентским приложениям копия из серверного комплекта не требуется.
`icon_path: null` или отсутствие поля выбирает этот логотип. Для своей иконки:

```json
"application": {
  "ui": "tray",
  "icon_path": "logo/my_gateway.ico"
}
```

Относительный путь считается от **общего JSON сервера**, а не от папки PowerShell.
Допускается абсолютный путь. В Python API используется `ApplicationConfig(icon_path=Path(...))`
с абсолютным путём. Рекомендуется ICO с размерами 16/24/32/48/64/128/256;
PNG также поддерживается. Изменение применяется после перезапуска manager.
`--check-config` проверяет наличие файла, но не декодирует картинку и не импортирует
Pillow. Повреждённое изображение обнаруживается при запуске трея; запуск завершается
без вывода содержимого файла. В `headless` изображение не загружается, но явно
указанный путь всё равно проверяется. Исходник и запрос генерации:
[GATEWAY_FOLLOW_UP.md](GATEWAY_FOLLOW_UP.md).

## Ошибки и миграция приложений

CLI возвращает 0 при успешной проверке, 1 при отказе и 2 при неверных аргументах.
`code=config_read/config_json/config_size/config_schema/config_value` указывает
категорию; `field` — только известный раздел. `path_unavailable` означает неверный
тип/отсутствие требуемого файла. `component_config` означает ошибку связанного
конфига: запустите его прежний `--check-config` для точного безопасного пояснения.
Значения и пути намеренно не выводятся.

Миграцию callbacks status/resume/suspend можно готовить независимо от manager.
С 0.4.2.dev4 клиент команд **автоматически регистрирует новую сессию после
перезапуска hub**, сохраняя журнал. Для старых клиентов нужен перезапуск приложения.
Готовность командного пути всё равно проверяется отдельно: UNKNOWN/несверенный
результат может блокировать восстановление. Callback автоматически не повторяется.
Подробности: [COMMAND_RECONNECT.md](COMMAND_RECONNECT.md). См. [COMMAND_EXECUTION.md](COMMAND_EXECUTION.md)
и раздел миграции [ADR 0012](adr/0012-gateway-deployment-and-supervision.md).
При автоматическом перезапуске command-компонента status дополнительно показывает
`command_sessions=re_registration_required`; dev4 клиент выполняет её автоматически,
но manager не наблюдает результат каждого клиентского handshake. Даже `ready` не доказывает готовность
прежних клиентских сессий. После полного нового запуска manager состояние сессий
отмечено `not_verified`, потому что manager не знает жизненный цикл приложений.
