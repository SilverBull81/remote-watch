## Среда и проверки

```console
python -m venv .venv
python -m pip install -e ".[dev,telegram,ntfy,gateway,commands,service,tray]"
python -m ruff check .
python tools/check_style.py
python tools/check_docs.py
python -m pytest -q -m "not integration"
python tools/validate.py --mode core --output .development/check-core
python tools/validate.py --mode extras --output .development/check-extras
```

Выполняйте команды из venv. Каталоги output должны быть новыми. validate строит
sdist/wheel, проверяет отсутствие private/runtime файлов, заново собирает wheel
из sdist, устанавливает в чистый venv, проверяет installed CLI и выполняет тесты.
`integration` — opt-in живые провайдеры, не часть обычного CI. В тестах нет production
credentials, имитации не выдают за field acceptance. Windows и Linux, Python
3.10/3.12, core/extras проверяются восемью ручными jobs `.github/workflows/validation.yml`.
CI запускается для согласованных крупных изменений, не автоматически на каждый push.

## Рабочие артефакты

Локальная папка `.development/` заменяет прежнюю `build/` как место для отчётов,
проверочных окружений, релизных файлов и временной работы. Она исключена из Git,
Ruff и sdist. Setuptools использует `.development/setuptools/` по setup.cfg;
не переносите временные файлы в src/ или docs/ ради удобства.

Сохраняйте опубликованные wheel/sdist/SHA256SUMS и результаты проверок, на которые
ссылается VALIDATION.md. Одноразовые venv, промежуточные сборки, дубли архивов и
каталоги синтетических тестов после проверки удаляются. Venv не переносится вместе
с папкой: в его launchers записаны абсолютные пути, при необходимости создайте новый.
Встроенные в старые логи абсолютные пути остаются историческими; сами отчёты
после переезда находятся под `.development/`.

Секреты, реальные журналы команд и машинные инструкции к рабочим артефактам не
относятся. Их не удаляют при очистке; локальная документация хранится в docs/private/,
рабочие данные — в явно выбранных приложением местах.

## Порядок выпуска

Обычные проверенные исправления выпускаются сразу как стабильные patch-версии:
1.0.1, 1.0.2 и далее. Совместимые расширения получают minor-номер, например 1.1.0;
несовместимые изменения публичного API требуют следующего major-номера.
Маркировка dev по умолчанию не используется. Для крупных или спорных изменений,
которым нужен отдельный полевой прогон, допустим release candidate вида 1.1.0rc1.

Перед стабильным выпуском выполните необходимые behavioral/style/docs и чистые
core/extras wheel-from-sdist проверки. Объём полевых проверок зависит от изменения;
зафиксируйте реальные результаты и ограничения. Полную CI-матрицу запускайте для
согласованных крупных изменений. Затем закрепите проверенный commit аннотированным
тегом vMAJOR.MINOR.PATCH и создайте GitHub Release с wheel, sdist и SHA256SUMS.txt.
Опубликованные версии, файлы и теги не заменяйте: новое исправление — новый номер.
Prod устанавливается оператором в согласованное окно обслуживания; публикация
релиза сама не меняет рабочие приложения/службы. PyPI и единый EXE не планируются.

## Изменение

Прочитайте AGENTS и относящийся контракт. Сохраняйте чужие изменения, не трогайте
production процессы/SQLite/CA без отдельной авторизации. Исправление гарантии
должно иметь тест поведения; механическая массовая правка — также сравнение AST.
Проверяйте состав архивов и staged diff, затем создавайте локальный осмысленный commit.
Не называйте реализацию релизом или успешной полевой проверкой без соответствующей записи.

## Публичная и локальная документация

README — краткий старт; docs — инструкции текущего API, examples — синтетические
конфиги. Публичные материалы не содержат имён deployment, реальных путей/адресов,
топологии, credentials и полевых журналов. Локальные инструкции оператора и старые
подробные записи хранятся в игнорируемой docs/private. MANIFEST дополнительно
исключает её из sdist; Git ignore сам по себе не исключает файлы из Python-поставки.

Перенос в private не удаляет прежние сведения из истории Git. История не
переписывается в рамках реорганизации: отдельный аудит/переписывание потребовали бы
отдельного решения и плана синхронизации. Не дублируйте TODO по десяткам документов:
нереализованные возможности — только BACKLOG, текущие ограничения — в руководстве.
