# Command hub и клиент приложения

Version 1.0.5

Автор: Sergey Fundobny (silverbull@mail.ru) + GPT-6

Дата и время последнего изменения: 261008-001220

## Что реализовано в 0.3.3.dev1

Этап 0.3.3 соединяет отдельную авторизацию команд, постоянные журналы hub и клиента,
регистрацию приложения, heartbeat и HTTPS long polling. На стороне RU нужны только
исходящие соединения. Один hub обслуживает несколько приложений и чатов.

Проверенный путь: подставной источник → настоящий hub → HTTPS → клиент → подставной
callback → сохранённый результат → квитанция hub. Тесты используют временные SQLite
и собственный временный CA. Ни Telegram, ни настоящие приложения они не затрагивают.

В 0.3.4.dev1 поверх этого клиента добавлены dispatcher пользовательских
sync/async callbacks и подключение к RemoteWatcher: [COMMAND_EXECUTION.md](COMMAND_EXECUTION.md).
Получение
Telegram updates, командные JSON-настройки, CLI и живой smoke — к 0.3.5.
Текущий `python -m remote_watch.gateway --config ...` запускает только outbound relay.

## Разделение ответственности и прав

| Объект | Назначение |
| --- | --- |
| `commands.hub_config.CommandPrincipal` | Отдельный token приложения, список точных Identity и разрешённых scopes |
| `CommandAccess` | Точное сочетание actor_id, conversation_id, Identity и scopes |
| `CommandSource` | Отдельный секрет доверенного адаптера входящих сообщений и его ACL |
| `CommandHubConfig` | Неизменяемые настройки прав и конечных пределов |
| `commands.hub.CommandHub` | Регистрации, проверка свежести, сохранение разрешений и результатов |
| `gateway.command_server.CommandHubServer` | Только командные endpoints; владеет запуском и остановкой hub |
| `adapters.command_http.HttpsCommandTransport` | Проверяемый TLS, Bearer auth, конечные запросы без автоматических повторов |
| `commands.client.CommandClient` | Журнал приложения, heartbeat, получение разрешения и доставка результата |
| `CommandTicket` | Сохранённое разрешение, которое исполнитель проверяет перед callback |

Приложения и источники имеют разные секреты длиной 32–256 печатных ASCII-символов.
Значения нужно генерировать случайно; проверки длины недостаточно для стойкости секрета.
Токены скрыты из repr настроек. Ошибки не возвращают токены, URL, actor/chat или тело команды.
Настройки команд не наследуют права relay. При совместном размещении оператор задаёт
другие секреты; библиотека не читает соседнюю конфигурацию relay для поиска совпадений.

Каждая полная Identity принадлежит ровно одному principal. Все пять полей проверяются
точно; шаблонов, поиска по имени чата и broadcast нет. Scope capability должен входить
и в права приложения, и в правило отправителя. Неизвестные команды и аргументы для
capability с `accepts_arguments=False` отвергаются до записи разрешённой команды.

Доверенный source вызывает Python API `target`, `source_cursor`, `submit`, `results`
и `acknowledge`. Публичного HTTP endpoint для произвольной передачи actor/chat нет:
эти идентификаторы должен устанавливать будущий адаптер из проверенного ответа
провайдера. Секрет приложения не разрешает impersonation отправителя.

## Регистрация и сохранение состояния

Каждый запуск hub получает новый `epoch = secrets.token_hex(16)`. Он совпадает
с `generation` его SQLite-журнала; роль журнала — `StoreRole.HUB`.
Каждый запуск приложения получает новый `session_id` того же формата; это
`generation` клиентского журнала с ролью `StoreRole.CLIENT`.
`owner_id` и путь файла, напротив, остаются постоянными между перезапусками.

Hub регистрирует `CommandRegistration(identity, session_id, capabilities)`.
С 0.4.1.dev9 допускается также command_display_mode=full/compact/text; None
оставляет оформление на источнике. Режим принадлежит конкретной регистрации
и сохраняется в исходном request до submit. Изменить его повторной регистрацией
того же session_id нельзя; новый конфиг применяется после нового запуска приложения.
Собственный доверенный source получает режим через `hub.response_mode_for(token, ref)`
после выбора исходной сессии и передаёт его в CommandRequest.command_display_mode.
Hub отклоняет несовпадение с регистрацией; восстановленное решение не выбирает режим заново.
Повтор той же регистрации возвращает оставшееся время и не продлевает срок.
Heartbeat продлевает только ещё живую сессию. Второй процесс с той же Identity
не заменяет живой первый процесс. Истёкший session_id больше нельзя зарегистрировать
в этом запуске hub; новый процесс использует новый ID. Клиент не регистрируется
автоматически заново после истечения срока или смены epoch.

`submit` проверяет ACL и возраст `message_date` через TrustedClock, затем атомарно
сохраняет принятое решение и позицию source. Только возвращённый cursor можно
подтвердить провайдеру. Переполнение или ошибка записи не продвигают cursor.
Отказ по правам/времени фиксируется вместе с позицией, но не создаёт исполнимую команду.

Порядок исполнения:

1. Клиент получает offer с постоянной последовательностью журнала и остатком TTL.
2. Клиент сохраняет запрос и единственный claim_id до обращения за разрешением.
   Dispatcher проверяет аргументы до grant; отказ сохраняется как REJECTED и
   отправляется через result без запуска callback.
3. Hub сохраняет CLAIMED и STARTED до отправки grant.
4. Клиент проверяет полную корреляцию, вычитает весь RTT и сохраняет свой STARTED.
5. `acquire()` возвращает ticket. Исполнитель непосредственно перед callback вызывает
   `begin(ticket)`; только `True` разрешает вызов. Повтор `begin` запрещён.
6. После завершения callback `complete(ticket, result)` сначала сохраняет результат
   локально и только затем отправляет его hub. ACK клиента следует за точной квитанцией.
7. Доверенный source читает результат и отдельно подтверждает его после ответа в чат.

`acquire()` сам callback не вызывает. Ticket нельзя копировать или передавать другому
клиенту. Между успешным `begin` и непосредственным вызовом не должно быть `await` либо
другой отложенной работы. Если срок уже истёк, callback не вызывается; исполнитель
сохраняет UNKNOWN/TIMEOUT через `complete`. Dispatcher 0.3.4 дополнительно проверяет
`remaining(ticket)` в рабочем потоке непосредственно перед callback. При timeout
с ещё живым callback используется `complete(..., execution_finished=False)`;
после фактического завершения — `release(ticket)`, без замены результата.
`pending()`, `lookup(ref)` и `reconcile()` поддерживают разбор неподтверждённых
записей. Восстановленный UNKNOWN автоматически не освобождается.

После потери grant второй claim не выдаёт новое разрешение. Команда может остаться
невыполненной; по истечении срока hub отмечает UNKNOWN. Это осознанная цена запрета
неявного повторного действия. Потеря квитанции результата допускает повтор доставки
того же результата через `flush_results()`, но не повтор callback.

Hub периодически завершает просроченные записи. READY/CLAIMED превращаются в EXPIRED,
STARTED — в UNKNOWN. Уже сохранённый UNKNOWN не заменяется поздним COMPLETED;
клиент получает конфликт, требующий разбора. UNKNOWN с возможным живым исполнением
остаётся закреплённым в журнале. Истечение timeout не доказывает остановку callback.
Подтверждение отправки ответа в чат само по себе такую запись не освобождает.

При перезапуске журналы сохраняют cursor и восстанавливают безопасные терминальные
состояния, но не монотонные сроки старого процесса. Клиент не отправляет результаты
старой сессии от имени новой и не запускает их callbacks. Восстановленные результаты
hub доступны источнику. Утрата самого файла hub не является штатным restart:
для нового журнала нужен новый `stream_id` клиента и отдельное согласование состояния.

## Время и границы ресурсов

В 0.3.6.dev1 добавлен `CommandHub.health()` для локального чтения готовности
на loop владельца, без сетевой пробы и обращения к SQLite. Он показывает
maintenance_running/time_ready, ready/reason и fatal. Ошибка, ранний return или
неожиданная отмена maintenance task фиксируются как maintenance_failed;
последующие вызовы hub отклоняются с unavailable, ожидающие polls пробуждаются.
Уже начатая операция хранения может завершиться: fault detection не откатывает
commit и не доказывает, что выполнявшийся callback остановился.
Штатное close не считается аварией. Временная ошибка UTC делает hub неготовым
к приёму новых команд, но сохраняет цикл обновления. Подробности состояния
сервера и CLI: [COMMAND_SOURCES.md](COMMAND_SOURCES.md).

Hub получает `TrustedClock` и необязательный `TimeSource`. В рабочей конфигурации
используется выбранный `TimeApiTimeSource`, без автоматической замены источника.
Время обновляется при старте и далее каждые 60 с; одна попытка ожидается до 5 с.
Ошибка обновления закрывает приём новых команд до следующего успешного показания.
Уже принятые сроки не продлеваются. Без source можно заранее установить показание
для теста; после его срока годности новые команды также закрываются.

Hub, его журнал и TrustedClock используют одни монотонные часы. Клиент и его журнал
используют свои общие монотонные часы. В рабочем случае это `time.monotonic`.
Отдельные системные часы RU/LV не сравниваются. Откат монотонных часов делает объект
непригодным для новых действий до перезапуска. Допущения точности TimeAPI и проверка
источника изложены в [COMMAND_TIME.md](COMMAND_TIME.md).

| Ограничение | По умолчанию / предел |
| --- | --- |
| Principal / source | По 64 в конфигурации |
| Identity на principal / ACL на source | 64 / 256 |
| Выданные сессии, включая истёкшие | 256, настраивается до 4096 на запуск hub |
| Неподтверждённые или ещё исполняемые записи | 1000; дополнительно действуют StoreLimits |
| Срок регистрации | 60 с, допустимо 10–300 с |
| Ожидание long poll | 5 с, максимум 20 с и строго меньше половины session TTL |
| Ожидание хранения | 3 с, максимум 30 с |
| Рабочий поток хранения | Один на объект; только hub имеет ограниченное ожидание в event loop |
| `max_storage_waiters` hub | 64 по умолчанию, 1–256; не включает активную операцию |
| HTTP-обработчики / long polls | 16 / 8; общий предел не больше 256 |
| Ожидающие poll на сессию | Один |
| Запросы HTTP-клиента | Два: обычный обмен и heartbeat |
| HTTP timeout клиента | 25 с, максимум 30 с; без скрытого retry |
| Тело HTTP / командное сообщение | 70 000 / 65 536 байт |
| Чтение тела на сервере | До 5 с; auth проверяется до чтения |
| Ожидание закрытия журнала | 5 с по умолчанию |

С 0.4.1.dev12 короткое пересечение `_offer`, `sweep` и других обращений к журналу
hub ожидает освобождения исполнителя в ограниченной FIFO-очереди event loop.
`storage_timeout` — общий бюджет ожидания и выполнения, он не начинается заново
при освобождении исполнителя. `max_storage_waiters` можно задать в разделе `hub`
JSON либо CommandHubConfig. Настройки существующего конфига менять не требуется.
Клиентские/source StoreWorker сохраняют прежний немедленный отказ при занятости.

Очередь ThreadPoolExecutor не накапливается. Отменённый либо просроченный waiter
не вызывает store; при закрытии ожидающие операции также не запускаются.
Отмена/timeout уже начатой операции не освобождают слот до фактического завершения.
Единственная отложенная операция executor — закрытие журнала за текущей записью. Синхронную операцию произвольного пользовательского store
Python принудительно не останавливает: реализации должны иметь собственные
конечные ожидания. Это также относится к пользовательским TimeSource/Transport:
они обязаны не блокировать event loop и корректно принимать отмену.

При остановке hub будит long polls и отменяет обслуживание времени. Сервер после
закрытия hub очищает aiohttp runner с `shutdown_timeout=1`. Лимит журнала и очистка
HTTP последовательны. Клиент прекращает heartbeat, закрывает transport и журнал;
остановку чужого callback этот низкоуровневый объект не подтверждает.

TLS-handshake, число ещё не допущенных TCP-соединений и защита публичного входа
относятся к reverse proxy/firewall. Лимиты обработчиков не являются защитой от
всех видов сетевого DoS. Для закрытого VM/VPN-размещения действуют рекомендации
[GATEWAY_SERVER.md](GATEWAY_SERVER.md); слушатели relay и команд настраиваются отдельно.

## Транспорт и установка

```powershell
python -m pip install "remote-watch[commands]"
```

Импорт командных моделей, hub, клиента и серверного класса не импортирует aiohttp,
не создаёт потоков и не открывает сеть. Optional-зависимость нужна при запуске HTTP.

Операции — POST `/v1/commands/register`, `/heartbeat`, `/poll`, `/claim`, `/result`,
`/release`. Последняя добавлена в 0.3.4: CommandClaim подтверждает фактическое
окончание исполнения, а CommandReceipt относится к прежнему терминальному
результату. Проверяются владелец, ref, claim_id и digest. Старая сессия этого же
запуска hub может закончить отчёт; чужая сессия не может снять блокировку.
Hub и клиент нужно обновить вместе; JSON-схема сообщений остаётся 1.
Тело запроса использует [COMMAND_PROTOCOL.md](COMMAND_PROTOCOL.md). Ответ poll — 204
либо JSON с точными полями `offer`, `sequence`, `remaining_ttl`; `offer` содержит
обычный CommandRequest. Остальные успешные ответы — типизированные сообщения
протокола. Повторные ключи, лишние поля и неверные типы отклоняются.

`HttpsCommandTransport(endpoint, token, ssl_context=...)` принимает HTTPS origin без
userinfo, пути, query и fragment. Проверяются CA и имя/IP сертификата. Redirects,
proxy из окружения, cookies и сжатие отключены. `allow_loopback_http=True` допустим
только явно и только для числового loopback — для локального теста или TLS reverse
proxy на самой VM. Он не разрешает незашифрованную связь между RU и LV.

Ошибки имеют фиксированные коды. С 0.4.1.dev6 HTTP-клиент сохраняет серверный код
из JSON-объекта с единственным полем `code` (до 256 байт, без дублей и сжатия),
если код соответствует HTTP-статусу. Например, HTTP 409 сохраняет `stale_session`,
а HTTP 503 различает `capacity`, `closed` и `unavailable`. Чтение ограничено общим
timeout запроса. При неподходящем или незавершённом теле остаётся классификация:
401/403 → `denied`, 409 → `conflict`, 429 → `busy`, остальные → `unavailable`.
Числовой `http_status` сохраняется даже при отказе чтения/разбора после заголовков;
ошибка до получения заголовков оставляет None. Произвольное
тело ошибки внешнего сервера не копируется в исключение. Ни один отказ не даёт
разрешения вызвать callback.

## Причины busy и обновление клиента

С 0.4.1.dev12 CommandError и текущий StageHealth сохраняют `busy_reason`.
HTTP 429 может содержать `{"code":"busy","busy_reason":"storage_wait_timeout"}`.
Допустимы только следующие фиксированные причины:

| busy_reason | Причина |
| --- | --- |
| `storage_busy` | Исполнитель занят у worker без очереди, например на клиенте |
| `storage_queue_full` | Достигнут предел ожидающих обращений к журналу hub |
| `storage_wait_timeout` | Бюджет ожидания исчерпан до запуска операции store |
| `session_poll_active` | Для этой сессии уже выполняется другой poll |
| `http_requests_full` | Достигнут общий предел HTTP-запросов gateway |
| `http_polls_full` | Достигнут отдельный предел long poll |
| `transport_requests_full` | Заняты оба места HTTP-транспорта клиента |
| `client_operation_active` | Уже выполняется несовместимая операция клиента/runtime |

Для остальных кодов busy_reason отсутствует. Неизвестные значения/поля, дубли,
слишком большие тела и несовпадение HTTP-статуса не раскрывают подробностей.
Старый клиент по-прежнему получает busy по HTTP 429; для просмотра новой причины
обновите также библиотеку в приложении. Прежняя одно-полевая оболочка ошибки
поддерживается. Успешные сообщения и постоянные журналы не меняют формат.
При восстановлении соответствующего этапа текущий busy_reason очищается;
счётчики отказов/восстановлений и last_error сохраняют прежний смысл.

Достаточно обновить command gateway для устранения обычных пересечений и ложной
потери времени во время refresh. Плановый перезапуск hub всё ещё требует нового
жизненного цикла командного клиента приложения: автоматической перерегистрации
нет. Журналы, CA и provider cursors не удалять. Полевая проверка: оставить приложение
без команд на несколько периодов refresh, затем проверить status и resume/suspend.
Если busy остаётся, собирать busy_reason/этап; при time_unavailable — time_reason.

## Локальная проверка без провайдера

```powershell
python -m pytest tests/contract/test_command_hub.py tests/contract/test_command_http.py -q
```

HTTP-тесты требуют development-зависимостей, включая cryptography. Они создают
сертификаты только во временном каталоге, не меняют системное хранилище доверия и
не читают credentials.local.json. Общая проверка установленного wheel также
подтверждает отсутствие старых корневых smoke-модулей.
