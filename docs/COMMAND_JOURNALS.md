## Где смотреть

С **0.4.4.dev5** работающий gateway передаёт кэш сводок в существующий локальный
status. Новых публичных endpoints нет. Прежний client doctor не получает сводку
всего hub: токен приложения не даёт доступа к данным других приложений.

На LV, пока gateway_server работает:

```powershell
$py = 'C:\Work\RemoteWatch\.venv\Scripts\python.exe'
& $py -m remote_watch.gateway_server --config C:\Work\RemoteWatch\gateway_server.local.json --status
& $py -m remote_watch.diagnostics.gateway_doctor --mode server --config C:\Work\RemoteWatch\gateway_server.local.json --online --report .\doctor-journals.local.json
```

В `components.commands.journals` находятся `hub` и список `sources` в порядке
конфигурации. В doctor это `commands.journal.hub` и `source_1`, `source_2` и т. д.
Имена источников, токены, Identity, actor/chat, пути, запросы, тексты результатов,
provider IDs и реальные курсоры не включаются. JSON-отчёт содержит только
разрешённые числа и фиксированные категории; новый report не перезаписывает старый.

Обновите библиотеку на gateway и перезапустите **весь manager**, чтобы его дочерние
процессы использовали ту же версию локального IPC. Существующую внешнюю службу
Caddy менять не требуется. Command wire, конфиги и SQLite-схемы не изменены;
сохраняйте прежние пути журналов. Старый manager без этой сводки даст skipped,
а не ложное подтверждение отсутствия UNKNOWN.

## Что означают числа

| Поле snapshot | Значение |
| --- | --- |
| kind / schema_version | hub, client либо source; версия существующего SQLite |
| records / records_limit | Все сохраняемые команды и их лимит; для source — replay-ID |
| pending | Без ACK **или** с неосвобождённым исполнением; у source — одно решение, 0/1 |
| unknown | Все сохраняемые UNKNOWN, включая уже подтверждённые источнику; у source — null |
| unresolved_unknown | UNKNOWN без отдельного административного решения; у source — null |
| execution_active | Исполнения, окончание которых не подтверждено; у source — null |
| streams / streams_limit | Постоянные потоки защиты от повтора и их предел |
| audit_entries / audit_limit | Ротируемый краткий аудит и его предел |
| payload_bytes | Объём запросов/результатов и отдельных resolution; у source — объём данных без их содержимого |
| payload_reserved_bytes / payload_limit_bytes | Занятый логический резерв и предел, включая место под ещё не полученный результат |
| database_bytes / database_limit_bytes | Выделенные страницы основной SQLite и настроенный предел файла |
| free_database_bytes | Уже выделенные свободные страницы, которые SQLite переиспользует |
| resolutions | Отдельные административные решения; исходный UNKNOWN остаётся UNKNOWN |
| capacity | ok, near_limit, at_limit или unknown |

Пример: records=87 при records_limit=1024 не означает очередь из 87 команд.
Часть записей завершена и сохраняется до retention. Pending=2 может быть нормальным
обменом подтверждениями. UNKNOWN=1 требует разбора конкретного исхода; автоматически
повторять callback нельзя. execution_active — консервативный маркер журнала,
а не число живых потоков/процессов после аварии.

Для hub/client pressure считается по числу записей, постоянных потоков, резерву
payload и используемым страницам относительно лимитов. От 80% — near_limit,
от 100% — at_limit. Ротируемый аудит сам по себе не создаёт давление на admission.
Свободные страницы учитываются, но фрагментация и будущий размер команды не позволяют
по одной сводке гарантировать успешный приём. Это не свободное место диска ОС.

`journal_capacity` и `journal_unknown` в doctor — **warning**. Последний ставится
по unresolved_unknown: после отдельного принятия клиентского итога исходный UNKNOWN
остаётся в истории, но уже не требует повторной сверки. Само подтверждение окончания
исполнения или ACK источника не является принятием известного бизнес-результата.
Эти предупреждения не меняют
готовность hub, не вызывают restart и не приводят к автоматической очистке.
Код выхода doctor остаётся 0, если нет failed; warnings нужно прочитать.
Решение о UNKNOWN: [COMMAND_RESOLUTION.md](COMMAND_RESOLUTION.md).

## Насколько свежий снимок

Каждый storage worker может обновить сводку после обычной операции не чаще раза
в 5 секунд. Дополнительных задач/очередей executor нет. Используется тот же
последовательный владелец, SQL-наблюдение не ждёт writer и имеет бюджет 50 мс
с progress handler. Ожидание файловой системы не является жёстко ограничиваемой
SQL-операцией. Наблюдение не меняет generation/cursors/ACK и состояния команд.
Его ошибка не заменяет результат исходной операции, в том числе после commit.
Результат и время окончания реальной операции фиксируются отдельно. Если срок
ожидания истёк уже при диагностическом чтении, возвращается исход операции,
завершившейся до своего deadline. Слишком поздняя реальная запись по-прежнему
даёт timeout. Executor не освобождается, пока чтение фактически не закончилось;
для client/source с обычным max_waiters=0 один следующий caller может дождаться
наблюдения в прежнем общем бюджете. Второго executor или неограниченной очереди нет.

Обёртка содержит `state`, `age_seconds`, `snapshot`. State: available, unavailable,
unsupported, not_observed либо closed. После ошибки сохраняется последний успешный
snapshot с настоящим возрастом, а state становится unavailable. Возраст растёт и
после последнего heartbeat в manager; остановившийся child не выдаёт старую сводку
за свежую. Старше 30 секунд doctor показывает warning journal_stale. Простой
владельца без storage-операций тоже увеличивает возраст; это не доказательство hang.

Из приложения можно читать `client.journal_status`; на hub и SourceRunner есть
такое же свойство. Чтение только кэша потокобезопасно и не обращается к SQLite/сети.
После последней операции до следующего обновления числа могут отставать. Для
финального состояния остановленной БД используйте отдельный режим ниже.
Пользовательский store может добавить `journal_stats() -> JournalStats`; при
отсутствии метода сводка unsupported, остальное исполнение сохраняет прежний контракт.
DTO импортируется из `remote_watch.commands.journal_stats`.

## Остановленная БД

Отдельно и явно можно исследовать локальный hub, клиентский журнал или журнал
источника. Остановите владельца выбранной БД или используйте его проверенную
копию после остановки. Для **работающего** gateway используйте server --online.

```powershell
& $py -m remote_watch.diagnostics.gateway_doctor --mode journal --journal C:\Work\RemoteWatch\data\commands\hub.sqlite --json --report .\hub-journal.local.json
```

Для клиента подставьте фактический SQLite из конфига приложения. Source-файл
можно выбрать так же. В этом режиме `--config` и `--online` не принимаются.
Runtime open/recovery/migration не вызываются, process/provider locks не создаются.
SQLite открывается `mode=ro&immutable=1`, без создания нового файла и sidecar.
При наличии `-journal`, `-wal` или `-shm` проверка отказывает, ничего не чинит и
не удаляет. Не удаляйте эти файлы ради прохождения doctor — сначала разберитесь
с владельцем/резервной копией. UNC/сетевые SQLite не поддерживаются.

Immutable не является согласованным способом наблюдать одновременно изменяемый
файл. Он выбран для **остановленной** БД и отсутствия побочных файлов/recovery.
Ошибка доступа, неизвестная схема, незавершённый journal или SQL-бюджет дают
фиксированный journal_read_failed без путей, SQL и исключений в отчёте.

Командные схемы 1 и 2 читаются без изменения файла. Source хранит только схему 1
и не сохраняет seen_limit/настроенный page limit: offline эти пределы равны null,
capacity=unknown, а journal_limits_unknown — skipped. Значения по умолчанию не
выдаются за настройки старого процесса. У работающего владельца пределы известны.

SQL выбирает не более 100001 команд/операций аудита, 1025 потоков и 10001 replay-ID;
превышение поддерживаемой границы отвергается. Содержимое запросов/результатов не
декодируется и не возвращается; для объёма используются только SQL length/SUM.
Для запуска не нужны bot credentials и не отправляются уведомления или команды.
