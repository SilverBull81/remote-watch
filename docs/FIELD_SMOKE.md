## Что проверяет команда

`python -m remote_watch.field_smoke` проверяет путь обычный logger → RemoteWatcher →
очереди/retry → Telegram/ntfy. Команда появилась в 0.2.0.dev1 как инструмент полевой
проверки возможностей 0.1. Она запускается только явно и не входит в обычные тесты.
Реальные credentials читаются из того же локального файла, что у [smoke](SMOKE.md).

Оба канала работают в одном runtime независимо. Периодически отправляется одно
контрольное сообщение каждому выбранному провайдеру; два дополнительных сообщения
должны остаться только локально. Циклически проверяются четыре случая:

1. ERROR, кириллица и emoji, выбор получателей по теме и метке.
2. INFO с `notify=True`.
3. Синтетическое исключение: `FIELD_TEST_SECRET` заменяется на `[удалено]` в удалённом
   тексте; исходная тестовая строка остаётся в локальном журнале.
4. Длинный текст с усечением. Номер сообщения стоит в начале и должен сохраниться.

В каждом удалённом сообщении есть `run=... seq=...`, а стандартный renderer добавляет
service/environment/region/host/instance, event/session/delivery IDs и время UTC.
Повтор доставки сохраняет delivery ID и может дать второе сообщение на телефоне.

Проверка не заменяет offline-тесты переполнения, искусственных ошибок и всех комбинаций
конфигурации. Она собирает полевые свидетельства доступности и доставки; не выключает
сеть, не меняет firewall и не управляет телефоном автоматически.

## Установка на серверах

В окружении сервера должна быть новая ревизия пакета с extras `telegram,ntfy`.
При установке из приватного GitHub используйте собственный URL и конкретную ревизию,
доступную на сервере; пример для уже настроенного SSH-доступа:

```sh
python -m pip install "remote-watch[telegram,ntfy] @ git+ssh://git@github.com/OWNER/REPOSITORY.git@REVISION"
python -m remote_watch.field_smoke --help
```

OWNER/REPOSITORY/REVISION — заменяемые значения. На всех трёх серверах используйте
одну ревизию. Инструмент сам запишет версию пакета, Python и название ОС в отчёт.
Цель совместимости — Python 3.10+; фактический запуск на Linux/минимальном Python
нужно подтвердить результатами с этих машин.

Сначала выполните оба коротких smoke. Локальный файл credentials не отправляется
в GitHub и не переносится между серверами самим пакетом. Для ntfy на текущем бесплатном
аккаунте без резервирования темы используйте только синтетические данные сценария;
проверка доставки не означает наличия закрытого ACL.

## Запуск на трёх серверах

Сначала можно пройти все четыре случая за четыре минуты:

```sh
python -m remote_watch.field_smoke both --region ru --host server-ru --instance-id ru-01 --duration 240 --interval 60 --output runs/field-ru-quick.jsonl
```

Для суточного наблюдения, по одной команде в окружении каждого сервера:

```sh
python -m remote_watch.field_smoke both --region ru --host server-ru --instance-id ru-01 --output runs/field-ru-day1.jsonl
python -m remote_watch.field_smoke both --region region-2 --host server-2 --instance-id server-02 --output runs/field-server2-day1.jsonl
python -m remote_watch.field_smoke both --region region-3 --host server-3 --instance-id server-03 --output runs/field-server3-day1.jsonl
```

Замените region/host/instance-id своими явными обозначениями. По умолчанию длительность
86400 секунд, интервал 900 секунд: около 96 сообщений на каждый канал от каждого сервера.
Номера разных запусков различаются по `run`. `telegram` либо `ntfy` вместо `both`
выбирает один канал. `--credentials` задаёт иной путь к локальному файлу.

Каждый запуск требует нового пути `.jsonl`; существующий отчёт не перезаписывается.
Без `--output` создаётся уникальный файл в `runs/`, путь печатается при запуске.
Рядом записывается `.log` с ротацией: порог 1 MiB, два предыдущих файла. Строка с длинным
текстом может превысить порог ротации, как в стандартном logging.
Расписание ограничено семью сутками и 1000 контрольными сообщениями; интервал не меньше
секунды. После паузы процесса пропущенные интервалы не отправляются залпом.

Команда работает в переднем плане. Для суток используйте уже принятый на сервере
способ сохранения сессии/процесса после отключения SSH. Ctrl+C завершает runtime и
записывает итог. Аварийное завершение или принудительное убийство процесса могут
оставить отчёт без summary; такой запуск не считается штатно завершённым.

## План наблюдений на телефоне

| Период | Действие | Что зафиксировать |
| --- | --- | --- |
| Первые 15 минут | Телефон активен, Wi-Fi | Наличие обоих каналов и различимых отправителей |
| Следующие 2 часа | Заблокировать экран, не открывать приложения | Какие уведомления пришли сразу, какие появились после разблокировки |
| Следующий час | Перейти на мобильную сеть | Пропуски, задержки и изменение порядка |
| Следующие 30 минут | Отключить сеть телефона, затем включить | Догрузку сообщений, дубликаты, задержки после восстановления |
| Далее до утра | Оставить телефон в обычном режиме, включая длительный простой | Доставку при фоновых ограничениях конкретного Android |
| В конце | Открыть приложения, перезапустить их и сопоставить номера | Отложенные сообщения и окончательные пропуски |

Проверку недоступности **сети сервера** проводите отдельно, сохранив доступ к SSH.
Команда имеет по три попытки, TTL 120 секунд и максимум 16 незавершённых доставок
на провайдера. Длительная недоступность может закончиться потерей сообщения;
восстановление сети не перечитывает старый локальный журнал. Новые номера должны
начать приходить, а здоровый соседний канал должен продолжать работу.

Время серверов и телефона должно быть синхронизировано. Запишите модель/версию Android,
версию приложений, режим энергосбережения, ограничения фоновой работы и время смены сети.
Для ручной таблицы достаточно колонок:

```text
run_id,seq,provider,region,host,received_utc,phone_state,network,duplicate,notes
```

Наблюдение на экране не нужно выдавать за точное время прихода пакета на устройство.
Если телефон проверен только утром, запишите этот факт вместо придуманной задержки.
Приемлемую задержку определите по своим эксплуатационным требованиям до оценки результата.

## Как читать отчёт

JSONL содержит строки `run`, `sample`, `attempt`, `summary`. Каждая строка отдельно
дописывается и сбрасывается в файл, поэтому отчёт можно читать во время работы.

- `run`: среда, отправитель, общий идентификатор и параметры расписания.
- `sample`: номер, тип проверки, время подготовки, ожидаемое одно уведомление на канал.
- `attempt`: канал, номер образца, event/delivery ID, номер попытки, безопасный статус,
  машинная причина и продолжительность. Токены, chat/topic, URL и исходные ответы не записываются.
- `summary`: число образцов, счётчики по каналам, состояние runtime, потери диагностики
  и признаки ошибки/прерывания. `provider_acceptance_complete` проверяет приём сервисами;
  `phone_display_verified` всегда false — получение на телефоне сверяет человек.

Код 0 означает, что все подготовленные контрольные сообщения приняты обоими выбранными
сервисами и очистка прошла без отмеченных ошибок. Это не гарантия отсутствия дубликатов
или показа на Android. Код 1 — неполная доставка/ошибка, 2 — ошибка настройки,
130 — прерывание. Если передача зависла или истёк TTL, смотрите retries, unknown_attempts,
expired, exhausted, overflow и shutdown-счётчики отдельно для каждого канала.

Попытки накапливаются в ограниченном буфере 1024 записей; локальный отчёт записывает
основной поток. При потере диагностических записей `diagnostic_drops` ненулевой,
и полный успех не объявляется. Файл local logging содержит только синтетический текст
этого запуска; реальные рабочие журналы приложение не читает.
