# Команды из Telegram и закрытых топиков ntfy

Version 1.0.6

Автор: Sergey Fundobny (silverbull@mail.ru) + GPT-6

Дата и время последнего изменения: 261006-103703

В 0.3.5.dev1 реализован путь «сообщение → командный gateway → конкретный запуск
приложения → пользовательский callback → ответ». Telegram и ntfy используют общий
контур исполнения и разные правила удостоверения отправителя.
02.10.2026 владелец подтвердил Telegram smoke через LV/RU с одним и двумя
тестовыми приложениями. Live-проверка команд закрытого ntfy отложена на
неопределённый срок. Локальные тесты сами по себе не подтверждают доступность
провайдера с конкретной VM. Ответ отправляет командный gateway в исходный чат;
запуск отдельного outbound gateway для ответа на команду не требуется.

## Готовность и диагностика в 0.3.6.dev1

В 0.4.1.dev2 диагностика дополнена: синтаксические ошибки JSON сообщают причину,
строку и столбец без фрагмента файла; ошибки структуры показывают обязательное
поле либо раздел с неизвестными ключами. CLI поддерживает `--version` без конфига
и добавляет версию к сообщению об исключении. В старой 0.3.5.dev2 ошибка JSON
могла выглядеть просто как `code=operation_failed field=config`.

Пример новой диагностики:

```text
Ошибка command gateway: code=config_json field=config. Лишняя запятая перед ] или }. Уберите запятую после последнего элемента. Строка 110, столбец 3.
```

Координаты относятся к закрывающей скобке, у которой parser обнаружил проблему:
запятая может находиться на предыдущей строке. В JSON нельзя оставлять запятую
после последнего элемента объекта или списка. Для путей Windows используйте
`C:/Work/RemoteWatch/data` либо `C:\\Work\\RemoteWatch\\data`.
Повторные ключи, NaN/Infinity, неверная кодировка и лишний текст после JSON
также получают отдельное пояснение. Номера строки/столбца печатаются только там,
где parser их предоставляет; исходная строка с возможными токенами не выводится.

Первичная проверка на сервере:

```powershell
C:\Work\RemoteWatch\.venv\Scripts\python.exe -m pip show remote-watch
C:\Work\RemoteWatch\.venv\Scripts\python.exe -m remote_watch.gateway.commands --config C:\Work\RemoteWatch\command_gateway.json --check-config
```

После обновления до 0.4.1.dev2 доступна короткая проверка версии:
`python -m remote_watch.gateway.commands --version` в том же venv.
`--check-config` не запускает сервер, не отправляет сообщения и не меняет журналы.

| Новый code | Действие |
| --- | --- |
| config_missing | Добавить обязательное поле, указанное в field |
| config_unknown | Сверить ключи раздела с шаблоном; неизвестные названия намеренно не печатаются |
| config_object / config_list | Проверить `{...}` / непустой `[...]` и допустимый размер списка |
| address_in_use / address_unavailable | Проверить прежний процесс, разные порты и локальный адрес --host |
| tls_pair / tls_invalid | Указать вместе --cert/--key и проверить PEM; за Caddy оставить loopback HTTP |
| permission_denied / file_missing | Проверить доступ к файлам/каталогам; CLI-пути TLS относительны cwd |
| dependency_missing | Установить extra commands в используемый venv |
| command_conflict | Проверить второго владельца и соответствие постоянного журнала; не удалять locks/SQLite |
| command_capacity / command_busy / command_unavailable | Проверить пределы/доступность журнала и предыдущий status/summary |

При неизвестном сбое выводится только категория встроенного исключения, например
KeyError, и версия пакета. Произвольные имена классов, `str(error)`, traceback,
provider payload и приватные пути не раскрываются. `field=startup` охватывает
создание, запуск и дальнейший цикл сервера; более точная причина берётся из code.
Подсказка `command_conflict` не утверждает, что второй процесс точно найден:
возможен также конфликт владельца/поколения сохранённых данных.

`source_id` — постоянное локальное имя источника, например `telegram-loader`,
а не числовой Telegram actor/chat ID. Для разных источников нужны разные имена.
Если добавляется второй bot, сохраните имя уже работающего источника и задайте
новое имя добавленному. Если bot один и общий для нескольких приложений, оставьте
один source с нужными правилами access: переименование копии не разрешает второго
reader того же bot. Не меняйте source_id существующего источника только ради
обхода проверки постоянного журнала.

После открытия listener командный CLI печатает `command_gateway_status` и затем
повторяет его только при изменении ready/reason/fatal. Например:

```json
{"kind": "command_gateway_status", "ready": false, "reason": "time_unavailable", "fatal": false}
```

Это означает, что сервер запущен, но доверенного времени для новых команд нет.
Loop обновления продолжает работать; после пригодного показания TimeAPI состояние
становится `ready=true`, `reason=null` без смены epoch или перезапуска журналов.
На часы VM сервер не переключается. Уже принятые сроки не продлеваются.
Счётчики источника могут хранить код прежней ошибки: это не история переходов readiness.

`CommandGateway.stats()` теперь включает ready/reason/fatal, вложенное состояние
hub (maintenance_running/time_ready/ready/reason/fatal) и прежние счётчики sources.
Это локальная проверка на loop владельца, не новый публичный HTTP endpoint.
Она не открывает SQLite, не обновляет UTC и не проверяет доставку на телефон.
Готовность не обещает свободный слот хранения или доступность провайдера
в момент следующего запроса. Неожиданные возврат, исключение и отмена критической
задачи видны как отказ, а штатная отмена при close не становится новой аварией.

| reason | Значение и действие |
| --- | --- |
| not_started / closed | Компонент ещё не запущен или уже закрыт |
| time_unavailable | Нет пригодного UTC; проверить TimeAPI, дождаться успешного обновления |
| storage_unavailable / storage_capacity | Обслуживание журнала получило отказ/переполнение; проверить состояние хранения |
| maintenance_failed | Неожиданно завершилась задача обслуживания hub; новые обращения к нему закрыты |
| source_stopped | Остановился цикл чтения или ответов источника |

Временная занятость SQLite (`busy`) не объявляется отказом; после успешного sweep
код ошибки хранения снимается. Фатальный отказ обслуживания/источника приводит
к закрытию ресурсов и ненулевому завершению CLI. Автоматического restart в 0.3.6 нет.
Перед завершением выводится состояние отказа; итоговый gateway_summary содержит
счётчики и закрытое состояние. Исключения фоновых задач извлекаются без печати
их исходного текста. Возможный callback не запускается повторно из-за диагностики.

Ошибки настроек gateway и command smoke теперь дают фиксированный code,
безопасный field с индексом и короткую русскую подсказку. Например:

```text
Ошибка command gateway: code=duplicate_principal_token field=principals[1].token. У каждого приложения должен быть свой командный токен.
```

| code | Что исправить |
| --- | --- |
| duplicate_principal_token | Разные командные токены для разных principals |
| duplicate_principal_name / duplicate_identity | Однозначные имена и владение Identity |
| unknown_target / unassigned_target | Ссылки на targets и назначение владельца каждой цели |
| duplicate_source / duplicate_provider | Единственный reader для каждого bot/topic |
| source_acl | Формат Telegram actor/chat или соответствие закрытому ntfy topic |
| credential_source / credential_environment / credential_value | Источник, имя переменной либо формат/наличие секрета |
| config_read / config_json / config_size / config_schema | Доступность, JSON, предел 1 MiB или schema_version=1 |
| ca_read / ca_invalid | Доступность файла CA и корректный PEM |
| endpoint_invalid | Синтаксис HTTPS-origin без credentials, query и пути операции |
| config_value | Остальные типы, пределы или связи указанного раздела |

`--check-config` не читает значения переменных окружения: одинаковое имя token_env
у двух principals выявляется сразу, одинаковые значения разных переменных —
при настоящей загрузке. Проверка синтаксиса endpoint не определяет, на том ли
порту работает Caddy. Числовой actor_id может быть корректным по форме, но чужим.
Для этих случаев по-прежнему нужны отдельная сетевая проверка и явный smoke.
Формат JSON и командный wire не изменились; старые конфиги остаются пригодны.

## Сообщение и адрес приложения

С 0.4.1.dev7 Telegram поддерживает `Help` без учёта регистра, `/help`, `/status`
и другие `/имя` зарегистрированных команд без alias, если для данного actor/chat
**в конфигурации разрешена ровно одна Identity**. В отдельном чате приложения:

```text
Help
/status
/resume_load
/suspend_load
```

Справка начинается строкой `Allowed Bot Commands:`, затем каждая разрешённая
команда идёт с новой строки с префиксом `-> `. С dev9 первой показывается встроенная
`-> /help`, даже если приложение не объявляло callback help. Перечень учитывает scopes и регистрацию приложения;
неразрешённые имена не показываются. Большая справка отправляется двумя ограниченными
сообщениями без усечения списка. Это попытки отправки после постоянного решения
источника; если ответ потерялся, справку можно запросить новым сообщением.

При нескольких настроенных целях требуется `/rw alias команда`, даже если сейчас
доступна только одна. Неявной рассылки и автоматического выбора единственного живого
instance нет. При одной недоступной цели приходит отказ, без смены адреса.
Actor/chat ACL, scopes, свежесть и точная привязка к исходной сессии остаются обязательными.
Повтор сохранённого события не выбирает новую сессию после перезапуска приложения.

Telegram-адаптер принимает `/command@имя_бота` только при совпадении с username,
проверенным через getMe; чужой суффикс игнорируется. Исходные сообщения людей
проверяются по тем же правилам, что и `/rw`: пересылки, правки, анонимные отправители
и сообщения ботов не дают права на команду. Обрабатываются только сообщения,
которые провайдер передал боту. `/help` — служебная справка без аргументов;
пользовательский callback с именем help остаётся доступен через `/rw alias help`.
Регистр пользовательских имён команд автоматически не меняется.

В собственном Python-подключении Telegram передайте `short_commands=True` в
CommandSourceRunner. JSON command gateway включает это по типу Telegram-настроек.
ntfy сохраняет явный `/rw` для команд приложения; служебная `/help` также доступна.
При нескольких настроенных разрешённых целях `/help` предлагает выбрать приложение,
не ориентируясь на число живых экземпляров. Требования закрытого топика не меняются.
Прежний синтаксис также полностью поддерживается:

```text
/rw
/rw loader-ru
/rw loader-ru status
/rw loader-ru suspend_load
/rw loader-ru resume_load
/rw loader-ru custom_command key="значение с пробелами"
```

`/rw` показывает только разрешённые адреса, `/rw адрес` — разрешённые команды
живого приложения. Адрес однозначно связан со всеми пятью полями Identity.
Угадывание адреса по имени чата, выбор «любого подходящего instance» и broadcast
не поддерживаются. Имена `status`, `check_load`, `resume_load`, `suspend_load` —
только пример регистрации в приложении, а не обязательные встроенные callbacks.

С **0.4.1.dev9** встроенные сообщения в мессенджере — на английском.
Ответ на `/rw` описывает настроенные разрешённые приложения, а не обещает,
что все они сейчас подключены:

```text
Configured applications:
-> loader-ru
-> loader-lv
Help: /rw app_name or /help
```

Ответ на `/rw loader-ru` содержит то же меню, что `/help` в однозначном чате,
и отдельную подсказку полного вызова:

```text
Allowed Bot Commands:
-> /help
-> /status
-> /resume_load
Usage: /rw loader-ru command [arg_name=value]
```

Имена команд в примере условные; неразрешённые scopes не раскрываются. При наличии
пользовательского callback help он по-прежнему вызывается через `/rw loader-ru help`;
короткая `/help` показывает справку и не исполняет callback. В меню help не дублируется.
Справка и краткие отказы не зависят от режима результата ниже.

Имя команды: `[a-z][a-z0-9_]{0,63}`. Аргументы — до 32 пар `имя=строка`, общий
размер проверяет CommandRequest; позиционные аргументы и повтор ключа запрещены.
Разбор кавычек не исполняет shell/Python. Команды со строковыми аргументами требуют
явного CommandSpec и валидатора приложения, см. [COMMANDS.md](COMMANDS.md).

Команда изменения состояния отправляется одним сообщением. Hub сверяет время
сообщения провайдера с доверенным интервалом TimeAPI и оставляет только остаток
срока, исходно не более 120 секунд. Допуск расхождения часов outbound relay
к командам не применяется. Часы Telegram/ntfy и выбранный HTTPS-источник UTC входят
в доверенную часть схемы; чтение времени по HTTPS само по себе не доказывает
точность серверных часов. При отсутствии пригодного времени команды отклоняются.

По умолчанию ответ содержит полную Identity, имя команды, command_id, session_id и исход.
Одно сообщение ответа ограничено 3800 байтами UTF-8; усечение результата отмечено явно.
Короткая справка при необходимости разбивается по границам строк. Нет Markdown/HTML
от провайдера. Возврат `None` означает «обработчик завершился», а не «загрузка
окончена». UNKNOWN не разрешает автоматический повтор callback.

## Отображение ответов команд на телефоне

С **0.4.1.dev9** отдельная настройка `command_display_mode` управляет ответами
Telegram и закрытого ntfy. Она не связана с `display_mode` outbound-уведомлений.

| Режим | Ответ команды |
| --- | --- |
| full | Прежняя полная шапка: Identity, команда, ID, сессия, исход и текст |
| compact | Все пять полей источника компактной строкой, имя команды, исход и текст; без ID |
| text | Текст успешного callback без шапки; при отказе/UNKNOWN — явный исход и причина |

При пустом успешном ответе библиотека сообщает `Handler completed.`. Это означает
завершение обработчика, а не завершение фоновой задачи приложения. Например,
UNKNOWN/timeout в text выглядит как `Command outcome is unknown (timeout).`. Сам текст callback
не переводится и не подменяется. Усечённый ответ помечается `[response truncated]`.
В text источник намеренно не виден; для общего чата нескольких экземпляров подходит compact.

Предпочтительный способ — поле в **клиентском командном JSON**:

```json
"command_display_mode": "compact"
```

Разместите его рядом с endpoint/identity/state_file и перезапустите приложение.
`load_command_client()` передаёт настройку при регистрации. В Python задайте
`CommandRegistration(..., command_display_mode="compact")` перед созданием CommandClient.
В шаблоне [command_client.example.json](examples/command_client.example.json) значение
null оставляет настройку источника gateway. Для возвращения к ней удалите поле либо задайте null.
Изменение файла само по себе не меняет уже запущенный объект.

На gateway резервный режим задаётся у источника, **вне provider settings**:

```json
{
  "source_id": "telegram",
  "provider": "telegram",
  "command_display_mode": "full"
}
```

Это фрагмент существующего элемента sources, а не полный конфиг. Если поле
отсутствует, используется full. Явный клиентский режим имеет приоритет и сохраняется
вместе с исходной командой до исполнения; поздний ответ не берёт настройку новой
регистрации. Источник без выбранного клиентом режима использует свой серверный default.
Меню, отказы до исполнения и справка уже краткие и не получают техническую шапку.

Один раз обновите **command gateway и клиентов** до dev9. В дальнейшем смена режима
в клиентском конфиге требует только перезапуска приложения. Caddy и notification
gateway к этой настройке отношения не имеют. JSON-конфиги сохраняют schema_version=1;
внутреннюю wire schema 2 библиотека выбирает сама только при явном клиентском режиме.
Старый gateway его отклонит; автоматического повтора без режима нет.
Существующие журналы сохраняйте: их старые записи и хеши остаются совместимыми.
Откат на старый пакет после записи новых сообщений wire 2 требует отдельной оценки;
удалять журналы или сбрасывать cursor для обхода ошибки нельзя.

Английский язык относится к встроенным текстам в мессенджере, включая ответы
command smoke и отметки усечения уведомлений. Документация, комментарии и локальные
CLI-подсказки остаются русскими. Тестовые уведомления с кириллицей продолжают проверять Unicode.

## Запуск на LV и клиенты на RU

Это отдельный процесс команд; работающий исходящий gateway 0.2 продолжает слушать
свой порт 8765. Один командный процесс обслуживает несколько приложений и чатов.
Каждому экземпляру нужны своя Identity, отдельный командный секрет и файл журнала.
Установить одинаковую версию пакета на gateway и клиентах:

```powershell
python -m pip install "remote-watch[commands,gateway,telegram,ntfy] @ git+https://github.com/SilverBull81/remote-watch.git"
```

Команда установит версию из удалённой ветки после публикации соответствующего
коммита. Для ещё не отправленных локальных изменений используйте установленный
wheel либо `python -m pip install ".[commands]"` из checkout.

Скопируйте подходящий шаблон:

- [command_gateway.telegram.example.json](examples/command_gateway.telegram.example.json)
  → `command_gateway.local.json` на LV;
- [command_gateway.ntfy.example.json](examples/command_gateway.ntfy.example.json)
  — вариант для ntfy; оба элемента `sources` можно объединить в одном серверном файле;
- [command_client.example.json](examples/command_client.example.json)
  → `command_client.local.json` на каждой клиентской VM.

Все значения секретов в шаблонах вымышлены и требуют замены. JSON допускает `token`
с самим токеном либо `token_env` с именем переменной, но не два действующих значения.
Командный секрет приложения — отдельная случайная ASCII-строка длиной 32–256 символов,
одинаковая в соответствующем principal gateway и его клиенте. Это не Telegram-токен
и не секрет outbound relay. Имена `*.local.json` игнорируются Git; ограничьте доступ
к этим файлам средствами ОС. Не отправляйте их содержимое в чат.

Для `one` и `two` задайте **разные** значения `principals[].token`.
У каждого клиента его `token` совпадает с токеном своего principal на LV.
Не копируйте Telegram-токен в эти поля: он находится только в
`sources[].settings.token`. Сгенерировать два секрета на своей машине:

```powershell
C:\Work\RemoteWatch\.venv\Scripts\python.exe -c "import secrets; print('one:', secrets.token_hex(32)); print('two:', secrets.token_hex(32))"
```

Полученные значения сохраняются в локальных настройках и не отправляются в чат.
Одинаковые токены у двух principals вызывали `operation_failed field=hub` в
0.3.5.dev2; с 0.3.6.dev1 выводится `duplicate_principal_token` с индексом principal.
Старый код обозначал общую проверку связей и пределов конфигурации,
а не обязательно ошибку одноимённого раздела. Раздел `hub` необязателен;
добавлять его для исправления повторяющихся токенов не нужно. Сам код может
означать и другие несогласованные настройки; он не устанавливает причину однозначно.

Пути `state_dir`, `state_file`, `ca_file` считаются относительно файла JSON.
Каждый перезапуск создаёт новую session/epoch, но продолжает использовать прежние
файлы журналов. Поля Identity клиента должны точно совпадать с записью targets
сервера. Для второго клиента из шаблона выберите instance_id `two`, его token,
owner_id и другой state_file. Приложение может находиться на той же VM, что и первое.

Проверка структуры не запускает сеть и не читает переменные окружения:

```powershell
C:\Work\RemoteWatch\.venv\Scripts\python.exe -m remote_watch.gateway.commands --config C:\Work\RemoteWatch\command_gateway.local.json --check-config
```

### Основной вариант для VM владельца: Caddy и два gateway

Уже работающий HTTPS-вход Caddy на LV, порт 8443, можно использовать и для
уведомлений, и для команд. На LV работают один Caddy и два Python-процесса:
исходящий gateway на `127.0.0.1:8765` и командный на `127.0.0.1:8766`.
Командный сервер запускается так:

```powershell
C:\Work\RemoteWatch\.venv\Scripts\python.exe -m remote_watch.gateway.commands --config C:\Work\RemoteWatch\command_gateway.local.json --host 127.0.0.1 --port 8766 --allow-loopback-http
```

Имя после `--config` должно совпадать с вашим файлом, например
`command_gateway.json`. `--cert` и `--key` здесь не нужны: TLS обслуживает Caddy.
В его существующем блоке сайта маршрут `/v1/commands/*` направляется на 8766,
остальные запросы — на 8765. Клиент RU использует `https://АДРЕС_LV:8443` и
`ca_file` с уже проверенным корневым сертификатом Caddy. Закрытые `.key` остаются
на LV; новый сертификат для второго gateway не нужен.

Пошаговые команды, Caddyfile, расположение `root.crt` и устранение ошибки
`localhost:2019 — connection refused`: [GATEWAY_TLS.md](GATEWAY_TLS.md).
`caddy validate` проверяет конфиг, `caddy run` запускает процесс,
`caddy reload` меняет настройки уже работающего процесса. Для smoke команд
исходящий gateway необязателен; он нужен для параллельной доставки уведомлений.

### Альтернатива: непосредственный TLS в Python без Caddy

Следующая команда предназначена для отдельного HTTPS-listener команд на 8766.
Для описанного выше общего входа Caddy она не нужна:


```powershell
C:\Work\RemoteWatch\.venv\Scripts\python.exe -m remote_watch.gateway.commands --config C:\Work\RemoteWatch\command_gateway.local.json --host 0.0.0.0 --port 8766 --cert C:\Work\RemoteWatch\secrets\gateway.crt --key C:\Work\RemoteWatch\secrets\gateway.key
```

Имена файлов сертификата здесь примерные: подставьте пути уже проверенной TLS-схемы.
В клиентском JSON укажите `https://АДРЕС_LV:8766` и `ca_file` с доверенным CA.
Имя/IP адреса должно входить в сертификат. Для этого варианта не нужен доступ
к физическому серверу компании: достаточно достигать порта VM по корпоративной сети.
С RU проверьте `Test-NetConnection АДРЕС_LV -Port 8766`; успешный тест 8765 ничего
не говорит о новом порте. Внешняя защита TCP/TLS и настройки Windows Firewall
описаны в [GATEWAY_TLS.md](GATEWAY_TLS.md). Не отключайте проверку сертификата.

Для отдельного теста на одном компьютере допустим явный
`--host 127.0.0.1 --allow-loopback-http` и HTTP endpoint клиента с
`"allow_loopback_http": true`. Между VM этот режим не разрешён.
При использовании Caddy этот флаг нужен лишь локальному Python-серверу:
клиент обращается к Caddy по HTTPS.
Сервер останавливается Ctrl+C или появлением файла, указанного через `--stop-file`;
до запуска этот файл должен отсутствовать. Отказ одного источника с постоянным
кодом завершает командный CLI, не затрагивая отдельный outbound gateway.

## Telegram

В `settings.token` укажите bot token. В `access` задайте строками настоящий
числовой `actor_id` пользователя Telegram и `conversation_id` чата. Display name,
username и текст сообщения не являются удостоверением отправителя. Не узнавайте
ID через пересылку приватных данных неизвестному стороннему bot.

`actor_id` отвечает на вопрос «кто отправил команду», `conversation_id` —
«в каком чате». В Telegram это `message.from.id` и `message.chat.id` соответственно.
В личном диалоге пользователя с ботом оба ID совпадают с числовым `chat_id`
этого диалога; в группе ID чата отрицательный, а ID пользователя положительный.
В JSON оба значения указываются строками. Gateway проверяет их совместно:
знания адреса приложения или участия в чате недостаточно для исполнения команды.
[Идентификаторы Telegram](https://core.telegram.org/api/bots/ids).

Если ID ещё неизвестны, остановите получатели этого bot, отправьте ему личное
сообщение и посмотрите только `message.from.id` и `message.chat.id` в его
`getUpdates` через собственный локальный инструмент Bot API. Не публикуйте полный
ответ и URL с токеном. После запуска gateway больше не вызывайте `getUpdates`
вручную и не оставляйте старый TelegramBot как второго получателя. Исходящая
отправка через тот же bot не является вторым потребителем updates.

На старте проверяются `getMe` и отсутствие webhook. Действующий webhook не удаляется
автоматически. Принимаются исходные текстовые сообщения людей из private/group/
supergroup; edited, forwarded, sender_chat, bot sender, channel/business и forum
topic отклоняются. В группе можно использовать `/rw@имя_этого_bot адрес команда`.
Для первого smoke удобнее личный чат; gateway всё равно сверяет оба ID.

ID Telegram после недели простоя может измениться не по порядку. Поэтому adapter
не применяет старый offset при старте. Он читает первое неподтверждённое событие,
сохраняет решение и только затем подтверждает именно этот ID. Потеря ACK допускает
повтор чтения, но не повторное назначение команды новому запуску приложения.
Семантика провайдера: [Telegram Bot API/getUpdates](https://core.telegram.org/bots/api#getupdates).

## ntfy: только закрытые командные топики

У исходного бесплатного незарезервированного топика уведомлений нет требуемой
границы доверия для управления приложением. Для команд нужны два отдельных закрытых
топика: `topic` для запросов и `reply_topic` для результатов. Публичные исходящие
уведомления можно оставить в их прежнем топике.

На ntfy.sh используйте возможность резервирования тем с запретом доступа остальным
пользователям; наличие аккаунта или случайное имя темы не заменяют ограничений.
Если аккаунт не позволяет закрыть две темы, нужен подходящий план или собственный
сервер. Актуальные условия проверяйте в своём аккаунте: пакет не создаёт подписку.

На собственном ntfy включите `auth-file`, `auth-default-access: deny-all` и HTTPS.
Пример прав для отдельных пользователей оператора и gateway:

```text
ntfy user add rw-owner
ntfy user add rw-gateway
ntfy access rw-owner rw-commands rw
ntfy access rw-owner rw-replies ro
ntfy access rw-gateway rw-commands ro
ntfy access rw-gateway rw-replies wo
ntfy token add rw-gateway
```

Полученный токен впишите в настройки gateway. Проверьте отсутствие иных разрешающих
ACL; анонимные чтение и запись должны быть запрещены. Эти команды выполняются
на собственном сервере ntfy, не на клиентских VM и не на ntfy.sh.
[Настройка ACL и токенов ntfy](https://docs.ntfy.sh/config/#access-control).

После проверки прав установите `private_topic_confirmed: true`. На старте adapter
дополнительно требует 401/403 при анонимном чтении обеих тем. Он не публикует пробную
команду для проверки записи: ответственность за write ACL остаётся у оператора.
Один только успешный `--check-config` не проверяет права в ntfy.

В сообщениях ntfy нет удостоверенного ID автора. `actor_id` в конфигурации — имя
общего субъекта «разрешённые писатели этого закрытого топика», а не доказательство
личности пользователя. Все, кому разрешена запись, получают настроенные для него
полномочия; читатели reply_topic видят ответы. Для разных полномочий создавайте
разные закрытые топики и источники. [Формат событий ntfy](https://docs.ntfy.sh/subscribe/api/#json-message-format).

В Android войдите в разрешённый аккаунт, подпишитесь на оба топика. В командном
топике отправляйте обычный текст `/rw one status` через строку публикации внизу
экрана; ответы появятся в reply_topic. Если строки нет: Settings → General →
Show message bar; в другой версии приложения используйте кнопку публикации.
[Публикация из Android](https://docs.ntfy.sh/subscribe/phone/#publishing-messages).
HTTP-кнопки с вложенными секретами в этой версии не создаются.

## Конечный smoke и подключение приложения

На RU после запуска gateway:

```powershell
python -m remote_watch.diagnostics.command_smoke --config C:\Work\RemoteWatch\command_client.local.json --duration 300 --report C:\Work\RemoteWatch\command-smoke.json
```

После строки «Smoke готов» отправьте с телефона по очереди, дожидаясь каждого ответа:

```text
/rw one status
/rw one suspend_load
/rw one status
/rw one resume_load
```

Smoke изменяет только собственный `threading.Event`, не управляет реальной загрузкой
или торговлей. Успех — `sequence_verified: true` и exit code 0 по окончании срока.
Отчёт хранит последние 64 наблюдения без токенов, endpoint, ID чатов и аргументов.
Показ результата на телефоне подтверждается вручную; число callbacks его не доказывает.
Ctrl+C завершает раньше с кодом 130 и сохраняет доступный отчёт.

Повторите с двумя одновременно запущенными smoke и адресами one/two. У второго
должны быть другие Identity/token/owner_id/state_file/report. Проверьте, что suspend
первого не меняет status второго; затем выполните полную последовательность для
второго. Проверьте оба провайдера отдельно. Для реального приложения передайте
его CommandRegistry в WatcherConfig и тот же реестр в
`load_command_client(path, registry)`, затем клиент — в `RemoteWatcher(command_client=...)`.
Словарь и partial остаются допустимыми; async callbacks требуют `astart`.
Подробности: [COMMAND_EXECUTION.md](COMMAND_EXECUTION.md).

## Хранение, пределы и восстановление

`commands.source` зависит только от протокола провайдера. Конкретные adapters
создаёт `gateway.command_service`. Импорт не открывает сеть; extra commands
требуется при запуске HTTP. Публичных HTTP endpoint для подачи source actor/chat нет.

Один `state_dir` принадлежит одному процессу. Блокировка ОС берётся до открытия
hub с новым поколением; отдельные блокировки защищают источники. Это локальная
защита, а не распределённый выбор лидера: не запускайте такой же bot/topic
из другой директории или с другой VM. HA не реализован.

До вызова hub сохраняются исходное событие, выбранная Identity/session и command_id.
После постоянного решения hub сохраняется позиция провайдера. Повтор после сбоя
продолжает прежнее решение; появление нового запуска приложения не меняет адресата.
Один незавершённый запрос занимает не более 128 KiB JSON. Список уже виденных ID —
до 1000 записей по умолчанию; заполнение приостанавливает приём до безопасной очистки.
Граница удалённых дат сохраняется необратимо: откат UTC не разрешает старые события.
Журнал источника ограничен 2048 страницами SQLite; обычный новый файл — около 8 MiB.

Источник имеет две фоновые задачи: приём и ответы. За порцию допускается до 32 событий,
адаптеры читают первое сообщение; ответы обходятся порциями до 32 с перемещением
начала. HTTP: два соединения, 25 секунд на запрос, 5 секунд на соединение,
ответ до 256 KiB; stream-строка до 64 KiB. Redirects, cookies, сжатие и proxy из
окружения отключены. Retry-After/Telegram retry_after дают паузу до суток.
Остановка отменяет задачи, ограничивает ожидания и закрывает собственные ресурсы.

Результат хранится до подтверждённой отправки провайдеру. Если провайдер принял ответ,
но квитанция потерялась, на телефоне возможны два одинаковых ответа с одним command_id.
Повтор callback этим не вызывается. Справка и быстрый отказ отправляются одной
попыткой после фиксации решения; их потеря не удерживает исполнение приложения.

Сохраняйте весь state_dir и отдельные клиентские журналы. Не удаляйте отдельный
source-файл, не обнуляйте cursor и не восстанавливайте старую копию журналов как
способ «повторить команды». Несогласованные позиции останавливают источник.
`source_id`, owner_id и пути журналов должны оставаться постоянными: новое имя
источника создаёт новый поток учёта, а не переименовывает прежний журнал.
UNKNOWN и старые незавершённые исполнения разбираются явно по
[COMMAND_STORAGE.md](COMMAND_STORAGE.md), без автоматического повторного действия.
