# Команды из Telegram и закрытых топиков ntfy

Version 1.0.0

Автор: Sergey Fundobny (silverbull@mail.ru) + GPT-6

Дата и время последнего изменения: 261001-185629

В 0.3.5.dev1 реализован путь «сообщение → командный gateway → конкретный запуск
приложения → пользовательский callback → ответ». Telegram и ntfy используют общий
контур исполнения и разные правила удостоверения отправителя. Реальная проверка
с телефона остаётся отдельным шагом; локальные тесты не подтверждают доступность
провайдера с конкретной VM.

## Сообщение и адрес приложения

```text
/rw
/rw loader-ru
/rw loader-ru status
/rw loader-ru suspend_load
/rw loader-ru resume_load
/rw loader-ru custom_command key="значение с пробелами"
```

`/rw` показывает только разрешённые адреса, `/rw адрес` — разрешённые команды
живого приложения. Адрес однозначно связан со всеми пятью полями Identity.
Угадывание адреса по имени чата, выбор «любого подходящего instance» и broadcast
не поддерживаются. Имена `status`, `check_load`, `resume_load`, `suspend_load` —
только пример регистрации в приложении, а не обязательные встроенные callbacks.

Имя команды: `[a-z][a-z0-9_]{0,63}`. Аргументы — до 32 пар `имя=строка`, общий
размер проверяет CommandRequest; позиционные аргументы и повтор ключа запрещены.
Разбор кавычек не исполняет shell/Python. Команды со строковыми аргументами требуют
явного CommandSpec и валидатора приложения, см. [COMMANDS.md](COMMANDS.md).

Команда изменения состояния отправляется одним сообщением. Hub сверяет время
сообщения провайдера с доверенным интервалом TimeAPI и оставляет только остаток
срока, исходно не более 120 секунд. Допуск расхождения часов outbound relay
к командам не применяется. Часы Telegram/ntfy и выбранный HTTPS-источник UTC входят
в доверенную часть схемы; чтение времени по HTTPS само по себе не доказывает
точность серверных часов. При отсутствии пригодного времени команды отклоняются.

Ответ содержит полную Identity, имя команды, command_id, session_id и исход.
Один ответ ограничен 3800 байтами UTF-8; усечение отмечено явно. Нет Markdown/HTML
от провайдера. Возврат `None` означает «обработчик завершился», а не «загрузка
окончена». UNKNOWN не разрешает автоматический повтор callback.

## Запуск на LV и клиенты на RU

Это отдельный процесс команд; работающий исходящий gateway 0.2 продолжает слушать
свой порт 8765. Один командный процесс обслуживает несколько приложений и чатов.
Каждому экземпляру нужны своя Identity, отдельный командный секрет и файл журнала.
Установить одинаковую версию пакета на gateway и клиентах:

```powershell
python -m pip install "remote-watch[commands] @ git+https://github.com/SilverBull81/remote-watch.git"
```

Команда установит версию из удалённой ветки после публикации соответствующего
коммита. Для ещё не отправленных локальных изменений используйте установленный
wheel либо `python -m pip install ".[commands]"` из checkout.

Скопируйте подходящий шаблон:

- [command_gateway.telegram.example.json](examples/command_gateway.telegram.example.json)
  → `command_gateway.local.json` на LV;
- [command_gateway.ntfy.example.json](examples/command_gateway.ntfy.example.json)
  — вариант для ntfy; оба элемента `sources` можно объединить в одном серверном файле;
- [command_client.example.json](examples/command_client.example.json)
  → `command_client.local.json` на каждой клиентской VM.

Все значения секретов в шаблонах вымышлены и требуют замены. JSON допускает `token`
с самим токеном либо `token_env` с именем переменной, но не два действующих значения.
Командный секрет приложения — отдельная случайная ASCII-строка длиной 32–256 символов,
одинаковая в соответствующем principal gateway и его клиенте. Это не Telegram-токен
и не секрет outbound relay. Имена `*.local.json` игнорируются Git; ограничьте доступ
к этим файлам средствами ОС. Не отправляйте их содержимое в чат.

Пути `state_dir`, `state_file`, `ca_file` считаются относительно файла JSON.
Каждый перезапуск создаёт новую session/epoch, но продолжает использовать прежние
файлы журналов. Поля Identity клиента должны точно совпадать с записью targets
сервера. Для второго клиента из шаблона выберите instance_id `two`, его token,
owner_id и другой state_file. Приложение может находиться на той же VM, что и первое.

Проверка структуры не запускает сеть и не читает переменные окружения:

```powershell
python -m remote_watch.gateway.commands --config C:\Work\RemoteWatch\command_gateway.local.json --check-config
```

Сервер с непосредственным TLS, порт команд 8766:

```powershell
python -m remote_watch.gateway.commands --config C:\Work\RemoteWatch\command_gateway.local.json --host 0.0.0.0 --port 8766 --cert C:\Work\RemoteWatch\secrets\gateway.crt --key C:\Work\RemoteWatch\secrets\gateway.key
```

Имена файлов сертификата здесь примерные: подставьте пути уже проверенной TLS-схемы.
В клиентском JSON укажите `https://АДРЕС_LV:8766` и `ca_file` с доверенным CA.
Имя/IP адреса должно входить в сертификат. Для этого варианта не нужен доступ
к физическому серверу компании: достаточно достигать порта VM по корпоративной сети.
С RU проверьте `Test-NetConnection АДРЕС_LV -Port 8766`; успешный тест 8765 ничего
не говорит о новом порте. Внешняя защита TCP/TLS и настройки Windows Firewall
описаны в [GATEWAY_TLS.md](GATEWAY_TLS.md). Не отключайте проверку сертификата.

Для одного компьютера или TLS reverse proxy на этой же VM допустим явный
`--host 127.0.0.1 --allow-loopback-http`; клиенту при HTTP также нужен
`"allow_loopback_http": true`. Между VM этот режим не разрешён.
Сервер останавливается Ctrl+C или появлением файла, указанного через `--stop-file`;
до запуска этот файл должен отсутствовать. Отказ одного источника с постоянным
кодом завершает командный CLI, не затрагивая отдельный outbound gateway.

## Telegram

В `settings.token` укажите bot token. В `access` задайте строками настоящий
числовой `actor_id` пользователя Telegram и `conversation_id` чата. Display name,
username и текст сообщения не являются удостоверением отправителя. Не узнавайте
ID через пересылку приватных данных неизвестному стороннему bot.

Если ID ещё неизвестны, остановите получатели этого bot, отправьте ему личное
сообщение и посмотрите только `message.from.id` и `message.chat.id` в его
`getUpdates` через собственный локальный инструмент Bot API. Не публикуйте полный
ответ и URL с токеном. После запуска gateway больше не вызывайте `getUpdates`
вручную и не оставляйте старый TelegramBot как второго получателя. Исходящая
отправка через тот же bot не является вторым потребителем updates.

На старте проверяются `getMe` и отсутствие webhook. Действующий webhook не удаляется
автоматически. Принимаются исходные текстовые сообщения людей из private/group/
supergroup; edited, forwarded, sender_chat, bot sender, channel/business и forum
topic отклоняются. В группе можно использовать `/rw@имя_этого_bot адрес команда`.
Для первого smoke удобнее личный чат; gateway всё равно сверяет оба ID.

ID Telegram после недели простоя может измениться не по порядку. Поэтому adapter
не применяет старый offset при старте. Он читает первое неподтверждённое событие,
сохраняет решение и только затем подтверждает именно этот ID. Потеря ACK допускает
повтор чтения, но не повторное назначение команды новому запуску приложения.
Семантика провайдера: [Telegram Bot API/getUpdates](https://core.telegram.org/bots/api#getupdates).

## ntfy: только закрытые командные топики

У исходного бесплатного незарезервированного топика уведомлений нет требуемой
границы доверия для управления приложением. Для команд нужны два отдельных закрытых
топика: `topic` для запросов и `reply_topic` для результатов. Публичные исходящие
уведомления можно оставить в их прежнем топике.

На ntfy.sh используйте возможность резервирования тем с запретом доступа остальным
пользователям; наличие аккаунта или случайное имя темы не заменяют ограничений.
Если аккаунт не позволяет закрыть две темы, нужен подходящий план или собственный
сервер. Актуальные условия проверяйте в своём аккаунте: пакет не создаёт подписку.

На собственном ntfy включите `auth-file`, `auth-default-access: deny-all` и HTTPS.
Пример прав для отдельных пользователей оператора и gateway:

```text
ntfy user add rw-owner
ntfy user add rw-gateway
ntfy access rw-owner rw-commands rw
ntfy access rw-owner rw-replies ro
ntfy access rw-gateway rw-commands ro
ntfy access rw-gateway rw-replies wo
ntfy token add rw-gateway
```

Полученный токен впишите в настройки gateway. Проверьте отсутствие иных разрешающих
ACL; анонимные чтение и запись должны быть запрещены. Эти команды выполняются
на собственном сервере ntfy, не на клиентских VM и не на ntfy.sh.
[Настройка ACL и токенов ntfy](https://docs.ntfy.sh/config/#access-control).

После проверки прав установите `private_topic_confirmed: true`. На старте adapter
дополнительно требует 401/403 при анонимном чтении обеих тем. Он не публикует пробную
команду для проверки записи: ответственность за write ACL остаётся у оператора.
Один только успешный `--check-config` не проверяет права в ntfy.

В сообщениях ntfy нет удостоверенного ID автора. `actor_id` в конфигурации — имя
общего субъекта «разрешённые писатели этого закрытого топика», а не доказательство
личности пользователя. Все, кому разрешена запись, получают настроенные для него
полномочия; читатели reply_topic видят ответы. Для разных полномочий создавайте
разные закрытые топики и источники. [Формат событий ntfy](https://docs.ntfy.sh/subscribe/api/#json-message-format).

В Android войдите в разрешённый аккаунт, подпишитесь на оба топика. В командном
топике отправляйте обычный текст `/rw one status` через строку публикации внизу
экрана; ответы появятся в reply_topic. Если строки нет: Settings → General →
Show message bar; в другой версии приложения используйте кнопку публикации.
[Публикация из Android](https://docs.ntfy.sh/subscribe/phone/#publishing-messages).
HTTP-кнопки с вложенными секретами в этой версии не создаются.

## Конечный smoke и подключение приложения

На RU после запуска gateway:

```powershell
python -m remote_watch.diagnostics.command_smoke --config C:\Work\RemoteWatch\command_client.local.json --duration 300 --report C:\Work\RemoteWatch\command-smoke.json
```

После строки «Smoke готов» отправьте с телефона по очереди, дожидаясь каждого ответа:

```text
/rw one status
/rw one suspend_load
/rw one status
/rw one resume_load
```

Smoke изменяет только собственный `threading.Event`, не управляет реальной загрузкой
или торговлей. Успех — `sequence_verified: true` и exit code 0 по окончании срока.
Отчёт хранит последние 64 наблюдения без токенов, endpoint, ID чатов и аргументов.
Показ результата на телефоне подтверждается вручную; число callbacks его не доказывает.
Ctrl+C завершает раньше с кодом 130 и сохраняет доступный отчёт.

Повторите с двумя одновременно запущенными smoke и адресами one/two. У второго
должны быть другие Identity/token/owner_id/state_file/report. Проверьте, что suspend
первого не меняет status второго; затем выполните полную последовательность для
второго. Проверьте оба провайдера отдельно. Для реального приложения передайте
его CommandRegistry в WatcherConfig и тот же реестр в
`load_command_client(path, registry)`, затем клиент — в `RemoteWatcher(command_client=...)`.
Словарь и partial остаются допустимыми; async callbacks требуют `astart`.
Подробности: [COMMAND_EXECUTION.md](COMMAND_EXECUTION.md).

## Хранение, пределы и восстановление

`commands.source` зависит только от протокола провайдера. Конкретные adapters
создаёт `gateway.command_service`. Импорт не открывает сеть; extra commands
требуется при запуске HTTP. Публичных HTTP endpoint для подачи source actor/chat нет.

Один `state_dir` принадлежит одному процессу. Блокировка ОС берётся до открытия
hub с новым поколением; отдельные блокировки защищают источники. Это локальная
защита, а не распределённый выбор лидера: не запускайте такой же bot/topic
из другой директории или с другой VM. HA не реализован.

До вызова hub сохраняются исходное событие, выбранная Identity/session и command_id.
После постоянного решения hub сохраняется позиция провайдера. Повтор после сбоя
продолжает прежнее решение; появление нового запуска приложения не меняет адресата.
Один незавершённый запрос занимает не более 128 KiB JSON. Список уже виденных ID —
до 1000 записей по умолчанию; заполнение приостанавливает приём до безопасной очистки.
Граница удалённых дат сохраняется необратимо: откат UTC не разрешает старые события.
Журнал источника ограничен 2048 страницами SQLite; обычный новый файл — около 8 MiB.

Источник имеет две фоновые задачи: приём и ответы. За порцию допускается до 32 событий,
адаптеры читают первое сообщение; ответы обходятся порциями до 32 с перемещением
начала. HTTP: два соединения, 25 секунд на запрос, 5 секунд на соединение,
ответ до 256 KiB; stream-строка до 64 KiB. Redirects, cookies, сжатие и proxy из
окружения отключены. Retry-After/Telegram retry_after дают паузу до суток.
Остановка отменяет задачи, ограничивает ожидания и закрывает собственные ресурсы.

Результат хранится до подтверждённой отправки провайдеру. Если провайдер принял ответ,
но квитанция потерялась, на телефоне возможны два одинаковых ответа с одним command_id.
Повтор callback этим не вызывается. Справка и быстрый отказ отправляются одной
попыткой после фиксации решения; их потеря не удерживает исполнение приложения.

Сохраняйте весь state_dir и отдельные клиентские журналы. Не удаляйте отдельный
source-файл, не обнуляйте cursor и не восстанавливайте старую копию журналов как
способ «повторить команды». Несогласованные позиции останавливают источник.
`source_id`, owner_id и пути журналов должны оставаться постоянными: новое имя
источника создаёт новый поток учёта, а не переименовывает прежний журнал.
UNKNOWN и старые незавершённые исполнения разбираются явно по
[COMMAND_STORAGE.md](COMMAND_STORAGE.md), без автоматического повторного действия.
