## Повторные короткие проверки ntfy

Исходные данные прочитаны из каталога владельца C:\Work\runs; они не копируются
в репозиторий. Новые отчёты — field-home-recheck.jsonl/log и field-ru-recheck.jsonl/log.

| --- | --- | --- | --- | --- |
| field-home-recheck | Windows / Python 3.12.10 | 0.2.0.dev2 | 3 provider_accepted | 3 transient_failure / http_temporary |

В обоих случаях четыре образца за 240 секунд, шесть попыток, два повтора,
три подтверждения приёма и одно exhausted. Runtime закрылся штатно, diagnostic_drops=0;
нет переполнений, expiry, adapter_errors или close_failed. В локальных .log
длинная запись присутствует. Ответы на неё получены за 0.125–0.391 секунды.

Это **не повтор прежнего результата** permanent_failure/http_rejected:
теперь классификатор получил HTTP 408 либо 500–599. Точный HTTP-код отброшен
в [_common.http_failure](../src/remote_watch/adapters/_common.py), поэтому назвать
500, 502 или другую конкретную причину по этим файлам нельзя. Нет подтверждения
приёма последнего сообщения; проблему нельзя свести к показу уведомления Android.
HTTP-ошибка сама по себе также не доказывает отсутствие побочного действия на сервере.

Значение failed=false в summary означает отсутствие исключения сценария.
Полный успех определяется provider_acceptance_complete=false и кодом выхода 1,
а не полем failed в отдельности. Это различие стоит сделать заметнее в отчёте.

Исправление ASCII-экранирования в dev2 было установлено. Оно устранило найденное
разрастание JSON, но не доказало устранения всей проблемы long text. В dev3/dev4
алгоритм отправки ntfy не менялся. Повторять тот же четырёхминутный сценарий
на dev4 без улучшения диагностики сейчас малоинформативно; сутки пока отложены.

## Обязательная работа до завершения приёмки

### 1. Диагностика ntfy и воспроизведение long text — высокий приоритет

Текущие DeliveryResult и field report сохраняют лишь обобщённый reason_code.
Нужно передавать безопасные числовые сведения: фактический HTTP-статус, при наличии
проверенный числовой код ntfy, длину message в UTF-8 и длину отправленного JSON.
Не включать токены, topic, произвольные error/description, тело ответа или запрос.
Провести сведения через direct/relay и отчёт, согласовав изменение wire-контракта.
Обновление должно учитывать совместимость старого и нового клиента/сервера.

Затем нужен короткий диагностический сценарий длины: ASCII и кириллица/emoji,
несколько размеров около границы, результат каждой отдельной попытки. Число
отправок и паузы конечны; не запускать массовый перебор или суточную проверку.
Локальные tests должны проверять реальные байты запроса и сохранение безопасных
диагностических полей, включая отсутствие приватного текста в результатах.

Нынешний fake HTTP воспроизводит выбранные ограничения размера и всегда отвечает
успехом для допустимого тела. Он не воспроизводит реальный сервер ntfy или его
промежуточные компоненты. Опубликованная граница текста —
[4096 байт](https://docs.ntfy.sh/publish/#limitations); её соблюдение само по себе
не объясняет новый ответ 408/5xx. Снижение лимита вслепую не считать исправлением
причины. Завершение пункта: воспроизведён конкретный отказ, исправление проверено
регрессией, короткая проверка снова дала четыре подтверждения приёма и сообщения.

### 2. Явные ограничения уведомления для relay — средний приоритет

[RelayRequest](../src/remote_watch/relay.py) на отправителе принимает Notification
с пользовательскими SnapshotLimits, но from_bytes создаёт Notification со стандартными
ограничениями. [GatewayConfig](../src/remote_watch/gateway_config.py) не позволяет
настроить эти пределы, а документация relay описывает прежде всего 64 KiB всего запроса.

Локально воспроизведено без сети: message из 10 000 ASCII-символов,
message_max_bytes=12 000, event_max_bytes=20 000. Отправитель принимает RelayRequest
размером 10 704 байта, принимающая сторона выдаёт invalid relay request: её предел
message — 8192 байта. Независимые пределы сервера правильны; их нельзя доверять
полям удалённого клиента. Недостаёт явного договора и ранней понятной диагностики.

Для первого варианта предпочтительно зафиксировать стандартные пределы схемы v1,
проверять их до отправки и документировать отличие от увеличенных локальных лимитов.
Альтернатива — явные серверные SnapshotLimits с согласованной клиентской настройкой.
Добавить пограничные тесты и round-trip с изменёнными локальными пределами.
Заодно использовать один способ JSON-кодирования для проверки и реальной отправки:
сейчас RelayRequest считает UTF-8 без ASCII-экранирования, HttpSender отправляет
JSON с экранированием. Переполнение на стандартных пределах этим ревью не подтверждено;
это расхождение реализации, а не доказанная причина текущего сбоя ntfy.

### 3. Настоящий TLS в локальных тестах — средний приоритет

Сервер запрещает публичный plaintext, HTTP-слой классифицирует ошибки сертификата,
но сквозные gateway-тесты используют HTTP loopback. Добавить локальный HTTPS-сервер
с временным тестовым центром сертификации: доверенный сертификат проходит,
недоверенный, просроченный или с другим именем отклоняется, HTTP не подменяет HTTPS.
Проверить путь CLI --cert/--key. Нужны только локальные сертификаты и sockets;
домен, реальные токены, доступ к хосту VM и публичные порты не требуются.

### 4. Проверяемая матрица сред — средний приоритет

Объявлено Python >=3.10, но локально установлен только Python 3.12. Полный набор
не проверен на 3.10/Linux; полевые отчёты тоже относятся к Windows. Это работа
по совместимости библиотеки, которую можно выполнить без доступа к серверам владельца.
Нужны повторяемые проверки Windows/Linux, минимального Python, core без extras
и всех реализованных extras, wheel/sdist. В репозитории пока нет CI workflow;
часть проверок чистой установки выполнялась одноразовыми скриптами в build/.
Перенести необходимые проверки в поддерживаемые инструменты проекта и добавить
матрицу CI. Само добавление workflow не считать успешным выполнением матрицы.

## Желательные улучшения эксплуатации 0.2

  Добавить ограниченную локальную сводку при остановке и, при необходимости,

  безопасную категорию или поле ошибки. Добавить фиксированные коды этапа и
  известные имена полей без значений, путей с секретами и исходных исключений.
- Дополнить четыре разных alias сценарием «несколько principals → один alias»,
  включая конкуренцию, 429 и отсутствие смешения прав/результатов.
- Длительный field_smoke поддерживает прямые Telegram/ntfy; relay пока имеет
  одноразовый smoke и offline mixed tests. До полевой приёмки 0.2 добавить режим
  наблюдения «Telegram через relay + ntfy напрямую» с теми же отчётами.
- Подготовить воспроизводимый запуск/остановку/автозапуск Windows-процессов и
  конкретный пример внешних ограничений proxy. Нынешний минимальный Caddyfile
  показывает TLS-маршрут, но не реализует все требования защиты внешнего входа.
  Установка Windows-службы и настройка сети не входят в текущее ревью.

## Что уже есть и не требует новой реализации

0.1: logging/LoggerAdapter, неизменяемые события, маршрутизация, ограниченные
очереди/retry/TTL, lifecycle, RemoteWatcher и локальные handlers, Telegram/ntfy,
короткие smoke, сборка. Нерешённый long text не отменяет наличие этих компонентов,
но мешает считать приёмку ntfy завершённой.

0.2: relay-клиент/протокол, один gateway для нескольких приложений, точные
identity/alias-права, отдельные токены, ограничения приёма/частоты, одна попытка
провайдера, shutdown, JSON/Python-конфигурация, смешанный HTTP-сценарий.

Команды, Matrix, durable outbox, автоматический fallback и высокая доступность
остаются последующими этапами. Внедрение реального приложения отложено владельцем
до минимальных команд. Лицензия публичного распространения не требуется для
согласованного личного использования. Закрытый ntfy-topic — настройка доступа
провайдера; бесплатная незарезервированная тема не становится закрытой от gateway.

## Порядок следующей работы

1. Безопасная диагностика HTTP/ntfy и короткий диагностический сценарий длины.
2. Согласование пределов relay и его пограничные проверки.
3. Локальные HTTPS-тесты и поддерживаемая матрица сборки/установки.
4. Локальная диагностика gateway, общий alias и режим mixed field smoke.
5. После успешной короткой проверки — сутки ntfy; после готовности размещения — relay.
