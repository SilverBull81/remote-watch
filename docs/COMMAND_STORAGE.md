# Постоянный журнал команд: этап 0.3.2

Version 1.0.4

Автор: Sergey Fundobny (silverbull@mail.ru) + GPT-6

Дата и время последнего изменения: 261006-103703

## Реализовано в 0.3.0.dev2

CommandStore — типизированный синхронный протокол. SQLiteCommandStore реализует
его на стандартном sqlite3 без внешней БД: запросы, результаты, версии, позиции
источников, аудит, восстановление и очистка. Журнал может обслуживать hub либо
приложение; их файлы и владельцы раздельны. Callback внутри хранилища не вызывается.

Новые модули доступны через remote_watch.commands.storage и
remote_watch.commands.sqlite_store. Сетевых endpoints, executor и Telegram polling
пока нет. Не следует выдавать эти компоненты за готовое удалённое управление.

## Пример приёма свежей команды

```python
from pathlib import Path
from tempfile import TemporaryDirectory

from remote_watch import Identity
from remote_watch.commands.protocol import CommandRef, CommandRequest
from remote_watch.commands.storage import StoreRole
from remote_watch.commands.time import TimeSample, TrustedClock
from remote_watch.commands.sqlite_store import SQLiteCommandStore

epoch = "a" * 32  # В настоящем запуске: secrets.token_hex(16), новый при каждом старте.
identity = Identity(service="loader", environment="test", region="ru", host="vm", instance_id="one")
request = CommandRequest(
    ref=CommandRef(identity=identity, session_id="b" * 32, hub_epoch=epoch, command_id="c" * 32),
    source_id="telegram-main", source_event_id="10", actor_id="42", conversation_id="123", name="resume_load",
)
clock = TrustedClock(clock=lambda: 100)
clock.install(TimeSample(lower_utc=1000000, upper_utc=1000002, observed_at=100))
freshness = clock.check(999990, epoch)

with TemporaryDirectory() as directory:
    store = SQLiteCommandStore(Path(directory) / "hub.db", owner_id="main-hub",
                               generation=epoch, role=StoreRole.HUB, clock=lambda: 100)
    store.open()
    try:
        assert freshness.deadline is not None
        admitted = store.admit("telegram-main", 10, -1, request, freshness.deadline)
        assert admitted.inserted and admitted.cursor == 10
        repeated = store.admit("telegram-main", 10, -1, request, freshness.deadline)
        assert not repeated.inserted
    finally:
        store.close()
```

Пример исполняется тестами без сети. Подставной запрос здесь не означает реальной
проверки actor/chat — это обязанность будущего источника и hub. Deadline должен
быть получен из [проверки свежести](COMMAND_TIME.md) на hub или из коррелированного
ответа hub на клиенте, в той же области локальных монотонных часов, что и журнал.

## Позиции источника и атомарность

С 0.4.1.dev9 внутри исходного CommandRequest также может сохраняться выбранный
клиентом command_display_mode. Это wire schema 2, но не новая схема таблиц SQLite.
Режим фиксируется до SourcePending и не пересчитывается при восстановлении/доставке
результата. Старые записи без режима используют прежнюю schema 1 с неизменными
каноническими байтами и digest; результат и его квитанция не получают новых полей.
Существующие журналы не нужно удалять или пересоздавать. После сохранения wire 2
старый пакет не сможет прочитать такие записи; откат версии не является автоматическим.

stream — постоянное имя доверенного упорядоченного потока, не поле произвольного
пользовательского сообщения. position — целое от 0 до 2^63−1, возрастающее для
новых событий и неизменное при повторной доставке. Начальный cursor равен −1.
expected_cursor защищает от двух конкурирующих потребителей. Приём идёт по порядку;
нельзя перескочить необработанное событие или переименовать stream ради повтора.

admit одной транзакцией записывает команду либо фиксированное решение о пропуске/
отказе и продвигает cursor. Только возвращённую после commit позицию можно
подтвердить внешнему источнику. Переполнение и ошибка записи не продвигают cursor.
Повтор position <= cursor не создаёт команду, даже после очистки её payload.
Повтор сохранённой позиции с другим содержимым даёт StoreConflict.

command_id и пара source_id/source_event_id уникальны среди сохраняемых команд;
claim связан с полным запросом. При повторе сохраняются и позиция, и исходный ID.
На hub sequence записи может стать стабильной позицией доставки клиенту;
SQLite AUTOINCREMENT не переиспользует её после очистки. Клиент сохраняет свой
cursor перед подтверждением получения. Назначать повтору новый sequence запрещено.

Это контракт упорядоченного целочисленного потока, а не универсальный формат
provider cursor. Telegram update_id и его возможная смена последовательности
после длительного простоя требуют явного сопоставления в source этапа 0.3.5.
Нельзя молча сбрасывать сохранённый cursor. Если необходим новый поток, его
вводят отдельно после проверки свежести и завершения старого; прежняя защита
не удаляется. Курсоры Matrix другого формата относятся к отдельному будущему адаптеру.

## Переход к исполнению

transition сравнивает revision, проверяет полную ссылку на команду и применяет
advance_command под BEGIN IMMEDIATE. Два соединения с одной revision не могут
оба получить start_callback=True. Возвращаемое разрешение появляется только
после успешного commit. Ошибка commit, в том числе при фактически записанном
STARTED, не даёт разрешения на побочное действие.

На hub следующий шаг после STARTED — отправка grant; на клиенте — callback.
Флаг start_callback в общем типе используется как разрешение соответствующего
следующего шага, а не как предложение исполнять application callback на hub.
START требует grant_deadline: локальный срок после вычета round trip запроса.
Он дополнительно ограничивается сохранённым сроком команды; повтор не продлевает
его. Срок регистрации проверяется отдельно. После commit сроки проверяются снова;
будущий executor также обязан проверить их непосредственно перед вызовом.

Результат хранится до его подтверждения. acknowledge принимает точный результат,
а не один command_id; его повтор безопасен. COMPLETED означает завершение callback,
а не окончание загрузки или другой операции приложения. UNKNOWN не вызывает
автоматического повторения и не переписывается поздним противоречащим результатом.

## Аварийное восстановление

generation — новый случайный 128-битный hex-ID каждого запуска владельца.
Для hub он совпадает с hub_epoch, для приложения — с session_id. Повторно
использовать ID после перезапуска запрещено: локальные сроки старого процесса
не восстанавливаются. Несколько соединений одного работающего владельца могут
разделять generation; это не поддержка нескольких независимых активных hub.

При open нового поколения READY/CLAIMED становятся EXPIRED, STARTED — UNKNOWN.
Терминальные результаты сохраняются. Восстановление и смена поколения атомарны;
старые открытые handles после смены больше не изменяют журнал. Cursor остаётся.
Срок очистки консервативно отсчитывается заново; это продлевает хранение,
но никогда не продлевает разрешение выполнить команду.

Нельзя мгновенно отозвать уже выданное ограниченное разрешение у отключённого
клиента. Поэтому STARTED после аварии — UNKNOWN. Журнал гарантирует порядок
фиксации, но не exactly-once внешней операции. Восстановление из старого backup,
удаление БД или недостоверный fsync не входят в эту гарантию.

## Очистка и пределы

| StoreLimits | По умолчанию |
| --- | --- |
| records, все сохраняемые команды | 1024 |
| streams, постоянные позиции | 64 |
| audit, последние краткие операции | 4096 |
| payload_bytes, запросы плюс резервы результатов | 32 MiB |
| database_bytes, основной файл SQLite | 64 MiB |
| retention, минимум после изменения/ACK | 86400 с |
| lock_timeout, каждое ожидание блокировки | 1 с |

При приёме резервируется полный допустимый wire результата, 64 KiB, плюс размер
запроса. Это логическая ёмкость, не гарантия свободного места файловой системы.
Физическое ограничение SQLite контролируется max_page_count; ошибка полного диска
или I/O закрывает этот экземпляр для дальнейших операций. Текст SQLite, пути
и содержимое запросов наружу не передаются. Новое поколение может увеличить
лимиты; уменьшение или изменение лимитов соседним handle не допускается.

prune удаляет только терминальные записи с ACK, истёкшим retention и без
execution_active. UNKNOWN/timeout может означать всё ещё работающий callback:
его запись остаётся даже после ACK. release_execution разрешён только после
проверенного фактического окончания вызова/сверки с приложением; истечение TTL
не является таким доказательством. После этой отметки выдерживается retention.
При потере возможности сверки неопределённая попытка остаётся в журнале.

Активные записи и неподтверждённые результаты не вытесняются при переполнении.
Постоянные позиции streams не очищаются вместе с payload. Аудит ограничен отдельно
и содержит только код действия, ID команды и состояние, без actor, аргументов
или текста результата. Обрезка аудита не влияет на защиту от повторов.
pending возвращает также подтверждённые UNKNOWN с незавершённым исполнением.
Все страницы и порции очистки ограничены 1000 записями, по умолчанию 100.

## Владение ресурсами

Конструктор не открывает файлы; open/close явные. После close нужен новый объект.
Каждое соединение защищено ограниченной блокировкой; SQLite-транзакции также
имеют ограниченное ожидание. Нет собственных потоков, очередей или фоновой очистки.
Синхронные операции следует выполнять вне потоков логирования и сетевого loop будущего runtime.
Таймаут блокировки не является жёстким пределом системного fsync при зависшем диске.

Используются локальный файл, journal_mode=DELETE и synchronous=FULL. Журнал
отката и служебные структуры занимают дополнительное ограниченное размером
транзакции место; database_bytes не является квотой всего каталога. Свободные
страницы переиспользуются, файл не обязан уменьшаться после prune. WAL, сетевые
файловые системы и HA не заявляются. Аргументы/результаты находятся в локальной
БД открытым текстом; права доступа задаются владельцем каталога.

Сведения об API и гарантиях SQLite:
[Python sqlite3](https://docs.python.org/3.10/library/sqlite3.html),
[SQLite PRAGMA](https://www.sqlite.org/pragma.html#pragma_max_page_count).

## Срок записи для hub и клиента 0.3.3

StoredCommand теперь возвращает также `deadline`. Он доступен только для строк
текущего поколения журнала. У восстановленных записей прежнего процесса поле
равно None: монотонный срок нельзя переносить между запусками. Схема файла
SQLite не менялась. Командные объекты используют журнал последовательно
через один рабочий поток с отказом при занятости; детали — в
[COMMAND_HUB.md](COMMAND_HUB.md).

## Связь с исполнителем 0.3.4

Фактическое окончание UNKNOWN и доставка его результата — разные подтверждения.
`release_execution` клиентского журнала атомарно снимает execution_active и
возвращает acknowledged=False: клиент обязан доставить hub подтверждение release
даже при потере предыдущей квитанции. На hub это не отменяет ACK источника.
Результат UNKNOWN остаётся неизменным; новый callback из него не запускается.

`CommandClient.reconcile()` отмечает подтверждёнными заведомо неисполненные EXPIRED,
включая восстановленные READY/CLAIMED. UNKNOWN после STARTED остаётся для ручного
разбора; срок или новая generation сами по себе не доказывают окончание работы.
Подробности: [COMMAND_EXECUTION.md](COMMAND_EXECUTION.md).
