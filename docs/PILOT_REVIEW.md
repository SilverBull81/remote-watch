## Новые коммиты

| Коммит | Результат ревью |
| --- | --- |
| `991b8b1` — literal token для relay | Направление правильное: общий валидатор, ровно один token/token_env, секрет исключён из repr, чтение окружения отложено до open. Обязательного перехода обратно на env не требуется. |
| `506472b` — причина старта и HTTP status | Числовой HTTP status полезен. Сырой __cause__ раскрывается стандартным traceback: R1. Сохранение статуса ещё не сохраняет точную причину HTTP-отказа: R2. |
| `81cb374` — явный TLS context relay | Уместное дополнение: доверие CA ограничено клиентом, окружение и системное доверие не меняются; CERT_REQUIRED и проверка имени обязательны. Контекст разделяется по ссылке, поэтому контракт «не менять после передачи» действительно нужен. Причину инцидента Caddy коммит не доказывает. |

### R1 — приватный текст в стандартном traceback, высокий приоритет

В [commands/runtime.py](../src/remote_watch/commands/runtime.py) сохраняется исходное
исключение потока, затем оно передаётся в `raise CommandError(...) from self._error`.
Безопасный `str()` верхней ошибки не делает безопасной всю цепочку. Обычный
`traceback.format_exception`, необработанное исключение или `logger.exception`
включают текст исходной причины. Пользовательский transport может поместить туда
URL, путь либо токен. Ссылка также удерживает исходный traceback с его объектами.

На подставном ModuleNotFoundError воспроизведено: приватный маркер отсутствует
в str верхней ошибки, но присутствует в стандартном форматировании цепочки.
Рабочие credentials для проверки не использовались. Текущий тест
`test_sync_startup_cause` проверяет str и тождество __cause__, поэтому проходит.
Документированная рекомендация приложению не печатать traceback не защищает
обычное необработанное исключение.

Предлагаемое исправление: переносить между потоками безопасную причину с закрытым
набором category/code/stage/http_status, без исходного текста, пути, произвольного
имени класса и traceback. Для CommandError сохранять его фиксированный code и
числовой статус; для неизвестных ошибок — только известную категорию.
Проверять всё форматирование цепочки, а не только str верхнего исключения.
Публичный верхний код и rollback запуска сохранить.

### R2 — потеря точной причины командного HTTP-отказа, средний приоритет

[gateway/command_server.py](../src/remote_watch/gateway/command_server.py) возвращает
HTTP 409 и ограниченное тело `{"code":"stale_session"}` либо другой фиксированный
код. [adapters/command_http.py](../src/remote_watch/adapters/command_http.py) не читает
тело отказа и превращает любой 409 в conflict. Аналогично HTTP 503 сам по себе
не различает capacity и unavailable. Это более ранний недостаток транспорта,
который добавление http_status в dev4 не устранило; не регрессия dev4.

Для пожелания о stale_session нужен ограниченный разбор безопасного error envelope:
известный Content-Type, предел байтов/времени, запрет сжатия/redirect и точная
таблица допустимых пар HTTP status + code. Произвольный текст proxy не становится
причиной ошибки приложения. Если тело не соответствует контракту, остаётся
безопасная классификация по HTTP status. Сохранять статус также при неподходящем
или слишком большом ответе после HTTP 200 и при ошибке decode.
Проверять stale_session через настоящий HTTP/TLS, а не только DirectTransport.

## Пожелание 1 — короткие Telegram-команды

Предлагаемый контракт:

- `Help` в любом регистре и `/help` открывают служебную справку; `/status` и
  другие `/имя` вызывают только зарегистрированные команды приложения.
- Кандидаты определяются по **настроенным** actor/chat ACL и точным Identity.
  Доступность сессии и текущий набор capabilities не сужают список кандидатов
  для неявного выбора. Иначе отключение второго приложения меняет адрес команды.
- При одной разрешённой Identity выбирается она; затем проверяются живая сессия,
  capability и пересечение scopes источника, principal и команды.
- При нескольких Identity требуется `/rw alias команда`; без callback и без
  рассылки всем. В ответе перечисляются только доступные данному actor/chat aliases.
- Выбор «единственного сейчас живого» в первой реализации **не включать**.
  Это отдельная будущая политика, требующая явного решения владельца.
- После выбора сохраняется прежний CommandRequest с точными session_id/hub_epoch;
  повтор события и перезапуск source не выбирают новую сессию.

Формат справки для однозначного назначения:

```text
Allowed Bot Commands:
/check_load
/resume_load
/status
/suspend_load
```

В список попадают только действительно доступные команды текущего приложения;
он не берётся целиком из глобального registry. Зарегистрированная пользователем
команда help по-прежнему доступна через полный `/rw alias help`; короткий `/help`
резервируется для служебной справки. Регистр пользовательских команд и aliases
не меняется автоматически. При отсутствии разрешённого actor/chat справка не
раскрывает конфигурацию, как и сейчас.

Существующий `/rw`, разбор key=value, ограничения текста/аргументов и поведение
ntfy сохраняются. Короткий синтаксис включается на Telegram-входе; общий core
не должен импортировать Telegram adapter. Форму `/command@bot` нельзя обрабатывать
простым удалением суффикса: нужен проверенный собственный bot либо отказ. Для
первого варианта допустимо ограничиться формами, перечисленными выше.

Основные места изменения: `commands/source_protocol.py`, `commands/source.py`,
соединение Telegram reader с runner в `gateway/command_service.py`.
Решение о выборе цели остаётся до записи SourcePending, а не переносится в callback.

Приёмка: разные варианты Help; корректная справка с урезанными scopes; чужой
actor/chat; одна разрешённая, но недоступная цель; две цели при одной живой;
явный alias; повтор события после замены сессии; сохранение /rw; отсутствие
побочных callback от справки и неоднозначного запроса.

## Пожелание 2 — отображение на назначении Telegram/ntfy

Добавить типизированные `display_mode: full | compact | text` и при необходимости
`display_fields` с закрытым набором имён, без форматирующего Python-кода из JSON.
Эти поля реализованы в моделях TelegramConfig/NtfyConfig начиная с dev7.

| Режим | Отображение |
| --- | --- |
| full | Прежний формат по умолчанию, без неожиданной смены существующих сообщений |
| compact | Короткая строка источника и выбранных служебных полей, затем сообщение |
| text | Текст сообщения и, при наличии, exception; без технической шапки |

Compact обязан сохранять различимый источник. Адаптер общего назначения не знает,
сколько независимых приложений сейчас им пользуется, поэтому нельзя скрывать
идентичность по числу недавно увиденных instances. Надёжный минимум — компактное
представление всех пяти компонентов Identity; сокращение до одного instance_id
не различает одинаковые instance_id в разных service/region/environment/host.
Выбор полей не должен позволять случайно убрать этот минимум из compact.
В режиме text отсутствие источника является явным выбором оператора назначения.
Заголовок ntfy остаётся отдельной настройкой title, а не частью технической шапки.

Настройка принадлежит TelegramConfig/NtfyConfig и соответствующему
`destinations[].settings` на gateway. Для direct она задаётся в приложении,
для relay в dev7 — в provider adapter на сервере. По последующему пожеланию
владельца в dev8 расширены RelayConfig и wire schema 3: клиент передаёт ограниченный
override режима/полей отдельно от Notification, а сервер применяет его в render.
Изменение конфига клиента требует перезапуска приложения; gateway продолжает работу.
Разрешения identity/alias остаются серверными. [Подробности](RELAY.md).

В dev7 Notification, Delivery и wire не изменяются; в dev8 Delivery и wire получают
поля представления, а Notification, Identity, IDs, digest, ACL и существующий аудит
сохраняются. Меняется только текст для провайдера. Это не добавляет отсутствующий
durable notification outbox и не обещает новые постоянные журналы каждой доставки.
Исходное сообщение и локальные logging handlers не переписываются.

Приёмка: full совместим со старым выводом; compact различает источники; text
оставляет сообщение/exception; запрещены неизвестные поля; сохраняются Unicode,
усечение Telegram и ntfy, предел JSON-публикации и изоляция получателей. В relay
тестировать настройку на gateway и неизменность wire/ID отдельно от видимого текста.

## Пожелание 3 — текущая готовность и история инцидентов

В `DispatcherStats.last_error` сейчас хранится историческое значение. Простое
обнуление после callback ошибочно: heartbeat выполняется независимо, а результат
может ещё не быть подтверждён hub или записан локально.

Нужна публичная неизменяемая статистика с общим `ready` и отдельным состоянием
этапов `poll`, `heartbeat`, `storage`, `result`. Для каждого этапа: текущий код
отказа, накопленные временные отказы, число восстановлений и при наличии безопасный
HTTP status. Общий last_error/last_error_stage хранит историю и не обнуляется
из-за успешного callback; приложение использует ready/состояние этапа для текущей
индикации. Если отказали два этапа, восстановление одного не скрывает второй.

Правила восстановления:

- Poll: успешно завершён и проверен соответствующий обмен; отсутствие новой
  команды является успешным опросом. Успех callback сам по себе недостаточен.
- Heartbeat: получен и проверен ответ, обновлена допустимая сессия/lease.
- Storage: действительно завершена операция; истечение timeout не доказывает,
  что поток SQLite остановился, и не освобождает его слот.
- Result: получена соответствующая устойчивая квитанция hub и выполнено локальное
  подтверждение. Необходимо отдельно видеть остающийся неподтверждённый результат.

`ready` означает наблюдаемую исправность контура с действующей сессией, а не
обещание мгновенного исполнения следующей команды. Фактическая занятость callback
остаётся отдельным running. До start и при shutdown ready=false. После
stale_session/истечения lease готовность не возвращается без нового допустимого
lifecycle; прозрачная перерегистрация по-прежнему отдельная задача.

Наблюдение должно находиться также в CommandClient и его обращениях к transport/
StoreWorker: один dispatcher не видит heartbeat и не отличает сбой сохранения
от сбоя HTTP-доставки результата. Не считать одно исключение дважды при его
прохождении через client и dispatcher. Stats читается без сетевых запросов и
SQLite, безопасно из другого потока синхронного RemoteWatcher. История ограничена
счётчиками/последними кодами, не растущим списком событий.

Приёмка: одиночный busy → восстановление; повторяющийся busy; одновременные
ошибки poll/heartbeat и независимое восстановление; HTTP stale_session; успешный
callback с потерей ACK/result; успешный callback перед отказом heartbeat;
ошибка storage и её восстановление; shutdown во время retry; UNKNOWN и запрет
повторного вызова callback. Само чтение stats ничего не восстанавливает и не очищает.

## Caddy: инцидент остаётся открытым

Зафиксировано только сообщение владельца: проблема сертификатов исчезла после
нового старта Caddy. Причина, версия Caddy, точный TLS verify code и журналы
renewal пока неизвестны. Не следует считать это исправлением в dev5 или гарантией,
что этап 0.4 автоматически устранит проблему.

Caddy должен обновлять управляемые сертификаты автоматически; вручную загруженные
сертификаты меняют условия автоматизации. Для внутреннего CA важны постоянное
хранилище и доверие корневому CA у клиента. Это поведение описано в
[Automatic HTTPS](https://caddyserver.com/docs/automatic-https).

При повторении до restart полезно сохранить локально:

1. Версию Caddy и точный код TLS-ошибки клиента: expired, not yet valid,
   unknown issuer, hostname mismatch либо вовсе connection refused.
2. UTC обеих VM; расхождение часов уже известно, а проверка TLS использует
   системное время, не TrustedClock команд.
3. Serial/fingerprint, issuer и notBefore/notAfter сертификата, реально выданного
   endpoint, до и после восстановления. Проверка должна использовать правильные
   имя/IP и root CA, без отключения TLS verification.
4. Журнал Caddy вокруг ошибки renewal, фактическую учётную запись процесса,
   выбранный config и эффективный storage. Перед передачей журнала удалить
   секреты, адреса и остальные приватные сведения.
5. Был ли перезапущен только Caddy или одновременно клиент/venv; отличаются ли
   static `tls cert key` от автоматического `tls internal` в фактическом конфиге.

Для 0.4.2/0.4.4 добавить наблюдение процесса отдельно от проверяемой доступности
TLS ingress, чтение безопасных кодов renewal и проверку сохранения CA/storage.
Autostart/restart решает lifecycle процесса; истёкшая/неподходящая цепочка требует
собственной диагностики. Запуск службой с устойчивой учётной записью/данными
согласуется с [Keep Caddy Running](https://caddyserver.com/docs/running).
