## Единый словарь

| Термин | Значение |
| --- | --- |
| Notifications, уведомления | События приложения, обычно от стандартного logger, отправляемые человеку |
| Commands, команды и ответы | Запрос человека приложению, проверка прав, выполнение callback и ответ на этот запрос |
| Direct, напрямую | Приложение само вызывает API мессенджера для уведомления |
| Gateway, через шлюз | Между приложением и мессенджером работает наш сервер |
| Notification gateway | Серверный компонент, пересылающий уведомления к провайдеру |
| Command gateway / hub | Компонент, принимающий команды, адресующий их приложениям и возвращающий ответы |
| Gateway server | Управляющее приложение: запускает компоненты, следит за ними, предоставляет status/stop и трей |
| Relay | Прежнее техническое название пересылки уведомлений через notification gateway; не третий контур |

Сейчас direct/gateway выбирается **для назначения уведомлений**. Путь команд
из Telegram/ntfy использует command gateway. Прямой приём команд в приложении
как готовый альтернативный режим не реализован. Возможность поднять gateway
на той же машине не превращает его в прямой адаптер команд.

```text
Notifications: приложение → адаптер → мессенджер
           или приложение → notification gateway → адаптер → мессенджер

Commands:      мессенджер → command gateway → приложение
Ответ:         приложение → command gateway → мессенджер
Help/отказ:                 command gateway → мессенджер
```

Ответы callback, справка и отказы отправляются командным контуром. Они не проходят
через logger/очередь уведомлений. Если сам callback пишет в logger, такая запись
может дополнительно стать обычным уведомлением согласно маршрутам приложения.
Служебные сообщения manager владельцу — отдельные прямые уведомления, не ответы
команд и не пересылка через неисправный дочерний gateway.

Два контура нужны из-за разных правил. Для уведомлений допустимы фильтрация,
переполнение очереди, TTL и возможные дубликаты доставки. Для команд нужны
ACL actor/chat/target/scopes, привязка к сессии, журнал до исполнения, сохранённый
результат и запрет повторного callback. Ответ должен вернуться в исходный чат,
даже если logger фильтрует INFO или notifications отключены. Компоненты могут
использовать один бот/чат; единственный читатель входящих сообщений остаётся
command source. Это логическое разделение, а не требование двух ботов/серверов.

## Предложение переименований

В пользовательских инструкциях предпочтительны «напрямую» и «через gateway»;
`relay` оставляем пояснением старых конфигов/протокола. Для кода предлагается:

| Сейчас | Предлагаемое основное имя |
| --- | --- |
| `RelayConfig`, `RelayChannel` | `NotificationGatewayConfig`, `NotificationGatewayChannel` |
| `adapters/relay.py` | `adapters/notification_gateway.py` |
| `relay_protocol.py` | `notification_gateway_protocol.py` |
| `DeliveryMode.RELAY` | `DeliveryMode.GATEWAY` с совместимым старым значением |

Не переименовывать всё одним поиском/заменой. Сначала добавить новые имена
и изменить примеры, сохранив старые imports/re-exports и значения конфигов.
Перенос реализации в файлы с новыми именами — отдельный проверяемый коммит.
Прежние wire schemas, URL, hash/canonical serialization, журналы и extra `relay`
сохраняются. Удаление совместимых имён не требуется для работающих приложений.
Новые имена не должны создавать впечатление, что notification adapter также
регистрирует команды. Это предложение ещё не изменяет публичный API.

## Автоматическое восстановление командной связи

Это доработка средней сложности, затрагивающая безопасность исполнения,
а не только повтор HTTP-запроса. Сейчас transient network/busy повторяются,
пока жива командная сессия. После истечения lease или смены hub epoch клиент
перестаёт принимать новые команды и сам не регистрируется заново.
Уведомления сессии не имеют: очередные отправки могут продолжиться после
восстановления gateway, но уже истёкшие/потерянные уведомления не воскресают.

Особенность кода: session_id также связан с поколением журнала клиента.
`_install_session` отвергает смену hub epoch, а `flush_results` отправляет только
результаты, относящиеся к текущей сессии. Простая замена session_id теряет этот
контракт; переоткрытие журнала при ещё работающем callback тоже небезопасно.

Предлагаемый порядок отдельной реализации:

1. ADR: определить различие живого владельца журнала, командной сессии и hub epoch;
   правила восстановления старых результатов и выданных разрешений. Не обещать
   бесшовного восстановления старых UNKNOWN. Если нужен новый recovery endpoint,
   сначала описать его авторизацию, корреляцию и совместимость.
2. Один координатор reconnect в CommandClient: ограниченный backoff с jitter,
   по одному запросу, отмена при shutdown. Повторять временную недоступность;
   denied/конфликт Identity/ошибку TLS доверия показывать отдельно, без обхода
   проверок и без бесконечного создания новых регистраций.
3. Во время восстановления остановить выдачу новых callbacks; учесть уже начатую
   работу и сохранённые результаты. Сначала восстановить безопасное состояние,
   затем разрешить новую сессию. Старые команды никогда не переводить на неё.
   UNKNOWN сохраняет ограничения до предусмотренного контрактом разбора.
4. Публичное состояние reconnect/recovered и причина блокировки. Готовый listener
   manager не означает, что все приложения восстановили командные сессии.
5. Регрессии: рестарт hub в простое; длинный обрыв до expiry; callback во время
   рестарта; потеря ACK после действия; старые source events и grants; два клиента;
   конфликт Identity; shutdown во время backoff; отказ storage/TLS/авторизации.
   Критерий: новые команды снова доступны без перезапуска приложения, а старый
   callback не повторяется. Заблокированный UNKNOWN остаётся явно видимым.

Приоритет — до эксплуатационной приёмки 0.4, желательно до подготовки deploy.
Переименования лучше завершить отдельным коммитом перед изменением lifecycle,
чтобы diff восстановления было проще проверить.

- Проверить существенные изменения процессов в Windows/Linux CI; последний
  локальный проход 0.4.2 на Windows не заменяет платформенную матрицу.
- Live команды ntfy оставлены в резерве по выбору владельца, без обязательной
  покупки. Успешные исходящие уведомления ntfy этим не отменяются.
- Следующая ранее выбранная интеграция — Matrix. До неё нужны решение по SDK,
  размещению и encrypted rooms; это не незавершённая часть 0.1–0.3.
- По отдельной потребности: durable notification outbox, batching/deduplication,
  quiet hours, fallback/escalation, вложения, email/webhook/Apprise, hot reload,
  группы/broadcast и HA. Не считать их обязательствами текущего этапа.
- Разбор UNKNOWN сейчас остаётся явной процедурой; удобный административный
  инструмент можно обсудить отдельно. Автоматическое повторное исполнение
  неизвестного результата не планируется.
- Для публичного распространения понадобится лицензия; сейчас использование
  частное. MAX и удалённое исполнение произвольного shell/Python вне плана.

Остаток собственно 0.4: deploy с шаблонами и сохранением CA/SQLite/секретов;
doctor сервера и клиента; установка службы manager и проверка reboot/восстановления.
Работающая служба Caddy не заменяет службу нового gateway_server.
