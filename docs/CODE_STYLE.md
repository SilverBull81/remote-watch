## Шапки и версии

Python-файл начинается с назначения, затем следуют Version A.B.C, автор с фактической
моделью и время изменения по Москве в формате YYMMDD-HHMMSS. После метаданных —
иерархический перечень собственных классов, методов, функций и значимых констант.
В тестах используется блок «Тесты». Между назначением, строками метаданных,
разделами перечня и отдельными группами классов оставляется строка `#`.
Методы группируются под своим классом. Короткие списки функций и экспортов можно
оставлять компактными: без строки `#` после названия раздела и между пунктами.
После шапки — две пустые строки.
В Markdown эти метаданные следуют за заголовком документа.

Пример расположения блоков шапки:

```python
# Регистрация команд приложения и проверка их обработчиков.
#
# Version 1.0.0
#
# Автор: Sergey Fundobny (silverbull@mail.ru) + GPT-6
#
# Дата и время последнего изменения: 260928-121352
#
# Классы:
# -> CommandSpec: Описание команды и условий её выполнения.
#    Специальные методы:
#    -> __post_init__(): Проверка описания команды при регистрации.
#
# -> CommandRegistry: Реестр команд с поиском по имени.
#    Интерфейс:
#    -> from_callbacks(): Регистрация словаря обработчиков.
```

Новый файл начинает с 1.0.0. Изменение существующего документа или кода повышает
версию минимум на patch и обновляет timestamp. A >= 1, B/C от 0 до 9;
переполнение переносится в следующий разряд. Версии файлов независимы от версии
пакета: версия пакета задаётся в pyproject после появления реализации.
При первичном введении шапки в ранее неверсионированный документ ставится 1.0.0.
Git/config-файлы не требуют вставки авторских шапок.

Перечень сущностей соответствует содержимому. В __init__.py перечисляются только
реальные imports/exports. Нет пустых секций и комментариев об отсутствии функций.
Служебный блок запуска описывается ниже; в перечень функций он не включается.

## Секции и функции

Секции по содержимому: ИМПОРТ, КОНСТАНТЫ, КЛАССЫ, ФУНКЦИИ, ТЕСТЫ, ЭКСПОРТ.
Секции обрамляются комментариями из звёздочек; классы, функции и методы — блоками
из дефисов с русским описанием назначения и закрывающим разделителем.
Разделитель с учётом отступа занимает до 115 символов. Соседние закрывающие
разделители не дублируются. Между самостоятельными блоками верхнего уровня —
две пустые строки, между методами — одна.

Закрывающие разделители вложенных блоков располагаются изнутри наружу: сначала
разделитель последнего метода с отступом класса, затем разделитель самого класса
без этого отступа. То же правило действует для вложенных функций. Это разные
границы блоков, поэтому оба разделителя сохраняются.

## Группы методов

В шапке файла и в реализации класса используется один порядок:

1. `__init__` — заголовок `КОНСТРУКТОР`, без дополнительного описания после двоеточия.
2. Публичные методы `x` и свойства — `ИНТЕРФЕЙС : Назначение`.
3. Остальные методы `__x__` — `СПЕЦИАЛЬНЫЙ МЕТОД : Назначение`.
4. Внутренние методы `_x` и приватные `__x` — `СЛУЖЕБНЫЙ МЕТОД : Назначение`.

В оглавлении под классом используются группы «Конструктор», «Интерфейс»,
«Специальные методы», «Служебные методы». Пустые группы не добавляются.
Поля, константы и docstring остаются перед методами; внутри группы методы следуют
в смысловом порядке, а не обязательно по алфавиту. Парные sync/async методы
располагаются рядом; property и его setter не разрываются. Зависимости декораторов
и выражений, вычисляемых при создании класса, должны сохраняться при перестановке.

`__post_init__`, `__enter__`, `__exit__`, `__getitem__` и подобные методы относятся
к специальным: их вызывает соответствующий протокол Python или dataclass.
Автоматически созданные методы dataclass в оглавление не включаются.
Правило обозначает назначение и доступность методов, а не требует переименовывать
публичные API или придумывать собственные имена вида `__x__`.

## Оформление тел методов

В теле функции пустые строки разделяют смысловые этапы: проверку типов,
проверку допустимых значений, копирование данных, преобразование и возврат результата.
Отдельные проверки можно разделять пустыми строками, как в `Notification.__post_init__`.
Связанные короткие операции допускается оставлять вместе. Не уплотнять код ради
экономии строк и не убирать вручную добавленные интервалы без причины.

Имена английские. Аргументы в многоаргументных сигнатурах — столбиком;
пустая сигнатура остаётся компактной. Все функции, включая внутренние и тестовые,
имеют type hints. Между сигнатурой и английским docstring — одна пустая строка.
Каждый явный аргумент, кроме self/cls, описывается парой :param/:type с пустой
строкой между парами. Для ненулевого результата нужны :return:/:rtype:;
для None эти строки опускаются, аннотация -> None остаётся.

После docstring — пустая строка, русские комментарии аргументов, пустая строка
и алгоритм. Вложенные функции оформляются по тем же правилам.

## Поля dataclass и пояснения алгоритма

Каждое поле dataclass, включая внутренние поля и ClassVar, получает русский
комментарий справа от объявления. Английский docstring класса сохраняет общее
описание контракта, но не заменяет комментариев к полям. Указывать смысл значения,
единицы измерения и значение None, если они не очевидны:

```python
command_id: str              # Идентификатор запроса на выполнение команды.
timeout: float = 10.0        # Предельное время выполнения, секунды.
topic: str | None = None     # Требуемая тема; None — любая.
```

Внутри dataclass комментарии выравниваются по одной или двум общим колонкам.
Колонки выбираются по шагам табуляции в четыре позиции, но заполняются пробелами,
как в текущем коде. Между объявлением и `#` — не менее двух пробелов.
Для большинства полей используется основная колонка; длинные объявления могут
иметь вторую колонку или индивидуальный отступ. Не нужно сдвигать весь блок вправо
из-за одного длинного поля. Единая колонка для всех классов файла не требуется.

Если объявление с комментарием выходит за предел 115 символов, вызов `field(...)`
переносится на несколько строк; комментарий остаётся справа от первой строки
объявления. Выравнивание не должно ухудшать читаемость или создавать чрезмерно
длинные строки. Существующие удачно выбранные колонки сохраняются при новых правках.

Внутри функций и методов нужны развёрнутые русские пояснения, особенно в длинных
проверках и преобразованиях. Перед каждым существенным этапом объяснять, что делает
блок и зачем это нужно. Отдельно пояснять неочевидные ограничения, защитное копирование,
работу с изменяемыми данными, частичный успех, отмену и освобождение ресурсов.
Однострочный очевидный метод не требует искусственного пересказа каждого оператора.
Комментарии должны позволять вспомнить ход работы через несколько месяцев без
повторного изучения всей архитектуры. При изменении алгоритма обновлять и пояснения.

Использовать естественный русский язык, а не буквальный перевод технических оборотов.
Например, «Подготовленное уведомление для отправки» понятнее, чем
«Сериализуемый неизменяемый снимок уведомления»; «Ограничения размера уведомления»
понятнее, чем «Бюджеты удерживаемого снимка». При необходимости отдельно объяснить,
что поля объекта нельзя менять и что его данные можно преобразовать в JSON.
Имена API (`LogRecord`, `callback`, `asyncio`) сохраняются там, где это помогает
найти соответствующий код. Не смешивать русскую фразу с английскими словами без нужды.

## Служебный блок запуска

В конце библиотечных модулей, `__init__.py`, тестов и других Python-файлов,
не предназначенных для самостоятельного запуска, нужен служебный блок по образцу MLTrade:

```python
#------------------------------------------------------------------------------------------------------------------
# СЛУЖЕБНЫЙ БЛОК : Сообщение о назначении файла
#------------------------------------------------------------------------------------------------------------------
if __name__ == "__main__":
    print("Модуль remote_watch.commands не предназначен для прямого запуска.")
#------------------------------------------------------------------------------------------------------------------
```

При обычном импорте блок ничего не выводит. В тестовых файлах сообщение дополнительно
подсказывает использовать pytest. Блок не должен запускать демонстрации, обращаться
к сети или менять настройки приложения. У настоящих точек входа остаётся их рабочая логика.

Как и обычный завершающий `__main__`-блок, он выполняется после импортов.
Модули с относительными импортами запускаются в контексте установленного пакета
через `python -m remote_watch.commands`, а не по пути к файлу. Блок не является
механизмом исправления отсутствующих зависимостей или путей импорта.

## Импорты и форматирование

Порядок: __future__, стандартная библиотека, сторонние пакеты, собственные модули.
Проверяется Ruff I001; не отключать его только ради произвольного порядка.
Для целевого Python 3.10+ использовать X | Y вместо Union[X, Y].
Планируемая ширина Python-строки — 115. Markdown-параграфы желательно переносить
примерно на 80–100 символах; таблицы и URL допускают более длинные строки.
Автоформаттер не должен разрушать договорённости по сигнатурам и разделителям.

## Специфика logging-библиотеки

Диагностика использует уровни logging и при необходимости префикс
ClassName.method_name(): или function_name():. Это правило внутренних сообщений;
пакет не требует такого префикса от приложений.

Из соседних проектов намеренно не переносится строгая проверка внешнего logger
только через isinstance(Logger): она исключила бы поддерживаемый LoggerAdapter.
Если API принимает logger, он явно документирует допустимые стандартные типы
или узкий структурный контракт. Никакой сети в logging handler.
Нельзя применять общий logger для диагностики собственного транспорта.
Credentials, полные provider payload и URL с токенами не выводятся.

## Кодировки и переводы строк

Python и Markdown — UTF-8 BOM, CRLF. Git attributes фиксируют CRLF рабочего дерева;
Git может нормализовать индекс в LF. Настройки Git/JSON/TOML — UTF-8 без BOM, CRLF.
JSON, если появится: отступ 2 пробела; короткие primitive lists компактны.
Это правило оформления, не выбор JSON как публичного формата конфигурации.

Смешанные newlines, повреждённая кириллица, trailing whitespace и реальные секреты
недопустимы. Ссылки внутри репозитория — относительные и проверяемые.
Документация ясно различает реализованное поведение, проектные решения и гипотезы.

`python tools/check_style.py` проверяет Python-файлы src, tests и tools:
BOM/CRLF, версии и timestamps, ширину строк, type hints, структуру docstring,
наличие русских пояснений аргументов и полей, порядок групп методов и служебные блоки.
Проверка не исполняет модули и не читает локальные credentials. Она не заменяет
ручную оценку ясности текста, смысловых интервалов и правильности разделителей.
Ruff дополнительно проверяет E501; автоматическое переформатирование не включено.

Порядок проверок и tooling: [DEVELOPMENT.md](DEVELOPMENT.md).

## Дополнительная проверка закрывающих строк

Закрывающая строка многострочной сигнатуры `) -> ...:` имеет тот же отступ,
что и `def`. Разделители закрывают сначала вложенный метод, затем класс.
`tools/check_style.py` проверяет оба правила, включая вложенные тестовые функции.
Описание результата в docstring должно называть возвращаемое значение;
шаблон `The value described by this operation.` запрещён. Формальная проверка
не заменяет чтение русских комментариев и проверку смысла описаний.
